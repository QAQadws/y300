# 漫画解析与书架问题修复方案

## 背景

当前漫画模块主要围绕 Discuz 帖子的首楼 `message` 解析图片和章节链接。随着历史帖子格式增多，出现了三类明显问题：

1. `http://data/attachment/sinaimg/...jpg` 这类旧帖新浪图床附件无法稳定解析和加载。
2. 部分漫画图片不出现在 `message` 的 `<img>` 中，而只存在于 `postlist.attachments` 字段。
3. 同一漫画的不同话分别收藏后，会以不同 `yamibo:<tid>` 作品 ID 出现在漫画书架中。
4. `unified_shelf_page.dart` 列表模式下分类横向栏透明，滚动时能透出列表；列表封面缺失时仍显示“无图片”占位图标。

本文基于当前 `lib` 代码给出根因分析和分阶段修复方案。

## 当前代码链路

### 帖子到漫画入库

- `ThreadDetailData.fromVariables` 读取 `variables['postlist']`，每个楼层映射为 `ThreadPost`。
- `ThreadPost` 当前只保留 `pid`、`author`、`authorId`、`message`、`number`、`isFirst`、`dateline`，没有保留 `attachments`。
- 线程详情页调用 `ComicPostAggregationService.build(posts)`，目前聚合首楼，必要时聚合楼主二楼。
- `HtmlComicParserService.parse(message: ...)` 只接收一段 HTML 字符串。
- `ForumPostDomExtractor.extractImageSources(html)` 从 `<img>` 的 `src/data-src/data-original/file` 中提取图片。
- `LocalComicRepository.addToShelf` 使用 `parsedPost.imageUrls` 写入默认章节图片。
- 阅读器缺图时，`NetworkComicReaderService.fetchEpisodeImagesByTid` 重新拉取帖子详情，但仍只解析首楼 `message`。

### 漫画作品 ID

- `ThreadDetailController._buildComicId` 固定返回 `yamibo:<tid>`。
- `RepositoryComicFavoriteIngestService.buildComicWorkId` 同样固定返回 `yamibo:<tid>`。
- `LocalComicRepository` 的 `episodes.source_tid` 已保存每话来源 tid，但入库前没有用这些 `source_tid` 查找已有作品。
- `shelf_items` 只约束 `(category_id, comic_id)` 唯一，无法阻止同一漫画以不同 `comic_id` 入架。

### 统一书架 UI

- `UnifiedShelfPage` 使用 `Column`：任务进度、错误提示、`FixedSlotPagerHeader`、`Divider`、`Expanded(PageView)`。
- `FixedSlotPagerHeader` 内部是一个裸 `SizedBox + Stack + SingleChildScrollView/Row`，没有自己的不透明背景或 `Material`。
- `_WorkList` 的 `ListTile.leading` 固定存在，内部 `_buildLeadingCover` 使用 `Icons.image_not_supported_outlined` 作为缺图 placeholder。

## 根因分析

### 1. sinaimg 旧格式 URL 解析问题

示例：

```text
http://data/attachment/sinaimg/tid503019/pid39465469/uid365616/63c446acd7a9d.jpg
```

这不是标准的站外绝对 URL。它带有 `http://` scheme，但 host 实际是 `data`，真实语义更像站内路径：

```text
data/attachment/sinaimg/tid503019/pid39465469/uid365616/63c446acd7a9d.jpg
```

当前 `SiteUrlResolver.resolve` 遇到任何 `uri.hasScheme == true` 的输入都会原样返回，因此上述 URL 会保留为 `http://data/...`。后续图片加载、缓存和请求头构建都会把 `data` 当成域名，导致图片请求失败。

此外，当前 `ForumPostDomExtractor.forumChromeImagePattern` 只过滤表情、静态图、头像等，不会过滤 `sinaimg`，所以问题不在 DOM 提取阶段，而在 URL 规范化阶段。

### 2. attachments 图片未进入解析链路

示例附件字段：

```json
{
  "attachment": "201802/16/002909v4kga3k6tkh4mlap.jpg",
  "url": "data/attachment/forum/",
  "attachimg": "1",
  "ext": "jpg"
}
```

当前 `ThreadPost.fromJson` 没有读取 `attachments`，因此数据在模型层已经丢失。后续 `ComicPostAggregationService`、`HtmlComicParserService`、`NetworkComicReaderService` 都只能看到 `message`，无法补充附件图片。

这会影响两条路径：

- 收藏/加入书架时，`parsedPost.imageUrls` 为空，默认章节没有图片。
- 阅读器打开章节后补拉图片时，`fetchEpisodeImagesByTid` 仍只解析 `message`，也无法恢复附件图片。

### 3. 同一漫画重复入架

Discuz 漫画常见结构是每话一个帖子，首楼会有目录或前后章节链接。当前系统将每个收藏帖独立映射为一个作品：

```text
thread 493928 -> comicId yamibo:493928
thread 496140 -> comicId yamibo:496140
```

即使两个帖子互相出现在同一组章节链接中，当前入库流程也不会归并。标题不能作为主判断条件，因为同一漫画不同话的标题格式可能不同，例如组名、站点名、日文名、中文名、话数后缀经常变化。

更可靠的判断依据是章节 tid 集合：

- 一个帖子解析出的章节链接包含多个 tid。
- 本地 `episodes.source_tid` 已保存某作品拥有的章节 tid。
- 如果新收藏帖的当前 tid 或解析出的章节 tid 与已有作品的 `episodes.source_tid` 有交集，就应归并到已有作品，而不是创建新作品。

### 4. 列表模式分类栏透明和缺图占位

分类横向栏透明的原因是 `FixedSlotPagerHeader` 没有背景。它位于 `Column` 顶部，下面是 `PageView` 里的列表。当列表内容滚动到头部下方时，透明区域会透出列表 tile，视觉上像分类栏悬浮在内容上。

列表缺图仍显示“无图片”图标的原因是 `_WorkList` 总是构建 `leading`，并把无封面的情况交给 `ShelfCoverImage` 或 `LibraryCachedImage` 的 placeholder。用户预期是：列表模式没有图片就不显示图片区域，而不是显示一个替代图标。

## 目标设计

### 统一图片来源模型

新增一个小而独立的图片来源抽象，不把附件解析直接塞进 DOM 解析器：

```dart
class ForumPostAttachmentImage {
  const ForumPostAttachmentImage({
    required this.aid,
    required this.url,
    required this.attachment,
    required this.filename,
    required this.imageIndexHint,
  });
}
```

`ThreadPost` 增加：

```dart
final List<ForumPostAttachmentImage> attachmentImages;
```

附件 URL 组装统一交给一个服务，例如：

```dart
class ForumAttachmentImageExtractor {
  List<String> extractImageUrls(ThreadPost post);
}
```

职责：

- 判断 `attachimg == '1'` 或 `ext` 属于 `jpg/jpeg/png/gif/webp`。
- 用 `url + attachment` 拼接附件路径。
- 交给 `SiteUrlResolver` 做最终规范化。
- 按附件 map 的插入顺序或 `aid` 排序，保证漫画页顺序稳定。

### URL 规范化补丁

在 `SiteUrlResolver` 增加 Discuz 伪绝对附件 URL 兼容：

```text
http://data/attachment/...  -> https://bbs.yamibo.com/data/attachment/...
https://data/attachment/... -> https://bbs.yamibo.com/data/attachment/...
```

建议逻辑放在 `uri.hasScheme` 分支之前：

1. trim 和反复解 `&amp;`。
2. 匹配 `^https?://data/attachment/`。
3. 去掉伪 scheme 和 host，得到 `data/attachment/...`。
4. 用站点 origin resolve。

这样 `ThreadPostHtml`、漫画解析、缓存服务、请求头构建都会共享同一规范化行为。

### 聚合解析接口升级

保留 `ComicParserService.parse(message: ...)` 兼容已有测试和调用，同时新增面向帖子上下文的入口：

```dart
class ComicPostParseInput {
  const ComicPostParseInput({
    required this.messageHtml,
    this.attachmentImageUrls = const <String>[],
  });
}

abstract class ComicParserService {
  ParsedComicPost parse({required String message});
  ParsedComicPost parseInput(ComicPostParseInput input);
}
```

`HtmlComicParserService.parseInput` 合并两类图片：

1. DOM `<img>` 图片。
2. `attachments` 图片。

合并规则：

- 按“message 图片在前，attachments 图片在后”。
- 用规范化后的 URL 去重。
- 记录 debug signal，例如 `attachment images=2`、`dedup images=37`。

如果后续发现附件图片在真实阅读顺序上应优先于 message，可通过单独策略参数调整，不要写死散落在调用方。

### 漫画去重与归并

新增一个作品归并服务，例如：

```dart
class ComicWorkIdentityResolver {
  Future<ComicIdentityResolution> resolve({
    required String seedTid,
    required ParsedComicPost parsedPost,
  });
}
```

输入：

- 当前帖子 tid。
- 解析出的章节链接 tid 集合。

候选 key：

- `seedTid`
- `parsedPost.episodeLinks` 中所有可解析 tid。

查找策略：

1. 在 `episodes` 表查询 `source_tid IN candidateTids`。
2. 按命中数量降序排序已有 `comic_id`。
3. 若有命中，返回命中最多的 `comic_id` 作为 canonical comicId。
4. 若无命中，创建新 ID `yamibo:<seedTid>`。

冲突处理：

- 如果命中了多个已有 `comic_id`，先选命中最多且 `updated_at` 最新的作为 canonical。
- 后续阶段再做真正的数据合并；第一阶段可以只避免新重复产生。

入库后，确保当前 seed tid 本身也作为一个 episode 写入 canonical comicId。这样用户从任意一话收藏，都能在同一作品内看到该话。

### 书架 UI 修复

分类栏：

- 在 `FixedSlotPagerHeader` 外层或内部增加不透明 `Material`。
- 背景色使用 `Theme.of(context).colorScheme.surface`，而不是透明。
- 保留 `Divider`，避免视觉粘连。

推荐内部修复，因为该组件是“分页头”，语义上应该自带 header 背景：

```dart
return Material(
  color: Theme.of(context).colorScheme.surface,
  child: SizedBox(height: 56, child: ...),
);
```

列表缺图：

- `_WorkList` 增加 `hasCover(item)` 判断。
- 有封面时构建当前 `leading`。
- 没有封面时 `leading: null`，并适当收紧 `contentPadding`。
- `ShelfCoverImage` 的错误占位只用于“有远程封面但加载失败”的情况，不用于“本来没有封面”的情况。

判断条件：

```dart
bool _hasCover(LibraryWorkItem item) {
  return _notBlank(item.customCoverLocalPath) ||
      _notBlank(item.coverLocalPath) ||
      _notBlank(item.coverImageUrl);
}
```

## 分阶段实施计划

### Phase 1：URL 规范化与 sinaimg 兼容

预计时间：0.5 天。

改动范围：

- `lib/core/network/site_url_resolver.dart`
- `test/core/network/site_url_resolver_test.dart`
- `test/features/thread/domain/services/forum_post_dom_extractor_test.dart`

实现内容：

1. 在 `SiteUrlResolver.resolve` 中识别 `http://data/attachment/...` 和 `https://data/attachment/...`。
2. 将其规范化为 `${AppConfig.siteBaseUrl}/data/attachment/...`。
3. 保持正常绝对 URL、协议相对 URL、根路径、相对路径的现有行为不变。
4. 为 `ForumPostDomExtractor.extractImageSources` 增加覆盖用例，确保示例 sinaimg URL 能输出站内可访问 URL。

验收标准：

- `http://data/attachment/sinaimg/...jpg` 解析为 `https://bbs.yamibo.com/data/attachment/sinaimg/...jpg`。
- `https://img.test/a.jpg` 不被改写。
- `data/attachment/forum/a.jpg` 原行为不变。

风险：

- 极少数真实第三方域名如果正好叫 `data` 会被改写。这个风险可接受，因为示例格式是 Discuz 历史伪 URL，且 host 为裸 `data` 不具备公网可访问性。

### Phase 2：保留并解析 postlist.attachments

预计时间：1 天。

改动范围：

- `lib/features/thread/data/models/thread_detail_models.dart`
- 新增 `lib/features/thread/domain/services/forum_attachment_image_extractor.dart`
- `lib/features/comic/domain/services/comic_post_aggregation_service.dart`
- `lib/features/comic/domain/services/comic_consecutive_op_post_parser.dart`
- `lib/features/comic/domain/services/comic_services_impl.dart`
- 对应测试文件。

实现内容：

1. `ThreadPost` 增加 `attachmentImages` 字段，默认空列表。
2. `ThreadPost.fromJson` 解析 `attachments`：
   - 兼容 Discuz 返回 map。
   - 忽略非 map 项。
   - 只保留图片附件。
3. 新增 `ForumAttachmentImageExtractor`，负责把 `url` 和 `attachment` 拼接并规范化。
4. `ComicPostAggregationResult` 增加聚合后的附件图片 URL：
   - 首楼附件参与。
   - 若二楼被合并，二楼附件也参与。
5. `HtmlComicParserService` 新增 `parseInput`，合并 DOM 图片和附件图片。
6. `NetworkComicReaderService.fetchEpisodeImagesByTid` 也改为读取 `ThreadPost` 的附件图片，而不是只解析 `firstPost.message`。

验收标准：

- 示例附件能生成 `https://bbs.yamibo.com/data/attachment/forum/201802/16/002909v4kga3k6tkh4mlap.jpg`。
- `message` 没有漫画 `<img>`、但 `attachments` 有图片时，加入书架后默认章节有图片。
- 阅读器打开历史章节时，即使本地没有图片缓存，也能从附件补拉图片。
- 表情附件、非图片附件不进入漫画图片列表。

风险：

- Discuz `attachments` 的 `isimage` 示例为 `-1`，不能只用 `isimage > 0` 判断。应以 `attachimg == '1'` 或扩展名白名单为主。
- 附件顺序必须稳定。建议优先用原 map 遍历顺序；如发现不稳定，再按 `aid` 或 `dateline` 排序。

### Phase 3：解析入口收敛，避免首楼/多楼逻辑分叉

预计时间：0.5 天。

改动范围：

- `ComicPostAggregationService`
- `ComicConsecutiveOpPostParser`
- `NetworkComicReaderService`
- `ThreadDetailController`
- `RepositoryComicFavoriteIngestService`

实现内容：

1. 定义统一的 `ComicPostParseInput` 或 `ComicPostBundle`。
2. 所有“解析漫画图片”的调用都走同一入口：
   - 详情页加入书架。
   - 收藏同步入库。
   - 阅读器懒加载章节图片。
   - 连续楼主楼层解析。
3. `HtmlComicParserService.parse(message: ...)` 保留为测试和旧调用兼容，但内部委托到新入口。

验收标准：

- 不再有一条路径支持附件、另一条路径不支持附件的行为差异。
- debug 信息能分辨 DOM 图片数量和附件图片数量。

风险：

- 调用点较多，容易漏改。建议先增加测试，再逐步替换。

### Phase 4：基于章节 tid 的漫画归并
请你注意归并只发生在漫画模块的shelf中，在收藏模块应保留全部的收藏，不过在收藏模块打开同一漫画的不同收藏帖子，应会打开同一个detail页
预计时间：1.5 天。

改动范围：

- `lib/features/comic/data/comic_repository.dart`
- `lib/features/comic/data/local_comic_repository.dart`
- `lib/features/comic/data/comic_favorite_ingest_service.dart`
- `lib/features/thread/presentation/thread_detail_controller.dart`
- 新增 `lib/features/comic/domain/services/comic_work_identity_resolver.dart`
- 对应仓库和同步测试。

实现内容：

1. 新增仓库查询方法：

```dart
Future<String?> findComicIdBySourceTids(Set<String> sourceTids);
```

2. 查询 SQL：

```sql
SELECT comic_id, COUNT(*) AS hit_count
FROM episodes
WHERE source_tid IN (...)
GROUP BY comic_id
ORDER BY hit_count DESC
LIMIT 1
```

3. `ComicWorkIdentityResolver` 用 `seedTid + parsedPost.episodeLinks` 得到候选 tid 集合。
4. 入库前先解析身份：
   - 命中已有作品：使用已有 `comicId`。
   - 未命中：使用 `yamibo:<seedTid>`。
5. `addToShelf` 中确保 seed tid 对应章节存在：
   - 如果 `parsedPost.episodeLinks` 没有包含当前 tid，也要插入当前帖章节。
   - 章节标题优先用 subject parser 的 `episodeLabel`，没有则用 `首楼` 或当前标题。
6. `ThreadDetailController.isInShelf` 也使用 resolver，而不是只查 `yamibo:<当前 tid>`。
7. 收藏同步时，`FavoriteThreadCacheRecord.workId` 写 canonical comicId。

验收标准：

- 先收藏第 2 话，再收藏第 6 话，书架只有一个漫画作品。
- 新收藏的话会合并为已有作品的章节。
- 不依赖标题相似度。
- 如果一个帖子没有任何章节链接，仍按 `yamibo:<tid>` 独立入库。

风险：

- 旧数据已经重复存在时，仅避免新增重复还不够。建议把历史合并作为 Phase 5。
- 若两个不同漫画意外互链或共用 tid，可能误合并。tid 是帖子唯一 ID，真实误合并概率低；但冲突时应记录 debug 日志，便于回滚。

### Phase 5：历史重复作品合并与迁移

预计时间：1 天。

改动范围：

- `LocalComicRepository`
- 可选新增后台维护服务，例如 `ComicDuplicateMergeService`
- `docs/开发文档.md` 可记录维护入口。

实现内容：

1. 扫描 `episodes.source_tid`，找出同一 tid 被多个 `comic_id` 持有的情况。
2. 选择 canonical：
   - 优先在书架中存在的作品。
   - 再比较章节数。
   - 再比较最近 `updated_at`。
3. 合并数据：
   - episodes：迁移到 canonical，episodeId 重建为 `$canonicalComicId:$sourceTid`。
   - episode_images：随 episodeId 更新。
   - reading_progress：保留最近更新。
   - shelf_items：合并分类关系，避免重复。
   - custom metadata 和 custom cover：优先保留 canonical，非空补齐。
4. 删除被合并的 duplicate comic rows。
5. 提供 dry-run 日志，正式执行前可统计影响数量。

验收标准：

- 已经重复入架的同一漫画可以合并为一个作品。
- 阅读进度、缓存状态、封面尽量不丢。
- 合并过程可重复执行，不会破坏已合并数据。

风险：

- 这是数据迁移，风险高于前几阶段。建议先不自动执行，可放到设置页维护按钮或启动后一次性带开关执行。

预计时间：0.5 天。

   - `color: Theme.of(context).colorScheme.surface`
   - 保持高度和槽位宽度不变。
2. `_WorkList` 增加 `_hasCover`。
3. `itemBuilder` 中：
   - 有封面才传 `leading`。
   - 无封面传 `leading: null`。

## 推荐实现顺序

1. Phase 1：先修 URL 规范化，成本低、收益直接，也能让帖子详情页图片显示受益。
2. Phase 2：补齐附件模型和附件图片解析，解决无法解析章节图片的核心问题。

1. 打开含 `http://data/attachment/sinaimg/...` 的帖子，确认帖子详情和漫画阅读器都能显示图片。
2. 打开只有 attachments 图片的帖子，加入漫画书架后能阅读。
3. 收藏同一漫画不同章节帖子，确认漫画书架只有一个作品。

5. 删除封面或遇到无封面作品时，确认列表项不显示“无图片”图标。

## 代码风格建议

- 附件解析、URL 规范化、作品身份识别分别独立成小服务，不要把逻辑堆进 `LocalComicRepository` 或 UI。
- 数据模型保持向后兼容，`ThreadPost.attachmentImages` 默认空列表。
- 对外保留旧接口，新增上下文接口逐步迁移，降低一次性改动风险。
- 对数据迁移使用 dry-run 和日志，不在普通解析流程里偷偷删除历史数据。
- debug signal 继续沿用 `ComicParsingDebugInfo`，便于后续用户贴日志时定位是 DOM 图、附件图还是去重出了问题。
