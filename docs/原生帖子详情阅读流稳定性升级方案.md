# 原生帖子详情阅读流稳定性升级方案

## 1. 背景与现状

原生帖子详情页已经从“一楼一个巨大组件”升级为 `ThreadDetailRenderEntry` 驱动的阅读流：

- `postHeader`
- `postBodySegment`
- `postFooter`
- `pagination`

正文 HTML 通过 `ThreadPostBodyRenderPlanner` 解析、normalize，并按约 600 字生成 segment。阅读态不再启用 `SelectionArea`；长按正文后通过底部抽屉提供 `选择复制` 和 `全部复制`，其中 `选择复制` 进入独立页面一次性渲染整楼正文并启用选择系统。

这条路线是正确的：阅读页优先流畅，复制页独立承担选择系统成本。下一阶段的重点不应再推翻渲染架构，而是围绕“滚动稳定性”继续收口。

当前最需要补齐的问题是：

- 多图片帖子中，图片尺寸/缓存尺寸异步补全后可能改变 item 高度，引起上滑回溯。
- 行内表情尺寸异步补全后可能改变行高，导致楼层高度漂移。
- render plan 已经出现，但资源布局 hint、图片阅读器入口、诊断数据还没有形成统一模型。
- 复制功能已可用，但纯文本格式、表情文本、引用换行仍需要按论坛语义继续细化。
- 后续繁简转换、字号、段距、行高设置需要接入显示层，而不是污染 parser 或原始 document。

## 2. 总体目标

本方案的核心目标是构建一个稳定、可维护、可扩展的“原生论坛帖子阅读流”。

### 2.1 用户体验目标

- 长文本、多图、多表情帖子上下滑动时不再出现明显卡顿、回溯、跳动。
- 图片和表情加载不应让已显示楼层突然变高或变矮。
- 复制功能可用，但不影响默认阅读态性能。
- 后续图片阅读器、繁简转换、字体设置、段距设置可以接入，不需要重写帖子详情页。

### 2.2 工程目标

- 保持 `thread` feature 内部职责清晰：
  - `domain` 负责正文语义、render plan、布局 hint、纯文本提取。
  - `data/cache` 负责资源尺寸持久化和缓存命中。
  - `presentation` 只消费 render plan 和 layout hint，不在 build 中做重解析。
- 所有滚动中可能改变布局高度的异步行为必须有明确策略。
- 资源尺寸、阅读器图片组、复制文本、显示设置都从同一份 render plan 派生，避免多套解析逻辑。

## 3. 设计原则

### 3.1 阅读态优先稳定

阅读态的第一优先级是滚动稳定，而不是立刻追求最精确的图片比例或最完整的复制能力。

规则：

- 进入当前阅读生命周期后，已构建 entry 的高度应尽量不再因为异步资源结果变化。
- 图片真实尺寸、表情真实尺寸可以写入缓存，但默认不立即修改当前已显示 widget 的布局尺寸。
- 当前页面使用的布局尺寸来自“首次构建时可同步得到的 hint”。

### 3.2 解析、计划、渲染分层

帖子正文处理链路应保持：

```text
raw HTML
  -> ThreadPostBodyDocument
  -> normalized document
  -> ThreadPostBodyRenderPlan
  -> ThreadDetailRenderEntry
  -> Widget rendering
```

后续繁简转换、字号、行高、段距属于显示层设置，应生成显示用 render plan 或显示用 text span，不应修改原始 HTML 和 parser 输出。

### 3.3 阅读态与复制态分离

阅读态：

- segment 懒加载。
- 不启用页面级或楼内全量 `SelectionArea`。
- 长按只打开复制动作。

复制态：

- 独立页面。
- 一次性渲染单楼完整正文。
- 可以启用 `SelectionArea`。
- 可以为了复制体验承担额外布局成本。

### 3.4 资源布局 hint 是领域能力

图片和表情的布局尺寸不应散落在 widget 内部临时判断。它们应抽象成稳定的 layout hint：

```dart
enum ThreadLayoutHintSource {
  htmlAttribute,
  cacheRecord,
  forumSmileyCatalog,
  contentDefault,
}

class ThreadImageLayoutHint {
  const ThreadImageLayoutHint({
    required this.aspectRatio,
    required this.source,
    required this.lockForCurrentBuild,
  });

  final double aspectRatio;
  final ThreadLayoutHintSource source;
  final bool lockForCurrentBuild;
}

class ThreadInlineImageLayoutHint {
  const ThreadInlineImageLayoutHint({
    required this.size,
    required this.source,
    required this.lockForCurrentBuild,
  });

  final Size size;
  final ThreadLayoutHintSource source;
  final bool lockForCurrentBuild;
}
```

Widget 消费 hint，不直接决定“该不该异步改高度”。

### 3.5 诊断先于猜测

帖子详情性能问题高度依赖内容结构。需要在更多页或 debug flag 中提供诊断开关，记录：

- entry build 次数。
- render plan 生成次数。
- 图片/表情布局 hint 来源。
- 资源解码后是否尝试改变布局。
- scroll offset 是否被 `jumpTo` / `animateTo` / 目标楼层定位修改。

## 4. 目标架构

### 4.1 Domain 层

建议新增或完善以下领域模型：

```dart
class ThreadPostBodyRenderPlan {
  final ThreadPostBodyDocument document;
  final List<ThreadPostImageBlock> images;
  final List<ThreadPostBodySegment> segments;
  final ThreadPostPlainTextSnapshot plainText;
  final ThreadPostImageGroup imageGroup;
}

class ThreadPostBodySegment {
  final int index;
  final List<ThreadPostBodyBlock> blocks;
  final String anchorId;
  final int estimatedTextLength;
}

class ThreadPostImageGroup {
  final String tid;
  final String pid;
  final List<ThreadPostImageEntry> entries;
}

class ThreadPostImageEntry {
  final String url;
  final String rawUrl;
  final int indexInPost;
  final String? aid;
  final ThreadImageLayoutHint layoutHint;
}
```

说明：

- `ThreadPostImageGroup` 为后续自制图片阅读器预留，点击任意图片时不再临时从 widget 树拼数据。
- `plainText` 可以由 `ThreadPostBodyPlainTextExtractor` 生成，也可以先保持 service 形态，等接口稳定后再缓存到 plan。

### 4.2 Data / Cache 层

缓存层已经有 `CachedImageRecord.width/height` 方向，后续应明确尺寸写入和读取策略：

```dart
abstract class ThreadResourceDimensionRepository {
  Future<ThreadImageDimension?> getImageDimension(String cacheKey);
  Future<void> recordImageDimension({
    required String cacheKey,
    required int width,
    required int height,
  });
}
```

注意：

- 读取尺寸可以参与下一次 render plan 或 widget 首次构建。
- 写入尺寸不代表当前 widget 必须立即改变布局。

### 4.3 Presentation 层

帖子详情阅读页保持 entry builder：

```text
ThreadDetailContent
  ListView.builder
    postHeader
    postBodySegment
    postFooter
    pagination
```

正文 segment widget 只消费：

- `ThreadPostBodyRenderPlan`
- 当前 `ThreadPostBodySegment`
- 图片 headers
- 链接点击回调
- 图片点击回调
- 长按复制回调

不应在 segment widget 内做：

- HTML parse。
- normalize。
- 全楼选择系统。
- 高成本资源预加载。

## 5. 分阶段实现计划

## Phase 1：锁定阅读态资源布局高度

### 目标

解决多图上滑回溯、表情加载后楼层高度漂移的问题。

### 主要改动

1. 调整 `ThreadPostImageBlockView`
   - 首次 build 时确定 `aspectRatio`。
   - 优先级：
     - HTML `width/height`
     - 已同步可得的缓存尺寸
     - 默认漫画比例 `0.7`
   - 图片解码成功后只记录尺寸到 cache，不在当前 widget 生命周期内 `setState` 改 `aspectRatio`。

2. 调整行内表情布局
   - 有 HTML 尺寸或表情 catalog 尺寸时使用真实尺寸。
   - 没有尺寸时使用稳定 fallback。
   - 解码得到真实尺寸后只写缓存，不立刻改变当前行高。

3. 明确布局锁定策略

```dart
class ThreadResourceLayoutPolicy {
  const ThreadResourceLayoutPolicy({
    required this.lockImageAspectRatioForCurrentBuild,
    required this.lockInlineImageSizeForCurrentBuild,
  });

  final bool lockImageAspectRatioForCurrentBuild;
  final bool lockInlineImageSizeForCurrentBuild;
}
```

默认阅读态：

```dart
const ThreadResourceLayoutPolicy(
  lockImageAspectRatioForCurrentBuild: true,
  lockInlineImageSizeForCurrentBuild: true,
);
```

复制页或调试页可以允许更精确但更容易重排的策略。

### 测试重点

- 图片解码成功后不会触发当前图片 block 高度变化。
- 缓存尺寸存在时，首次构建就使用缓存比例。
- 无缓存尺寸时使用 `0.7` fallback，之后只记录尺寸。
- 表情尺寸异步补全不改变当前 RichText 行高。

## Phase 2：资源 layout hint 统一化

### 目标

把图片和表情的尺寸判断从 widget 中抽出来，形成可复用、可测试的领域服务。

### 建议接口

```dart
class ThreadPostResourceLayoutHintResolver {
  const ThreadPostResourceLayoutHintResolver({
    required this.imageCacheLookup,
    required this.smileyCatalogLookup,
    this.defaultImageAspectRatio = 0.7,
    this.defaultInlineImageSize = const Size(24, 24),
  });

  Future<ThreadImageLayoutHint> resolveBlockImage(
    ThreadPostImageBlock image,
  );

  Future<ThreadInlineImageLayoutHint> resolveInlineImage(
    ThreadPostInlineImage image,
  );
}
```

### 实现要求

- 先允许 widget 层同步消费已有 hint。
- 如果 resolver 需要异步查 cache，应在 render plan 构建或页面加载阶段完成，不要在每个图片 widget 进入视口后各自查一遍。
- 需要有 `source` 字段，方便诊断“为什么这个图片用的是 0.7”。

## Phase 3：RenderPlan 缓存与失效策略

### 目标

保证同一页内 rebuild 不重复 parse / normalize / segment，同时 settings 变化时能正确失效。

### 缓存 key

```dart
class ThreadPostBodyRenderPlanCacheKey {
  final String tid;
  final String pid;
  final String messageHash;
  final String renderSettingsSignature;
  final String resourceHintVersion;
}
```

### 失效条件

- 当前页 posts 替换。
- 当前 post message 改变。
- 字号、行高、段距、繁简转换模式改变。
- 资源 hint 版本显式刷新。

### 不应失效的情况

- 图片加载成功。
- 图片尺寸写入缓存。
- 折叠评分/点评/投票。
- 收藏、回复、评分提交状态变化。

## Phase 4：图片阅读器入口预留

### 目标

为后续自制图片阅读器打通数据结构，不在本阶段实现阅读器 UI。

### 建议接口

```dart
class ThreadImageOpenRequest {
  final String tid;
  final String pid;
  final int postNumber;
  final ThreadPostImageGroup group;
  final int initialIndex;
  final String referer;
}
```

点击图片时传递完整 `ThreadPostImageGroup`，阅读器未来可以：

- 从当前图片开始。
- 横向/纵向浏览该楼全部图片。
- 读取缓存路径。
- 触发下载或预取。
- 记录阅读进度。

### 设计边界

- 帖子详情页只负责构造 request。
- 图片阅读器属于 `thread` 或未来共享 reader 模块，不反向依赖帖子详情 widget。

## Phase 5：复制体验完善

### 目标

让 `全部复制` 和 `选择复制` 的文本语义更接近论坛正文。

### 纯文本提取规则

建议完善为：

- 普通文本按 block 顺序拼接。
- quote 前后保留换行，可选添加引用前缀。
- 链接复制显示文本，不复制 URL，除非显示文本为空。
- block 图片默认省略，可配置为插入 `[图片]` 或图片 URL。
- inline 表情优先复制论坛 BBCode，其次 alt/title，最后省略。
- 编辑提示、评分提示等特殊文字保留原文本。

### 接口建议

```dart
class ThreadPostPlainTextExtractOptions {
  final bool includeBlockImagePlaceholder;
  final bool includeBlockImageUrl;
  final ThreadInlineImageTextPolicy inlineImagePolicy;
  final ThreadQuoteTextPolicy quotePolicy;
}
```

## Phase 6：阅读显示设置接入

### 目标

为繁简转换、字号、行高、段距等设置打基础。

### 原则

- 原始 HTML 不变。
- parser 输出不变。
- normalized document 尽量不变。
- 显示设置只影响 render plan 或 span 构建。

### 建议扩展

```dart
class ThreadPostBodyRenderSettings {
  final double? fontSize;
  final double? lineHeight;
  final double? paragraphSpacing;
  final double? blockSpacing;
  final ThreadTextConversionMode conversionMode;
  final String signature;
}
```

繁简转换建议作为 `TextTransformer` 或 display document transformer，而不是直接改 `ThreadPostTextRun.text` 的源数据。

## Phase 7：滚动诊断工具

### 目标

帮助定位“某个固定位置卡顿/回溯”的真实原因。

### 建议诊断数据

```dart
class ThreadDetailScrollDiagnosticEvent {
  final DateTime time;
  final String type;
  final String? entryKey;
  final String? pid;
  final double? scrollOffset;
  final String message;
}
```

事件类型：

- `entry.build`
- `renderPlan.create`
- `image.layoutHint`
- `image.dimensionRecorded`
- `inlineImage.layoutHint`
- `scroll.jumpTo`
- `scroll.animateTo`
- `targetPost.scroll`
- `layout.heightChanged`

### UI 入口

更多页新增开发/诊断开关：

- 帖子详情滚动诊断。
- 显示当前页面诊断事件。
- 一键复制诊断日志。

## Phase 8：温和预热策略

### 目标

在滚动稳定后，再考虑重新引入资源预热，而不是现在就恢复旧预加载队列。

### 策略

- 只预取视口附近 1 到 2 个图片资源。
- 只下载/缓存，不触发当前 widget 布局变化。
- 不解析远处楼层 HTML，因为 render plan 已经负责当前页结构。
- 使用低并发队列，例如 1。

```dart
class ThreadResourceWarmupQueue {
  Future<void> warmupImages({
    required String tid,
    required List<ThreadPostImageEntry> images,
    required int centerIndex,
  });
}
```

## 6. 推荐执行顺序

最推荐的顺序是：

1. Phase 1：锁定图片和表情布局高度。
2. Phase 2：抽出资源 layout hint resolver。
3. Phase 3：稳住 render plan cache 和失效策略。
4. Phase 4：预留图片阅读器 request。
5. Phase 5：完善复制文本语义。
6. Phase 6：接入阅读显示设置。
7. Phase 7：补诊断工具。
8. Phase 8：确认滚动稳定后再做温和预热。

其中 Phase 1 是最高优先级。只要滚动中仍有图片或表情改变布局高度，继续做更多功能都会放大不稳定感。

## 7. Review 清单

每一阶段完成后建议检查：

- 长文本楼上下滑动是否稳定。
- 多图片楼快速上滑是否还会回溯。
- 表情首次加载是否导致楼层高度跳动。
- 点击图片、链接、回复、评分、点评是否正常。
- 长按正文复制动作是否正常。
- 选择复制页是否仍可楼内跨块选择。
- render plan 是否没有因为图片加载、折叠、收藏等状态变化重复生成。

## 8. 明确不做的事

近期不建议做：

- 恢复阅读页全局 `SelectionArea`。
- 让图片解码后立即修正当前布局高度。
- 让表情解码后立即修正当前行高。
- 重启旧的激进预加载队列。
- 把正文重新合并成一楼一个大 Column。
- 为了少量复制便利牺牲主阅读页滚动性能。

## 9. 阶段成功标准

当以下条件满足时，可以认为帖子详情阅读流进入稳定阶段：

- 长文本、多图、多表情帖子在真机上没有明显固定点卡顿。
- 多图帖子上滑不会出现持续回溯导致无法上滑。
- 图片和表情首次加载不会造成明显楼层高度跳变。
- 复制能力可通过独立页面完成，不影响阅读态。
- 图片阅读器可以基于 `ThreadImageOpenRequest` 接入，而不需要重写正文 parser。
- 字号、段距、繁简转换可以通过 `ThreadPostBodyRenderSettings` 接入。
