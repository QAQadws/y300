# 回复功能实现

## 1. 目标与范围

本文档用于在当前项目中实现 Discuz X3.5 论坛“回复帖子”能力，要求：

1. 工程化、可维护、低耦合。
2. 支持普通回复与“回复某楼（引用上下文）”。
3. 支持后续扩展图片/附件上传。
4. 优先尝试 `api/mobile/index.php?module=sendreply&version=4`，失败时可回退到网页表单链路。

不在本期范围：

1. 富文本编辑器（仅支持纯文本/简易 BBCode）。
2. 完整引用渲染 UI（先支持引用参数透传）。
3. 全量反垃圾策略（仅预留扩展点）。

---

## 2. 现状分析（基于你提供的 HTML + 当前项目）

你提供的移动网页回复页（`forum.php?mod=post&action=reply...&mobile=2`）可确认：

1. 提交地址（POST）
- `forum.php?mod=post&action=reply&fid={fid}&tid={tid}&...&replysubmit=yes&mobile=2`

2. 表单关键字段
- `formhash`
- `posttime`
- `fid`、`tid`（在 URL 上）
- `message`
- `replysubmit=yes`
- 可选：`usesig`
- 可选（回复某楼场景）：`reppid`、`reppost`、`noticeauthor`、`noticetrimstr`、`noticeauthormsg`

3. 前端提交方式
- `FormData` POST
- URL 追加 `&inajax=1&handlekey=postform`
- 返回 XML（JS 里读取提示文本）

4. 附件上传（网页链路）
- 图片：`misc.php?mod=swfupload&operation=upload&type=image...`
- 附件：`misc.php?mod=swfupload&operation=upload&fid=...`

当前项目已有可复用能力：

1. 已有登录与 Cookie 持久化网络层。
2. 已有 `formhash` 获取（`profile` 模块、搜索等已使用）。
3. 已有 `ThreadDetail` 页面与状态管理，可接入“发送回复”交互。

## 3. 技术路线（双通道，主备设计）

### 3.1 主通道：Mobile API（推荐）

接口：
- `POST /api/mobile/index.php?module=sendreply&version=4`

理由：

1. 与现有 `api/mobile` 体系一致，JSON 更易解析。
2. 减少 HTML/XML 解析脆弱性。
3. 后续可统一错误码处理与重试策略。

### 3.2 备通道：Web Form 回退（兜底）

接口：
- `POST /forum.php?mod=post&action=reply&fid={fid}&tid={tid}&replysubmit=yes&mobile=2&inajax=1`

理由：

1. 某些站点对 `sendreply` 插件/路由有兼容差异。
2. 当 API 返回结构不稳定时，可快速回退保障可用性。

### 3.3 通道路由策略

建议：

1. 默认走 API。
2. API 失败且属于“能力型失败”时回退 Web：
- module 不存在/权限提示异常/返回非预期结构。
3. API 失败且属于“业务失败”时不回退：
- 未登录、禁言、内容过短、发帖频率限制。

2. `api_client`
- 只负责 `sendreply` 请求与响应映射。

- 只负责网页回复提交与 XML/HTML 结果解析。

4. `repository`
- 负责主备策略、错误归一、埋点日志。

5. `controller`
- 负责 UI 状态（发送中、错误文案、发送成功后清空输入等）。

## 6. 请求协议设计

### 6.1 API 通道：`sendreply`

目标地址：
- `POST /api/mobile/index.php?module=sendreply&version=4`

建议请求头：

1. `content-type: application/x-www-form-urlencoded`
2. `accept: application/json, text/plain, */*`
3. `referer: https://bbs.yamibo.com/forum.php?mod=viewthread&tid={tid}&mobile=2`
4. `x-requested-with: XMLHttpRequest`（可选）
5. Cookie 由现有 `CookieStore` 自动附加

建议 body（最小集）：

1. `formhash`
2. `fid`
3. `tid`
4. `message`
5. `replysubmit=yes`
6. `usesig=1|0`

引用回复可选字段：

1. `reppid`
2. `reppost`
3. `noticeauthor`
4. `noticetrimstr`
5. `noticeauthormsg`

说明：

1. `posttime` 在 Web 表单中出现，API 可能不强制；若返回“非法提交/表单过期”，可追加该字段（通过预检页获取，见 6.3）。

### 6.2 Web 通道：`forum.php?mod=post&action=reply`

目标地址：
- `POST /forum.php?mod=post&action=reply&fid={fid}&tid={tid}&replysubmit=yes&mobile=2&inajax=1&handlekey=postform`

请求体建议：

1. `formhash`
2. `posttime`
3. `message`
4. `replysubmit=yes`
5. `usesig=1|0`
6. 引用相关字段（同上）

响应解析：

1. 优先解析 XML 的提示文本。
2. 兼容纯文本/HTML 提示（站点模板差异）。

### 6.3 预检页（可选但推荐）

当 API 失败提示“参数缺失/非法提交”时：

1. GET `forum.php?mod=post&action=reply&fid={fid}&tid={tid}&mobile=2`
2. 提取隐藏字段：`formhash`、`posttime`、`notice*`、`rep*`
3. 再次调用 API 或 Web 通道

这样可显著降低不同站点模板差异风险。

## 7. 错误处理与重试

### 7.1 错误归一策略

对 API/Web 的原始返回做统一映射：

1. 未登录：提示“请先登录”。
2. 无权限/禁言：提示“当前账号无回复权限”。
3. 内容校验失败：提示“内容为空/过短/包含敏感词”。
4. 频控：提示“发帖过快，请稍后再试”。
5. 网络错误：提示“网络异常，请重试”。

### 7.2 重试策略

1. 不自动重试业务错误。
2. 网络超时可一次幂等重试（仅 message 文本，不含文件上传）。
3. 若首次 API 失败且命中能力型失败，切换 Web 兜底一次。

## 9. 分阶段实施计划

## Phase 1：最小可用回复（文本）

目标：跑通发送回复主链路。

任务：

1. 建立 `ReplyDraft/ReplyResult` 模型。
2. 实现 `DiscuzReplyApiClient`（只做最小字段）。
3. 接入 `ThreadDetail` 的回复输入与发送按钮。
4. 发送成功后刷新帖子。

验收：

1. 已登录账号可回复成功。
2. 错误有可读提示。

## Phase 2：主备通道与预检

目标：提升兼容性与成功率。

任务：

1. 实现 `DiscuzReplyWebClient`。
2. `ReplyRepository` 增加 API->Web 回退策略。
3. 增加预检页提取 `posttime/notice*` 能力。

验收：

1. API 不稳定时 Web 可兜底。
2. “非法提交”类问题明显下降。

## Phase 3：引用回复与楼层回复

目标：支持针对某楼回复。

任务：

1. 在楼层菜单增加“回复此楼”。
2. 透传 `reppid/reppost/notice*`。
3. UI 显示“正在回复 @xxx”。

验收：

1. 服务端显示正确引用关系。

## Phase 4：附件/图片上传

目标：支持图文回复。

任务：

1. 上传服务抽象（图片/附件）。
2. 先走网页 swfupload 链路。
3. 把返回的 `attach` 标记插入正文（`[attach]id[/attach]`）。

验收：

1. 可上传并发送附件。
2. 失败时可清晰回滚与重试。

## 11. 安全与风控

1. 不在日志中打印完整 Cookie / 密码 / auth。
2. 不持久化明文草稿中的敏感信息（可选加密）。
3. 对外暴露错误文案做脱敏（不透出服务端内部细节）。

## 12. 与当前项目集成建议

1. 复用现有 `core/network/api_client.dart` 与 `CookieStore`。
2. 复用 `ProfileRepository.getProfile()` 获取 `formhash`。
3. 回复功能放到独立 `features/reply`，避免污染 `thread` 与 `search` 模块。
4. 在 `thread_detail_controller.dart` 仅依赖 `ReplyRepository` 抽象，不依赖具体 API/Web 实现。

## 13. 已知不确定项与建议验证

`sendreply` 在不同 Discuz 站点可能存在字段差异，建议做一次抓包验证（Charles/mitmproxy）：

1. 官方 App 或移动网页发一次成功回复。
2. 对比请求字段、请求头、返回结构。
3. 记录该站点“必填最小字段集”，写入项目内 `docs/reply_api_contract.md`。

推荐验证优先级：

1. `formhash` 是否必须从 profile 取，还是必须来自回复页。
2. `posttime` 是否为 sendreply 必填。
3. `notice*` 字段在“非引用回复”时是否可省略。
