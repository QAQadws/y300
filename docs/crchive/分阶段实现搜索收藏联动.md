# 分阶段实现搜索收藏联动

## 1. 文档目标与范围

本方案用于把当前项目从“可用的漫画解析与本地书架”升级为“可持续迭代、可备份恢复、可联动搜索与收藏的漫画数据系统”。

覆盖范围：
1. `fid=30` 漫画帖子解析重构（多楼层、可扩展规则、可递归）。
2. 搜索能力接入（Discuz mobile 搜索，含 formhash 流程与结果解析）。
3. 收藏页联动（网页收藏 + 本地缓存 + fid 回填）。
4. 漫画列表与收藏缓存联动刷新。
5. 备份/恢复（含收藏缓存、fid 映射、漫画缓存，预留小说扩展）。

不覆盖范围（本期只预留接口）：
1. 小说版块业务实现。
2. 全论坛功能重构。

---

## 2. 现状与关键问题（基于当前代码）

当前关键实现位置：
1. 解析：`lib/features/comic/domain/services/comic_services_impl.dart`（`HtmlComicParserService`）。
2. 漫画数据仓储：`lib/features/comic/data/local_comic_repository.dart` + `lib/features/comic/data/local/comic_local_db.dart`。
3. 收藏 API：`lib/features/favorites/data/favorite_repository.dart`（`myfavthread`）。
4. 线程详情 API：`lib/features/thread/data/thread_repository.dart`（`viewthread`）。

当前短板：
1. message 解析规则是“单体函数 + 少量正则”，扩展成本高。
2. episode link 只做了基础抽取，缺少“连续链接段、语义标签、规则评分”。
3. 没有“从首楼开始连续楼主楼层合并解析”的通用流程。
4. 缺少“只给上一话链接时的递归回溯”框架。
5. 收藏 thread 无 fid，本地没有“tid->fid 缓存字典”与增量补全策略。
6. 没有统一的搜索服务与限流（你要求“10 秒内最多一次搜索”）。
7. 缺少工程化备份内容定义、版本迁移与恢复校验。

## 3. 总体架构设计（建议落地）

### 3.1 新增模块边界

1. `ComicPostParsingEngine`：负责 message 与多楼层解析编排。
2. `ComicEpisodeDiscoveryService`：负责“当前帖->全话列表”发现策略（直接目录式、递归式、目录页面式）。
3. `DiscuzSearchService`：负责 formhash 获取、搜索提交、重定向结果抓取、HTML 结果解析。
4. `FavoriteSyncService`：负责 myfavthread 拉取、tid->fid 补全缓存、与漫画缓存联动。
5. `BackupService`：负责导出/导入 JSON 快照与版本兼容。

### 3.2 数据层分层

1. `Remote`：HTTP/API/HTML 请求与基础解析。
2. `Domain`：规则执行、候选评分、链路决策。
3. `Local`：SQLite 缓存、状态、增量游标。
4. `Orchestration`：定时刷新、手动更新按钮流程。

## 4. message 解析重构方案（核心）

## 4.1 解析目标对象模型

建议新增以下领域模型（保留现有 `ParsedComicPost`，逐步扩展）：

1. `ParsedPostContext`
- `tid`、`fid`、`subject`、`authorUid`、`isFirst`
- `messageHtml`、`messageText`

2. `ParsedAnchor`
- `rawHref`、`normalizedUrl`、`text`
- `tidCandidate`（可空）
- `linkKind`：`episode` / `catalog` / `external` / `unknown`
- `features`：例如 `containsOrdinal`, `contains特典`, `contains目录`

3. `EpisodeLinkCandidate`
- `tid`
- `titleRaw`
- `titleNormalized`
- `sourceType`：`thread_html` / `viewthread_query`
- `confidence`（0~1）
- `position`（在 message 中的序号）
- `groupId`（连续链接段）

4. `EpisodeExtractionResult`
- `episodes`
- `catalogLinks`
- `nextHopCandidates`（递归候选）
- `debugSignals`（命中规则、拒绝原因）

## 4.2 解析流水线（Pipeline）

阶段 A：HTML 标准化
1. 递归解码 `&amp;`。
2. 统一补全相对链接（基于 `https://bbs.yamibo.com/`）。
3. 移除无关节点（表情、小图标、头像类 img）。

阶段 B：Anchor 抽取与归一化
1. 支持两大主类型：
- 伪静态：`thread-<tid>-1-1.html`
- 动态：`forum.php?mod=viewthread&tid=<tid>`（含多余参数）
2. 兼容异常写法：如 `;tid=537155&...`（前缀残缺）。
3. 输出 `ParsedAnchor` 列表。

阶段 C：语义特征提取
1. 标题文本特征：
- 数字序号：`01`、`1`、`001`
- 话数模式：`第1话`、`第一话`、`第 92 话`
- 特典模式：`特典`、`第一卷特典`、`附录`、`蜜瓜特典`
- 目录模式：`目录`
2. 链接段特征：
- 是否形成“连续短文本链接簇”（如 01~23）。
- 簇内 tid 是否单调（可辅助判断可信度）。

阶段 D：规则引擎决策
1. `CatalogRule`：文本含目录 -> 标记 catalog。
2. `EpisodeStrongRule`：文本匹配话数/特典 + 可提取 tid -> `episode`。
3. `EpisodeClusterRule`：连续簇内锚点即使文本弱，也可提升为 episode。
4. `RejectRule`：非 viewthread/thread 且无 tid -> 排除。

阶段 E：去重与排序
1. 主键：`tid` 去重。
2. 保留策略：优先置信度高、位置靠前。
3. 排序：优先按簇顺序，再按文本序号（可解析时）。

## 4.3 多楼层（连续楼主）解析

规则：
1. 从 1 楼开始。
2. 仅合并“连续且作者为楼主”的楼层。
3. 一旦遇到非楼主楼层，停止继续合并。
4. 每层分别跑 pipeline，最后合并结果并去重。

建议接口：
1. `fetchConsecutiveOpPosts(tid)` -> `List<ThreadPost>`。
2. `parsePosts(List<ThreadPost>)` -> `EpisodeExtractionResult`。

## 5. 章节发现策略（3种方式统一）

## 5.1 Strategy-1：最新话内含全量跳转

判定：
1. 单帖中检测到足够多 episode links（例如 >= N，N 可配置）。
2. 或检测到高置信度连续簇。

动作：
1. 直接输出完整 episodes。
2. 不触发递归，不解析目录。

## 5.2 Strategy-2：仅上一话链接，需递归回溯

判定：
1. 仅检测到少量链接（如 1~2），且 subject 显示当前话数较大。
2. 链接语义命中“上一话/前话/数字递减”。

动作：
1. 从当前 tid 出发，沿“上一话候选 tid”递归抓取。
2. 每跳重复执行多楼层解析。
3. 终止条件：
- 无新 tid。
- 命中已访问集合。
- 达到最大深度（可配，默认 200）。
- 连续 K 次提取失败（可配）。

## 5.3 Strategy-3：目录链接解析（仅在必要时）

判定：
1. Strategy-1/2 失败或结果不足。
2. message 存在目录链接（文本含目录）。

目录 URL：
1. `misc.php?mod=tag&id=21137`
2. `misc.php?mod=tag&id=20452&type=thread&page=1`

动作：
1. 直接请求 HTML（不能加 `mobile=2`）。
2. 从 HTML 抽取所有 `thread-xxx-1-1.html`。
3. 去重 tid。
4. 支持翻页：识别下一页并遍历（限制最大页数，防止无限抓取）。

注意：
1. 当 Strategy-1 成功时，目录解析默认跳过。
2. 目录解析结果置信度较低，建议标记 `source=tag_catalog`。

## 6. 搜索功能工程化方案

## 6.1 搜索流程（Discuz mobile）

标准流程：
1. GET `search.php?mod=forum&mobile=2`，提取 `formhash`。
2. POST `search.php?mod=forum&searchsubmit=yes&mobile=2`，body 带 `srchtxt` + `formhash`。
3. 跟随 302 到 `searchid` 页面，抓取结果 HTML。
4. 解析 `.list` 项，提取 `tid`、标题、fid、作者、时间、热度信息。

## 6.2 限流策略（你要求：10 秒内最多一次）

建议实现 `SearchRateLimiter`：
1. 全局桶：每 10 秒 1 次。
2. 若命中限流：
- 返回剩余等待时间。
- UI 提示“请 X 秒后重试”。
3. 本地持久化最近搜索时间（防 App 重启绕过）。

## 6.3 结果匹配策略

用于“漫画详情页更新按钮”：
1. 关键词：优先用 `normalizedTitle`，备选 `原题/别名`。
2. 过滤：`fid==30`。
3. 排序打分：
- 标题相似度（主权重）。
- 是否含组名、作者名。
- 发布时间新近性。
- 回复/浏览热度（次权重）。
4. 取 Top-K（建议 K=3）进入 message 解析验证。

## 7. 收藏联动方案

## 7.1 新增本地缓存表（建议 DB v5）

在 `comic_local_db.dart` 升级版本并新增：

1. `favorite_threads_cache`
- `tid` TEXT PK
- `favid` TEXT
- `title` TEXT
- `author` TEXT
- `replies` INTEGER
- `url` TEXT
- `dateline` INTEGER
- `source_fid` TEXT NULL
- `fid_resolved_at` INTEGER NULL
- `updated_at` INTEGER NOT NULL

2. `favorite_sync_state`
- `id` INTEGER PK (固定 1)
- `last_synced_page` INTEGER
- `last_synced_at` INTEGER
- `etag_or_cursor` TEXT NULL

3. `search_state`
- `key` TEXT PK
- `value` TEXT
- 用于保存 `last_search_at`。

索引建议：
1. `idx_favorite_threads_cache_fid(source_fid)`
2. `idx_favorite_threads_cache_updated(updated_at DESC)`

## 7.2 fid 补全策略

问题：`myfavthread` 无 fid。

方案：
1. 收藏列表拉取后，先写入缓存（`source_fid` 可能为空）。
2. 对 `source_fid is null` 的 tid 做“按需补全”：
- 打开 `viewthread` API 获取帖子详情。
- 从变量中取 fid（需在 thread model 中补字段）。
3. 批量控制：每次同步最多补全 N 条（建议 20），避免重负载。
4. 补全成功后写入 `source_fid` 和时间戳。

## 7.3 收藏->漫画联动

1. 当收藏同步完成：
- 扫描 `source_fid==30` 的收藏。
2. 对漫画缓存中不存在的 tid：
- 自动加入漫画缓存（轻量记录）。
- 触发后台章节解析任务（可延迟执行）。
3. 对已存在漫画：
- 仅更新元信息与更新时间。

## 8. 漫画更新按钮联动流程

触发点：漫画详情页“更新”按钮。

流程：
1. 先执行本地规则解析（当前 tid 的连续楼主楼层）。
2. 若章节不足或可疑：
- 走搜索（受 10 秒限流）。
- 匹配 `fid=30` 的高分结果。
- 取 Top-K 逐个解析，择优结果。
3. 仍不足时：
- 尝试目录链接解析（若存在）。
4. 合并结果写入 `mergeEpisodesFromLinks`。
5. 记录 `refresh_log`（建议新增）便于问题追踪。

建议新增 `refresh_log` 字段：
1. `comic_id`
2. `strategy_used`（direct/recursive/catalog/search_fallback）
3. `inserted_count`
4. `updated_count`
5. `error_message`
6. `created_at`

## 9. 备份与恢复设计

## 9.1 备份内容（必须）

1. 漫画核心数据：`comics`、`episodes`、`episode_images`、`reading_progress`。
2. 收藏缓存：`favorite_threads_cache`、`favorite_sync_state`。
3. 搜索状态：`search_state`（限流时间戳等）。
4. 分类与书架：`categories`、`shelf_items`、`settings`。

## 9.2 备份格式建议

JSON 包结构：
1. `schemaVersion`：如 `backup_v1`。
2. `exportedAt`。
3. `tables`：按表名存数组。
4. `meta`：应用版本、平台、用户 uid（如可取）。

## 9.3 恢复策略

1. 先校验 `schemaVersion`。
2. 分阶段恢复：
- 基础表（categories/settings/comics）
- 关联表（episodes/images/shelf）
- 扩展缓存表（favorites/search_state）
3. 冲突策略：
- 主键冲突默认“以备份覆盖”。
- 可选“仅填补缺失”。
4. 恢复后执行一致性检查：
- 无孤儿 episode。
- 无无效 shelf 引用。

## 9.4 向前兼容

1. 每次 DB 升级同步升级 `BackupCodec`。
2. 保留“旧版本字段映射器”。
3. 对未知字段忽略，对缺失字段给默认值。

目标：把单体解析升级为可插拔规则流水线。

任务：
1. 新建 `comic_post_parsing_engine.dart`。
2. 拆分 rule 类：`CatalogRule`、`EpisodeStrongRule`、`EpisodeClusterRule`、`RejectRule`。

验收：
1. 能稳定识别 `thread` + `viewthread` + 异常 href。
2. 对“01~23 + 特典”场景完整输出。
3. 解析模块新增样例测试通过（由你本地执行）。

## Phase 2：递归回溯与目录解析（3~4 天）

目标：覆盖三种章节发现方式。

任务：
1. 实现 `ComicEpisodeDiscoveryService`，含 direct/recursive/catalog 三策略。

## Phase 3：搜索服务与限流（2~3 天）

目标：为“更新按钮智能补全”提供搜索后备路径。

任务：

3. 实现搜索结果评分与 Top-K 验证。

验收：
1. 能稳定拿到 `tid/fid/title` 搜索列表。
2. 10 秒内重复触发会被拦截并提示剩余秒数。

## Phase 4：收藏缓存与 fid 补全（3~4 天）

目标：让收藏成为漫画列表可信输入源。

任务：
1. DB 升级到 v5，新增收藏缓存相关表。

验收：
1. 收藏同步后本地能保存并复用 fid。
2. 二次同步时只补全未缓存项。

## Phase 5：备份恢复（2~3 天）

目标：保障迭代与用户迁移安全。

任务：

验收：

## 12. 风险与对策

风险 1：Discuz 页面结构变化导致 HTML 选择器失效。
1. 对策：解析器使用“多 selector + 正则兜底”。
2. 对策：保留原始 HTML 片段日志（截断存储）。

风险 2：递归回溯过深导致请求风暴。
1. 对策：深度限制 + 访问集 + 连续失败熔断。

风险 3：收藏 fid 补全成本高。
1. 对策：增量补全 + 后台分批 + 持久化缓存。

风险 4：搜索限流影响体验。
1. 对策：UI 显示剩余冷却秒数，允许使用本地缓存刷新。

风险 5：备份字段迭代导致恢复失败。
1. 对策：版本化 codec + 宽松反序列化 + 迁移测试样本。

4. 目录解析复杂且脆弱，放后面更稳。
