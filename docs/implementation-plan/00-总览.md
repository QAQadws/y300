# 收藏/漫画/小说模块优化 — 实施方案总览

## 当前架构

```
┌─────────────────────────────────────────────────────────────┐
│  UI 层                                                       │
│  FavoriteShelfPage → UnifiedShelfPage                        │
│  ComicShelfPage / NovelShelfPage                             │
├─────────────────────────────────────────────────────────────┤
│  适配器层                                                     │
│  FavoriteShelfAdapter ─── ComicShelfAdapter ─── NovelShelfAdapter │
├─────────────────────────────────────────────────────────────┤
│  同步/摄入层                                                  │
│  FavoriteSyncService                                         │
│    ├─ 拉取收藏列表 (myfavthread API)                          │
│    ├─ 逐条加载帖子详情 (thread detail)                         │
│    ├─ 分类: comic/novel/forum                                │
│    ├─ 漫画摄入: ComicFavoriteIngestService                    │
│    └─ 小说摄入: NovelFavoriteIngestService                    │
├─────────────────────────────────────────────────────────────┤
│  仓储层                                                       │
│  LocalFavoriteRepository ─── ComicRepository ─── NovelRepository │
├─────────────────────────────────────────────────────────────┤
│  数据库 (SQLite: comic_shelf.db)                              │
│  favorite_threads / comics / works / episodes / ...          │
└─────────────────────────────────────────────────────────────┘
```

## 问题与方案映射

| # | 问题 | 阶段 | 预计总时间 |
|---|------|------|-----------|
| 1 | 收藏解析优化：快速概览 + 渐进式深入 | 阶段 1 | 8–10h |
| 2 | 漫画搜索队列："長篇連載"延迟补全 | 阶段 2 | 6–8h |
| 3 | 论坛收藏 API | 阶段 3 | 3–4h |
| 4 | 实时刷新机制（事件总线） | 阶段 4 | 5–7h |
| 5 | 漫画重复检测与合并 | 阶段 5 | 8–10h |

**合计预估：30–39 小时**

## 解耦设计原则

1. **事件总线独立于业务模块**：`lib/core/events/` 下新建，不依赖任何 feature
2. **队列持久化与队列逻辑分离**：队列数据结构与 SQLite 仓储分开
3. **摄入管道可插拔**：每个阶段作为独立 pipeline stage，可按配置启用/禁用
4. **进度报告统一接口**：所有长任务走 `LibraryShelfTaskProgress` 或其扩展

## 实施顺序

```
阶段 1（解析优化）──→ 阶段 2（搜索队列）──→ 阶段 3（收藏 API）
         │                    │                    │
         └────────────────────┴────────────────────┘
                              │
              阶段 4（事件总线）──→ 阶段 5（去重合并）
```

- 阶段 1 和 2 有依赖关系（2 依赖 1 的管道设计）
- 阶段 3 可以独立实施
- 阶段 4 在 1、2、3 完成后实施效果最佳
- 阶段 5 依赖 1 的解析管道和 4 的事件系统
