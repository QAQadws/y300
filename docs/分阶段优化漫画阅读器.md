# 分阶段优化漫画阅读器

## 1. 背景与目标

这份文档用于规划 Y300 漫画阅读器的系统性优化。目标不是只把阅读页做得“能翻页”，而是把漫画阅读体验、详情页状态、书架状态、更新策略、缓存策略和作品元数据编辑打通，形成一个可维护、可验证、后续能继续扩展的阅读系统。

本方案基于以下代码阅读：

- 当前项目漫画阅读器：`lib/features/comic/presentation/comic_reader_page.dart`、`lib/features/comic/presentation/controllers/comic_reader_controller.dart`、`lib/features/comic/presentation/widgets/reader_top_bar.dart`、`lib/features/comic/presentation/widgets/reader_bottom_panel.dart`、`lib/features/comic/presentation/widgets/reader_progress_bar.dart`、`lib/features/comic/presentation/widgets/reader_tap_zones.dart`、`lib/features/comic/presentation/widgets/reader_zoomable_image.dart`、`lib/features/comic/presentation/models/reader_preferences.dart`、`lib/features/comic/presentation/providers/reader_preferences_provider.dart`
- 当前项目详情/书架联动：`lib/features/library_shared/presentation/pages/unified_detail_page.dart`、`lib/features/library_shared/presentation/controllers/unified_detail_controller.dart`、`lib/features/library_shared/presentation/pages/unified_shelf_page.dart`、`lib/features/library_shared/presentation/controllers/unified_shelf_controller.dart`、`lib/features/comic/presentation/adapters/comic_detail_adapter.dart`、`lib/features/comic/presentation/adapters/comic_shelf_adapter.dart`

最终目标：

- 阅读器只在用户真正读到本章最后一页时自动标记章节已读，详情页章节行才变淡，书架未读数才减少。
- 详情页、书架页、阅读器之间共享同一套作品状态和章节状态，不出现“点开就已读”“读完未读数不变”“详情页变淡但书架角标不变”的割裂。
- 点击屏幕中部出现的上下菜单更现代、更紧凑、更可操作，具备阅读模式、进度、章节切换、亮度/滤镜、缩放/裁边、缓存、书签等常用入口。
- 阅读器具备可控的图片预加载、章节预加载、失败重试、缓存状态回写、内存边界和性能观测。
- 作品支持用户自定义封面、标题、作者、汉化组；自定义封面应优先从阅读器当前页图片设置，并缓存图片本体到受保护封面缓存，而不是把 URL 当作封面本身；自定义标题要参与后续“搜索兜底更新章节”的关键词策略，避免解析标题不准确导致更新失败。
- 书架卡片左上角稳定显示未读章节数，未读数来自聚合快照，不依赖 UI 临时计算。
- 架构边界清晰：阅读器负责阅读行为和进度事件，仓储负责持久化，统一详情/书架只消费状态，更新服务负责远程发现与合并章节。

## 2. 当前实现诊断

### 2.1 已经具备的基础能力

当前漫画阅读器已经有不少可继续利用的基础：

- `ComicReaderPage` 支持垂直滚动、LTR 翻页、RTL 翻页。
- `ReaderTapZones` 已经具备左/中/右三区点击模型，中部用于切换菜单，左右用于翻页模式切页。
- `ReaderTopBar` 和 `ReaderBottomPanel` 已经实现上下滑入菜单。
- `ReaderProgressBar` 已经支持页码显示、Slider 跳页、上一话/下一话按钮。
- `ReaderZoomableImage` 支持双击缩放、手势缩放、缩放状态回调，并且阅读页会在缩放时禁用页级点击/翻页干扰。
- `ComicReaderController` 已经持久化 `reading_progress`，包含 `episodeId`、`imageIndex`、`scrollOffset`。
- `ComicReaderController` 已经有首批图片预热 `_preloadFirstBatch` 和跳页后的 `_prefetchAroundIndex`。
- 图片缓存已经有 `ImageCacheService`、`cachedImagesTable`、`episode_images.stable_cache_key/local_path/cache_status` 等基础字段。
- 书架统一页已经在卡片左上角支持 `topLeftBadge`，并且 `_UnreadBadge` 已存在。
- `ComicShelfAdapter.querySnapshot` 已经用 SQL 聚合了 `unread_count`、`read_count`、`downloaded_count`、`total_count`。
- 自定义封面字段已存在：`custom_cover_image_url`、`custom_cover_local_path`，并已经接入详情页和书架封面优先级。后续要进一步明确：真正展示和缓存的自定义封面应是本地图片文件，`custom_cover_image_url` 只能作为来源追踪或远程导入兜底，不能成为主要实现路径。

这些基础很好，后续优化应当在现有结构上推进，不建议推倒重来。

### 2.2 当前最重要的问题

#### 问题 1：详情页点击章节时提前标记已读

`UnifiedDetailPage` 的章节 `ListTile.onTap` 当前会先执行：

```dart
await _controller.markChapterRead(
  episodeId: chapter.episodeId,
  isRead: true,
);
await widget.onOpenReader(context, target);
```

这会导致用户只是点开章节，还没有读到最后一页，详情页章节已经变淡，书架未读数也可能减少。这与成熟漫画阅读器的行为不一致。Mihon 的做法是在 `ReaderViewModel.updateChapterProgress` 中每次页变更时保存 `last_page_read`，只有 `pageIndex == lastIndex` 时才调用完成逻辑并设置 `read = true`。Mangayomi 也是在 `ReaderController.setPageIndex` 中根据接近章节末尾的页码判断是否已读，而不是进入阅读器时立刻已读。

因此，Y300 后续应把“自动已读”的唯一来源收敛到阅读器内的“读到最后一页事件”。

#### 问题 2：阅读进度和统一章节状态分离

当前 `reading_progress` 记录了最后阅读到哪一页，但 `library_episode_state.is_read` 由统一详情页或适配器写入。阅读器只更新 `reading_progress`，没有在读完最后一页时写 `library_episode_state`。

结果是：

- 阅读器知道用户读到了哪里。
- 详情页/书架知道章节是否已读。
- 但两者之间没有稳定的事件桥。

应增加一个明确接口，例如 `ComicReaderProgressSink` 或直接扩展 `ComicRepository/LibraryStateRepository` 协作，让阅读器在最后一页时写入统一章节状态和作品状态。

#### 问题 3：预加载策略还比较粗糙

当前有两个预热入口：

- `_preloadFirstBatch(images)`：打开章节后缓存前 3 张。
- `_prefetchAroundIndex(centerIndex)`：跳页后缓存目标附近半径 2 张。

问题：

- 垂直滚动中 `_onVerticalScroll` 只保存进度，没有持续根据方向预加载后续页。
- `_prefetchAroundIndex` 并发 `Future.wait`，没有优先级、取消、队列或并发上限。
- 没有“当前页最高优先级、后续页次优先级、前序页低优先级”的任务模型。
- 没有“靠近章节末尾时预取下一章图片列表/首图”的章节级预加载。
- 没有根据网络/内存/下载状态动态调整预加载窗口。

Mihon 的 `HttpPageLoader` 使用 `PriorityBlockingQueue`，当前页 `DEFAULT/RETRY` 优先，邻近页 `ADJACENT` 低优先，并且 `preloadSize = 4`。Mangayomi 则在阅读器初始化时 `_prefetchPagesInOrder`，按阅读顺序 `precacheImage`，同时在距离章节末尾小于 `pagePreloadAmount` 时触发下一章预加载，并通过 `ChapterPreloadManager` 管理已加载章节集合。

Y300 可以借鉴两者：先做轻量任务队列，再做章节级预加载。

#### 问题 4：阅读器菜单功能偏基础

当前顶部菜单只有返回、缓存本话、缓存全部未读；底部菜单只有进度条、上一话/下一话、阅读模式切换。

对漫画阅读器来说，常用能力还缺：

- 当前作品标题 + 当前章节标题的双行展示，点击标题回详情页。
- 章节列表入口。
- 书签/取消书签当前章节。
- 标记本章已读/未读。
- 图片加载失败列表或一键重试。
- 阅读模式更多选项：垂直连续、横向连续、单页、双页、LTR/RTL。
- 显示设置：背景色、页间距、适应宽度/高度/屏幕、裁边、亮度、灰度/反色/色彩滤镜。
- 页码浮层开关。
- 自动滚动或音量键/键盘翻页等可选项。

不需要一次全部做完，但菜单结构应该提前设计成可扩展。

#### 问题 5：作品自定义元数据不完整

当前支持自定义封面相关字段，但实现方向需要收敛：用户最自然的封面自定义不是手动输入 URL，而是在阅读漫画时把当前页设置为封面。也就是说，封面缓存应保存图片本体，详情页和书架读取的是受保护的本地封面文件。标题、作者、汉化组还没有等价的用户覆盖字段。`comics.title/author/translation_group` 存储的是解析结果或初始结果，没有分离：

- 来源解析值
- 用户自定义值
- 用于搜索/更新的规范标题

用户指出的问题很关键：有时解析标题得到的标题并不是真正的标题，导致“搜索”作为更新兜底时不一定成功。当前 `NetworkComicEpisodeRefreshService._searchFallbackFromCurrentTid` 会重新抓当前帖 subject，并用 `_subjectParser.parse(thread.subject).normalizedTitle` 作为搜索关键词。这意味着即使用户在详情页知道正确标题，更新服务也无法利用。

后续应建立“自定义标题优先”的更新关键词策略。

#### 问题 6：未读数统计依赖状态表完整性

`ComicShelfAdapter.querySnapshot` 已经能聚合 `library_episode_state` 的 `unread_count`。但如果新增章节没有在 `library_episode_state` 中初始化一行，那么统计会出现偏差：章节表有章节，状态表没有状态，默认未读语义无法完整表达。

成熟实现一般会把章节状态作为章节列表查询的一部分：没有状态时视为未读，或者在章节合并后补齐状态行。Y300 当前 `querySnapshot` 的 `episode_stats` 只统计状态表，对无状态章节无法自然计入未读。

这会影响左上角未读数、筛选、排序和“缓存全部未读”。

## 3. 参考项目可借鉴结论

### 3.1 Mihon 的关键经验

Mihon 的阅读器设计有几个非常值得迁移的原则：

- 阅读进度由 reader 内页变更事件驱动，`last_page_read` 每页更新，只有最后一页才 `read = true`。
- `ReaderChapter` 有引用计数，章节不再显示时 `unref()` 并 `pageLoader.recycle()`，避免预加载无限占用资源。
- `HttpPageLoader` 用优先级队列加载图片，当前页/重试优先，邻近预加载低优先。
- 页列表会缓存，避免重复打开章节时重新解析所有 page list。
- reader 持有 `ViewerChapters(curr, prev, next)`，相邻章节是阅读器状态的一部分，预加载和章节切换自然围绕这个模型。
- 详情页章节列表的已读视觉只是状态结果，不负责进入 reader 时自动改状态。
- 书架 `LibraryItem` 明确带 `unreadCount`，排序/筛选/角标都围绕聚合状态实现。

Y300 不需要照搬 Kotlin/Android 架构，但应迁移这些行为边界。

### 3.2 Mangayomi 的关键经验

Mangayomi 对 Flutter 阅读器更直接可参考：

- 使用 `ChapterPreloadManager` 管理已加载章节、预加载中标记、章节转场页、章节 page list 合并。
- 在阅读器初始化时先按阅读顺序预取图片，让前面的页优先进入 Flutter ImageCache，避免后面的图片先出现。
- 靠近章节末尾时触发下一章预加载，末章则追加“最后一章”转场页。
- 底部菜单把进度、章节切换、阅读模式、裁边、双页、设置入口放在同一区域。
- 隐藏菜单时仍可显示底部页码浮层。
- 读页逻辑会考虑连续模式、双页模式、RTL、跳页时的 index 转换。

Y300 当前 Flutter 结构已经接近可迁移状态，尤其是 `ComicReaderPage` 的上下菜单和 `ReaderZoomableImage` 可以继续扩展。

## 4. 总体架构建议

建议把漫画阅读器拆成四条稳定链路：

### 4.1 Reader Session 链路

职责：加载当前章节、恢复进度、响应翻页/滚动/跳页、触发预加载、发出阅读进度事件。

建议新增或重构为：

- `ComicReaderSessionState`
- `ComicReaderPageState`
- `ComicReaderChapterState`
- `ComicReaderPreloadController`
- `ComicReaderProgressPolicy`

现有 `ComicReaderController` 可以逐步演进，不必一次改名。

### 4.2 Library State 链路

职责：统一维护作品和章节状态。

关键表：

- `library_work_state`
- `library_episode_state`
- `reading_progress`

建议规则：

- `reading_progress` 保存“最后读到哪里”。
- `library_episode_state.is_read` 保存“章节是否读完”。
- `library_work_state.last_read_episode_id/last_read_at` 保存作品级继续阅读入口和排序依据。
- 自动已读只能由阅读器读到最后一页触发。
- 手动已读/未读由详情页或批量操作触发。

### 4.3 Reader Cache 链路

职责：图片 URL 列表、图片文件缓存、预加载队列、失败重试、缓存状态回写。

建议将缓存分为：

- 页列表缓存：`episode_images`
- 页面图片缓存：`cached_images` + `episode_images.local_path/cache_status`
- 手动下载：`cache_status = downloaded` 或下载服务维护的本地路径
- 临时预加载：`cache_status = done`，可被清理

### 4.4 Metadata 链路

职责：来源元数据和用户自定义元数据分离，并为搜索兜底更新提供关键词。

建议字段分层：

- source title：来源解析标题
- display title：最终展示标题，用户自定义优先
- search title：更新搜索关键词，用户自定义优先，其次规范化标题，其次来源 subject
- author/translation group 同理区分 source 与 custom

## 6. Phase 0：基线、测试夹具与事件定义

### 目标

先明确“什么行为算正确”，避免后面优化时改出新的状态错乱。

### 实施范围

涉及文件：

- `lib/features/comic/presentation/controllers/comic_reader_controller.dart`
- `lib/features/comic/presentation/comic_reader_page.dart`
- `lib/features/library_shared/presentation/pages/unified_detail_page.dart`
- `lib/features/comic/presentation/adapters/comic_detail_adapter.dart`
- `lib/features/comic/data/local_comic_repository.dart`
- `lib/features/library_shared/data/local_library_state_repository.dart`

### 任务

1. 梳理当前阅读状态：
   - 当前章节 ID
   - 当前图片 index
   - 当前 scroll offset
   - 总页数
   - 是否到达最后一页
   - 是否已写入 `library_episode_state.is_read`
   - 作品 `lastReadEpisodeId/lastReadAt`

2. 为阅读事件定义统一语义：
   - `onPageVisible(index, source)`：页可见，保存进度。
   - `onPageSettled(index, source)`：翻页动画或跳页落定。
   - `onChapterCompleted(episodeId)`：最后一页完成阅读，自动已读。
   - `onManualMarkRead(episodeId, isRead)`：详情页手动操作。
   - `onExitReader()`：退出阅读器时确保进度落盘。

3. 建立测试数据：
   - 作品 A：3 章，每章 5 页。
   - 作品 B：1 章，1 页。
   - 作品 C：章节存在但没有 `library_episode_state` 行。
   - 作品 D：有阅读进度但未读完。

4. 加入基础日志：
   - 打开章节耗时。
   - 首图可见耗时。
   - 每次自动已读触发的 episodeId/pageIndex/total。
   - 预加载成功/失败数量。

### 验收标准

- 能明确复现当前“点击章节即已读”的问题。
- 能打印阅读器打开、页变化、读完、退出四类关键事件。
- 测试数据能覆盖单页章节、多页章节、未初始化状态章节。

### 预期时间

0.5-1 天。

## 7. Phase 1：最后一页才自动标记已读

### 目标

修复最关键行为：用户只有读到本章最后一页时，章节才自动标记为已读，详情页才变淡，书架未读角标才减少。

### 当前问题位置

`UnifiedDetailPage` 当前在章节点击时提前标记已读。应删除这个自动行为，保留长按菜单里的手动标记已读。

### 设计原则

- 详情页点击章节只负责打开 reader。
- 阅读器每次页变化保存阅读进度。
- 阅读器发现当前 index 到达最后一页时，调用统一章节状态写入。
- 自动已读只触发一次，避免重复写库。
- 如果用户手动标记未读，再打开 reader 读到最后一页仍可自动改回已读。

### 实施步骤

1. 修改 `UnifiedDetailPage` 章节点击逻辑：
   - 删除进入 reader 前的 `markChapterRead(isRead: true)`。
   - 打开 reader 后根据返回结果决定是否刷新详情页。
   - 建议 reader `Navigator.pop` 返回 `ComicReaderExitResult`，例如 `{completedEpisodeIds, lastReadEpisodeId}`。

2. 扩展 `ComicReaderController`：
   - 注入 `LibraryStateRepository`，或通过一个漫画域服务封装。
   - 新增方法 `markEpisodeCompletedIfNeeded(index)`。
   - 在 `jumpToImageIndex`、`onScrollProgress`、`_onPageChanged` 后统一检查。
   - 最后一页判断使用 `index >= images.length - 1`。

3. 写入状态：
   - `library_episode_state.is_read = true`
   - `library_episode_state.read_at = now`
   - `library_work_state.last_read_episode_id = episodeId`
   - `library_work_state.last_read_at = now`
   - `reading_progress.image_index = lastIndex`

4. 防重：
   - `ComicReaderViewState` 增加 `isCurrentEpisodeRead` 或 controller 内部维护 `_completedEpisodeIds`。
   - 如果状态已读，不重复写。

5. 单页章节特殊处理：
   - 单页章节打开后，只有当首图实际进入可见/页变更事件发生时才标记已读。
   - 不在 `_loadState` 里直接标记已读。

### 建议接口

```dart
abstract class ComicReadingStateWriter {
  Future<void> saveProgress({
    required String comicId,
    required String episodeId,
    required int imageIndex,
    required double scrollOffset,
  });

  Future<void> markEpisodeCompleted({
    required String comicId,
    required String episodeId,
    required DateTime completedAt,
  });
}
```

短期可直接在 `ComicReaderController` 中调用 `ComicRepository.updateLastReadProgress` 和 `LibraryStateRepository.upsertEpisodeState/upsertWorkState`。中期再提取 writer。

### 验收标准

- 从详情页点击未读章节，进入 reader 后详情页列表不立刻变淡。
- 阅读到最后一页后退出，详情页对应章节变淡。
- 阅读到最后一页后退出，书架卡片左上角未读数减少 1。
- 只读到倒数第二页退出，详情页不变淡，书架未读数不减少。
- 单页章节打开并显示后可以自动标记已读，但不能在页面加载失败时标记已读。
- 手动标记已读/未读仍然可用，不受自动逻辑影响。

### 风险

- 垂直滚动当前通过滚动比例估算 index，可能没有精确判断“最后一张真正可见”。Phase 1 可以先保守使用比例估算，Phase 4/5 再引入更精确的可见页计算。
- 如果图片加载失败但 index 到达最后一页，可能误标已读。应在 `ComicReaderImageState.failed == false` 或图片组件加载成功回调后再允许完成。短期可先在失败页不触发自动完成。

### 预期时间

1-1.5 天。

## 8. Phase 2：详情页和书架未读状态统一

### 目标

保证详情页章节状态、书架未读数、筛选排序都使用同一套状态语义。

### 当前问题

`ComicShelfAdapter.querySnapshot` 的 `unread_count` 依赖 `library_episode_state`。如果章节没有状态行，就不会计入未读。实际语义应该是：章节存在且没有显式已读状态时，应视为未读。

### 推荐 SQL 语义

当前：

```sql
SUM(CASE WHEN is_read = 0 THEN 1 ELSE 0 END) AS unread_count
```

建议改为从 `episodes` 左联 `library_episode_state`：

```sql
WITH chapter_stats AS (
  SELECT
    e.comic_id AS work_id,
    COUNT(*) AS total_count,
    SUM(CASE WHEN COALESCE(s.is_read, 0) = 0 THEN 1 ELSE 0 END) AS unread_count,
    SUM(CASE WHEN COALESCE(s.is_read, 0) = 1 THEN 1 ELSE 0 END) AS read_count,
    SUM(CASE WHEN COALESCE(s.is_downloaded, 0) = 1 THEN 1 ELSE 0 END) AS downloaded_count
  FROM episodes e
  LEFT JOIN library_episode_state s
    ON s.content_type = 'comic'
   AND s.episode_id = e.episode_id
  GROUP BY e.comic_id
)
```

这样无需预先为每章插入状态行，也能正确得到未读数。

### 实施步骤

1. 修改 `LocalComicRepository.queryShelfSnapshot`：
   - 以 `episodes` 为主表统计总数、未读数、已读数、下载数。
   - `library_episode_state` 只作为覆盖状态。
   - 过滤 unread/read/downloaded/bookmarked 时同样考虑 `COALESCE`。

2. 修改 `ComicDetailAdapter.loadChapters`：
   - 没有 `LibraryEpisodeState` 时 `isRead = false`。
   - 这已经基本符合，但需要确认筛选/排序和总数一致。

3. 修改 `LocalLibraryStateRepository.countUnreadEpisodes`：
   - 当前方法只能统计状态表，后续可以不再用于漫画聚合快照。
   - 如果仍保留给 fallback `_mapWork` 使用，建议为漫画模块增加 repository 专用聚合，避免状态表缺行导致 0。

4. 让阅读器完成章节后刷新上游：
   - reader pop 返回后，详情页调用 `_controller.reload()`。
   - 书架页在从详情页返回后触发 `_controller.refresh()` 或使用状态变更通知。

5. 增加“继续阅读”目标修正：
   - 当前 `ComicDetailAdapter.getReaderRouteTarget(preferContinue: true)` 使用 `episodes.last`，这不一定是 last read。
   - 应优先读 `library_work_state.last_read_episode_id` 或 `reading_progress.episode_id`。
   - 没有进度时才选择第一章或最新未读章节。

### 验收标准

- 没有状态行的新章节在书架未读角标中被计入。
- 手动标记已读后，未读角标减少。
- 手动取消已读后，未读角标增加。
- 阅读器读完最后一页后，详情页和书架状态一致。
- “继续”按钮优先打开上次阅读章节和页码，而不是简单打开 `episodes.last`。
- 未读筛选能正确显示没有状态行的新章节。

### 预期时间

1.5-2.5 天。

## 9. Phase 3：上下菜单和阅读交互优化

### 目标

把点击中部滑出的上下菜单升级为现代漫画阅读器的核心控制面板，同时保持简洁、不遮挡阅读。

### 菜单结构建议

- 中间：双行标题。
  - 第一行作品标题。
  - 第二行章节标题。

- 右侧：
  - 书签/取消书签当前章节。
  - 打开原帖。
  - 更多菜单。

更多菜单：

- 将当前页设为封面。

- 缓存未读章节。
- 清除本章缓存。
- 重试失败图片。

- 阅读模式：垂直连续、单页 LTR、单页 RTL，后续双页/横向连续。
- 页面适配：适应宽度、适应高度、适应屏幕、原始大小。
- 背景色：黑、白、灰、跟随主题。
- 页间距。
- 页码浮层开关。
- 裁边开关。
- 亮度/灰度/反色/色彩滤镜后续阶段加入。

   - 当菜单隐藏且偏好开启时显示。

5. 增加当前页封面动作：
   - `ComicReaderViewState` 暴露当前页 `imageUrl/effectiveLocalPath/cacheKey/imageIndex`。
   - 中部点击打开上下菜单后，`ReaderTopBar` 更多菜单或底部图片操作区提供“将当前页设为封面”。

### 预期时间

## 10. Phase 4：图片预加载队列和缓存策略

### 目标

建立可控、可取消、有优先级、有并发上限的图片预加载管线，提升阅读流畅度，避免无序并发造成前面图片没加载、后面图片先加载。

### 推荐策略

借鉴 Mihon：

- 当前页：最高优先级。
- 当前页重试：最高优先级且 force。
- 后续 3-5 页：中优先级。
- 前序 1-2 页：低优先级。
- 跳页目标附近：高优先级。
- 下一章前 1-3 页：低优先级。

借鉴 Mangayomi：

- 打开章节时按阅读顺序预热。
- 靠近章节末尾时预取下一章。
- 预加载任务应能被 dispose 取消。

### 建议新增模型

```dart
enum ComicReaderPreloadPriority {
  retry,
  visible,
  jumpTarget,
  adjacentForward,
  adjacentBackward,
  nextChapter,
}

class ComicReaderPreloadTask {
  const ComicReaderPreloadTask({
    required this.episodeId,
    required this.imageUrl,
    required this.imageIndex,
    required this.cacheKey,
    required this.priority,
  });
}
```

### 建议新增服务

`ComicReaderPreloadQueue`

职责：

- 维护优先级队列。
- 去重：同一个 `episodeId + imageIndex` 不重复入队。
- 并发上限：默认 2，Wi-Fi 可 3，低端设备或移动网络可 1。
- 支持取消：reader dispose、切换章节、跳页后取消旧窗口外任务。
- 成功后回写 `episode_images.local_path/cache_status/last_accessed_at/bytes`。
- 失败后标记失败但不打断阅读。

### 改造 `ComicReaderController`

1. 打开章节：
   - 立即入队当前页、当前页后 4 页。
   - 如果是垂直模式，从恢复位置对应 index 开始。

2. 页变化：
   - 根据阅读方向入队后续窗口。
   - 方向可通过新旧 index 比较推断。

3. Slider 跳页：
   - 取消旧窗口低优先级任务。
   - 入队目标页和前后各 2 页。

4. 图片失败：
   - `retryImage` 改为提交 retry 任务。
   - 成功后更新 UI 对应 image state。

5. 垂直滚动：
   - 当前 `_onVerticalScroll` 用比例估算 index，Phase 4 可先沿用。
   - 后续可换成 `VisibilityDetector` 或 item position 监听来计算真实可见页。

### 缓存状态建议

`episode_images.cache_status` 建议统一：

- `none`：未缓存。
- `queued`：已入预加载队列。
- `downloading`：正在下载。
- `done`：预加载完成。
- `downloaded`：用户主动下载，受保护。
- `failed`：最近一次失败。

### 验收标准

- 打开章节后首图优先加载，不被后面图片抢占。
- 连续阅读时后续 3-5 页大概率已缓存。
- 快速跳页不会继续大量下载旧位置附近图片。
- 图片失败后点击重试优先执行。
- 退出阅读器后预加载任务停止，不再写已销毁 provider 状态。
- 日志中能看到队列长度、成功数、失败数、取消数。

### 风险

- 如果直接用 `Future.wait` 并发缓存，仍然会乱序抢占。
- 如果队列回写太频繁，会造成 DB 写入压力，应合并或限流。
- 如果预加载窗口过大，低端设备内存和磁盘 IO 会抖动。

### 预期时间

2.5-4 天。

## 11. Phase 5：章节级预加载与章节转场

### 目标

用户读到章节末尾时，下一章已经拿到图片列表并缓存前几页，点击下一章或继续滚动时几乎无等待。

### 推荐模型

类似 Mihon 的 `ViewerChapters(curr, prev, next)` 和 Mangayomi 的 `ChapterPreloadManager`：

```dart
class ComicReaderChapterBundle {
  const ComicReaderChapterBundle({
    required this.current,
    this.previous,
    this.next,
  });

  final ComicReaderLoadedEpisode current;
  final ComicReaderLoadedEpisode? previous;
  final ComicReaderLoadedEpisode? next;
}
```

每个 loaded episode 包含：

- `episode`
- `images`
- `loadState`
- `firstPageCacheState`

### 实施步骤

1. 在 `_loadState` 时同时计算当前章节在章节列表中的位置。

2. 当前页距离末尾小于阈值时：
   - 阈值建议：总页数 <= 6 时最后 2 页；总页数 > 6 时最后 4 页。
   - 调用 `_ensureEpisodeImages(nextEpisode)` 获取下一章图片列表。
   - 入队下一章前 3 张图片，优先级 `nextChapter`。

3. 底部下一章按钮优化：
   - 如果下一章已预加载，直接切换，不显示全屏 loading。
   - 如果未预加载，显示轻量 loading dialog 或底部进度。

4. 垂直连续模式可选章节转场：
   - 在末尾显示“下一章：xxx”转场块。
   - 如果下一章已预加载，点击转场进入。
   - 后续可做自动拼接，但第一版建议不要直接拼接，避免当前阅读进度和章节状态复杂化。

5. 前一章预加载：
   - 可以先不做。
   - 等下一章稳定后再做向前预加载，因为 prepend 需要修正滚动位置，复杂度更高。

### 验收标准

- 阅读到最后几页时日志显示开始预加载下一章。
- 点击下一章时，如果已预加载，进入速度明显快于冷加载。
- 下一章预加载失败不影响当前章节阅读。
- 最后一章不再反复请求下一章，菜单或转场提示“已是最后一章”。
- 章节切换后阅读进度、已读状态属于正确章节。

### 预期时间

3-5 天。

## 12. Phase 6：阅读偏好扩展

### 目标

把阅读器从“基础模式切换”升级为可长期使用的阅读环境。

### 推荐偏好字段

扩展 `ReaderPreferences`：

第一版建议只做：

- `showPageIndicator`
- `keepScreenOn`

裁边、滤镜、亮度可以第二轮做。

### UI 建议

使用底部设置 sheet，分为三个 tab：

- 阅读：模式、方向、双页、页间距。
- 显示：适配方式、背景、页码、全屏、常亮。
- 图像：裁边、灰度、反色、亮度、重试失败图片。

### 实施要点

- 不要让设置 sheet 改动时重建整个 reader session。
- 对图片 fit 的改变只刷新图片布局，不重新抓图片。
- 对阅读模式改变要保持当前 logical index。
- 背景色应作用于 reader content，不影响菜单可读性。
- 页间距在垂直模式中影响 `SizedBox(height: gap)`，在 paged 模式中可影响 padding。

### 验收标准

- 切换阅读模式后仍停留在同一页附近。
- 修改页间距不丢失当前进度。
- 修改背景色立即生效。
- showPageIndicator 关闭后菜单隐藏时不显示页码浮层。
- 偏好重启 app 后仍保留。

## 13. Phase 7：自定义封面、标题、作者、汉化组

### 目标

支持用户修正作品元数据，并让自定义标题参与章节更新搜索兜底。自定义封面采用“阅读器当前页图片设为封面”的主路径：把当前页图片本体保存到受保护封面缓存，再让详情页和书架读取这个本地文件。

这是用户明确提出的关键需求，优先级应高于许多阅读器视觉增强。

### 当前已有能力

已有字段：

- `custom_cover_image_url`
- `custom_cover_local_path`

已有方法：

- `ComicRepository.updateCustomCover`
- `LocalComicRepository.updateCustomCover`

缺失：

- 从阅读器当前页设置封面的交互入口。
- 将当前页图片复制/登记为受保护封面缓存的服务。
- 自定义标题
- 自定义作者
- 自定义汉化组
- 自定义更新搜索关键词
- 来源标题与展示标题分离

### 自定义封面设计原则

- 主路径：阅读器当前页图片 -> 本地图片文件 -> 受保护封面缓存 -> `custom_cover_local_path`。
- `custom_cover_image_url` 不应作为主要展示依据；它只能记录“这张封面来自哪个页面 URL/图片 URL”，或作为跨设备/导入恢复时的兜底来源。
- 详情页和书架展示封面时，应始终优先读取 `custom_cover_local_path` 指向的本地文件。
- 自定义封面文件必须受保护，普通缓存清理、首话首图修正、章节刷新、封面预热都不能覆盖它。
- 如果当前页是已下载文件，设封面时应复制文件，而不是引用下载目录原路径，避免用户删除下载章节后封面丢失。
- 如果当前页是临时缓存文件，也应复制到封面缓存目录，避免普通页面缓存清理后封面丢失。

### 数据库设计建议

开发期可以直接升级 schema。如果后续需要兼容迁移，再写正式 migration。

在 `comics` 表新增：

```sql
source_title TEXT,
custom_title TEXT,
source_author TEXT,
custom_author TEXT,
source_translation_group TEXT,
custom_translation_group TEXT,
custom_cover_source_episode_id TEXT,
custom_cover_source_image_index INTEGER,
custom_cover_source_image_url TEXT,
custom_search_title TEXT,
metadata_updated_at INTEGER
```

兼容策略：

- 现有 `title` 暂时作为 display title。
- 新增后，`source_title` 初始填原 `title`。
- `custom_title` 为空时，展示 `source_title/title`。
- `custom_title` 非空时，展示 `custom_title`。

更长期的规范：

- `title` 可继续保存最终展示标题，降低现有查询改造量。
- `source_title/custom_title` 保存来源和覆盖来源。
- 每次更新来源解析结果时，只更新 `source_title`，不要覆盖 `custom_title`。
- 写入 `title = custom_title ?? source_title`，便于现有 UI 少改。

### 模型改造

扩展：

- `ComicRecord`
- `ComicDetail`
- `ComicShelfItem`
- `LibraryDetailHeader`
- `LibraryWorkItem`

新增字段：

### 仓储接口

在 `ComicRepository` 增加：

```dart

  required String comicId,

  String? sourceImageUrl,

  bool searchTitle = false,

```

旧的 `updateCustomCover({ customCoverImageUrl })` 可以保留为远程导入/兼容接口，但不应再作为阅读器设封面的主路径。阅读器设封面必须走本地文件写入接口。

### 封面缓存服务

建议新增 `ComicCustomCoverService` 或扩展 `LibraryCoverCacheService`：

职责：

- 接收当前页图片的本地路径或 URL。
- 如果只有 URL，先调用 reader cache 下载图片。
- 将图片复制到稳定目录，例如 `<app-cache>/protected_covers/comic/<comicId>/custom_cover.<ext>`。
- 生成/复用 `ImageCacheKeys.customCover(ownerType: comic, ownerId: comicId)`。
- 在 `cached_images` 中登记 `role = customCover`、`protected = true`、`local_path = copiedPath`。
- 调用仓储写入 `custom_cover_local_path` 和来源追踪字段。

注意：

- 封面缓存保存的是图片本体，不是 URL。
- 不要直接把 `episode_images.local_path` 写成 `custom_cover_local_path`，必须复制一份到封面专用位置。
- 复制时尽量保留原扩展名；无法判断时可根据 mime 或默认 `.jpg`。
- 如果新封面写入成功，再替换旧封面路径；失败时保留旧封面。

### UI 设计

详情页 `more` 菜单增加：

- 作者：可清空恢复来源作者。
- 汉化组：可清空恢复来源汉化组。
- 更新搜索关键词：默认跟随标题；高级项，可单独填写。

阅读器菜单增加：

- 将当前页设为封面。

详情页封面区域可选增加：

- 恢复默认封面。
- 查看封面来源：来自第 N 章第 M 页。
- 从 URL 导入封面。这个可以作为高级/备用能力，不是主路径。

建议显示“来源值”作为辅助文本：

- 来源标题：xxx
- 来源作者：xxx
- 来源汉化组：xxx

这样用户知道自己覆盖了什么。

### 更新策略接入

当前 `NetworkComicEpisodeRefreshService.fetchEpisodeLinksFromTid(String tid)` 只有 tid，不知道 comicId，也拿不到用户自定义标题。建议改造接口：

```dart
class ComicEpisodeRefreshRequest {
  const ComicEpisodeRefreshRequest({
    required this.comicId,
    required this.sourceTid,
    this.displayTitle,
    this.customTitle,
    this.customSearchTitle,
    this.sourceTitle,
  });
}

abstract class ComicEpisodeRefreshService {
  Future<List<ComicEpisodeLink>> fetchEpisodeLinks(ComicEpisodeRefreshRequest request);
}
```

关键词优先级：

1. `customSearchTitle`
2. `customTitle`
3. `displayTitle`
4. `sourceTitle`
5. 当前帖 subject 解析出的 normalizedTitle

搜索时可以多关键词尝试：

- 第一轮：最高优先级关键词。
- 第二轮：如果结果为空或低分，尝试来源 normalizedTitle。
- 第三轮：可尝试去掉括号、去掉汉化组、去掉卷/话后缀的简化标题。

评分时应加入：

- 标题包含关键词：高分。
- 关键词包含标题核心词：中高分。
- 当前漫画作者/汉化组命中：加分。
- tid 与当前 tid 相同：跳过。
- fid/typeid/sourceTagName 一致：加分。

### 实施步骤

1. 数据库和模型增加字段。
2. 仓储读写展示标题、作者、汉化组。
3. 新增自定义封面本地文件写入服务。
4. 阅读器菜单增加“将当前页设为封面”。
5. 详情页增加编辑作品信息 sheet。
6. 书架卡片展示自定义标题，并优先使用 `custom_cover_local_path`。
7. 更新服务接口从 `tid` 改成 request。
8. `ComicDetailAdapter.refreshWork` 传入 detail 的自定义字段。
9. 搜索兜底使用自定义关键词优先。
10. 增加日志：本次刷新使用了哪个关键词，命中了哪些候选，最终合并了多少章节。

### 验收标准

- 在阅读器菜单点击“将当前页设为封面”后，当前页图片被复制到受保护封面缓存目录。
- 设为封面后，`custom_cover_local_path` 指向本地图片文件，详情页和书架立即使用该图片。
- 删除本章普通页面缓存或下载章节后，自定义封面仍然存在。
- 普通封面预热、首话首图修正、刷新章节不会覆盖自定义封面。
- 修改标题后，详情页标题立即更新。
- 修改标题后，书架卡片标题立即更新。
- 修改作者/汉化组后，详情页头部立即更新。
- 清空自定义字段后恢复来源解析值。
- 设置自定义搜索关键词后，刷新章节时日志显示使用该关键词。
- 对解析标题错误的作品，设置正确标题后，搜索兜底能找到章节。
- 刷新来源信息时不会覆盖用户自定义标题/作者/汉化组。
- 自定义封面仍保持最高优先级，不被首话首图覆盖。

### 风险

- 如果继续只在 `comics.title` 存最终展示标题，可能丢失来源标题。应尽快补 `source_title`。
- 如果把页面缓存路径直接当作封面路径，清理页面缓存后封面会丢失；必须复制到受保护封面缓存。
- 如果只保存图片 URL，源站防盗链、删图或 cookie 变化都会导致封面失效；必须保存图片本体。
- 更新服务接口修改会影响 `ComicDetailController.refreshEpisodes` 和 `ComicDetailAdapter.refreshWork` 两条调用链，需要一起改。
- 搜索关键词过宽可能误合并其他作品章节，必须保留评分阈值和候选日志。

### 预期时间

2.5-4 天。

## 14. Phase 8：更新策略现代化

### 目标

让“更新章节”在目录页、当前帖连续链接、搜索兜底之间有清晰策略，并且可解释、可调试。

### 当前策略

`NetworkComicEpisodeRefreshService.fetchEpisodeLinksFromTid`：

1. 先 `discoverFromTidWithPreference(tid, preferCatalogFirst: true)`。
2. 如果结果是 catalog 且非空，直接返回。
3. 否则 `_searchFallbackFromCurrentTid(tid)`。
4. 搜索关键词来自当前帖 subject 的 normalizedTitle。
5. 搜索候选按 `_scoreTitleSimilarity` 过滤和排序。
6. 对 top 3 候选抓目录/章节链接并合并。

### 建议改造

1. 引入 request：
   - 带 `comicId/sourceTid/displayTitle/sourceTitle/customTitle/customSearchTitle/sourceFid/sourceTypeId/sourceTagName`。

2. 引入 refresh result：

```dart
class ComicEpisodeRefreshDebugResult {
  final List<ComicEpisodeLink> links;
  final EpisodeDiscoveryStrategy primaryStrategy;
  final List<String> attemptedKeywords;
  final List<ScoredEpisodeSearchCandidate> candidates;
  final int insertedCount;
  final int updatedCount;
  final String? warning;
}
```

短期服务仍可返回 links，但日志层应记录这些信息。

3. 多阶段更新：
   - Stage A：目录页。
   - Stage B：当前帖连续链接。
   - Stage C：自定义标题搜索。
   - Stage D：来源标题搜索。
   - Stage E：当前 subject normalized 搜索。

4. 合并策略：
   - 以 tid 为主键。
   - 同 tid 保留标题更完整的一侧。
   - 不删除本地已有章节，除非后续做显式“清理不存在章节”。
   - 新增章节默认未读。
   - 更新章节标题时不要覆盖用户对章节的手动状态。

5. 防误匹配：
   - 分数低于阈值不合并。
   - 候选标题和关键词字符重叠太低不合并。
   - 如果候选目录返回的章节 tid 与当前作品已有 tid 完全无交集，要降低信任。
   - 可要求至少 2 个章节链接或与当前 sourceTid 有邻近关系。

### 验收标准

- 目录可用时优先使用目录。
- 目录不可用但搜索可用时能补齐章节。
- 自定义标题能改变搜索结果。
- 搜索候选日志可定位为什么某个候选被接受/拒绝。
- 刷新后书架 `workUpdatedAt/lastFetchedAt/checkUpdatedAt` 有合理更新。
- 新增章节出现在书架未读角标中。

### 预期时间

3-5 天。

## 15. Phase 9：性能、内存、失败恢复和可观测性

### 目标

让阅读器在长章节、图片失败、网络慢、快速跳页、频繁进出页面时仍然稳定。

### 优化项

#### 15.1 图片尺寸和布局稳定

当前垂直模式 `_ReaderImageSlot` 用 `minHeight = width * 4 / 3` 预留空间，这能降低跳动，但真实漫画长图可能高度差异很大。

建议：

- 图片首次加载成功后记录宽高到内存 map。
- 可选持久化 `episode_images.width/height`。
- 第二次打开时按真实宽高预留空间。
- 长图按 `fitWidth`，不要强行固定高度。

#### 15.2 可见页计算

垂直滚动通过滚动比例估算 index，长短图混排时不精确。建议：

- 短期：保留比例估算。
- 中期：每个图片 slot 上报布局 offset，高频滚动时用 viewport center 找最近图片。
- 或引入轻量 `VisibilityDetector`，但要注意依赖和性能。

#### 15.3 失败恢复

增加：

- 页面级重试。
- 全部失败图片重试。
- 切换网络后自动重试可选。
- 失败状态写入 `episode_images.cache_status = failed`。
- 失败页不参与自动完成已读。

#### 15.4 内存边界

建议：

- 预加载队列只负责磁盘缓存，不强制大量 `precacheImage` 解码到内存。
- 当前页前后 1-2 页可 `precacheImage`。
- 章节级预加载只下载下一章前几页，不把整章全部解码。
- reader dispose 时取消队列和释放 controller。

#### 15.5 观测指标

记录：

- `reader.open.ms`
- `reader.first_image_visible.ms`
- `reader.page_change.persist.ms`
- `reader.image_cache.hit/miss`
- `reader.preload.queue_size`
- `reader.preload.success/failed/cancelled`
- `reader.chapter_complete`
- `reader.refresh.keyword`

可以先用 debug print 或现有 `ShelfPerfTrace` 风格的小工具，后续再统一。

### 验收标准

- 100 页章节连续滚动没有明显卡顿。
- 快速拖动 Slider 不产生大量旧任务继续下载。
- 网络失败后页面显示可重试。
- 失败页不会误触发已读。
- 退出阅读器后没有持续刷日志或写库。

### 预期时间

2-4 天。

## 16. Phase 10：验收、测试和灰度

### 目标

确保优化后的阅读器不破坏现有漫画、小说、统一书架能力。

### 单元测试建议

1. 阅读完成策略：
   - index < lastIndex 不标记已读。
   - index == lastIndex 标记已读。
   - 单页章节显示成功后标记已读。
   - 失败页不标记已读。

2. 未读聚合：
   - 没有状态行的章节计为未读。
   - 已读状态行不计未读。
   - 新增章节默认未读。

3. 自定义元数据：
   - custom title 优先展示。
   - 清空 custom title 恢复 source title。
   - custom search title 优先用于更新关键词。

4. 更新合并：
   - 同 tid 不重复插入。
   - 搜索候选低分不合并。
   - 同 tid 标题可更新但状态不丢失。

5. 预加载队列：
   - 同任务去重。
   - retry 优先于 adjacent。
   - dispose 后取消。

### Widget 测试建议

- `UnifiedDetailPage` 点击章节不立即变淡。
- `ComicReaderPage` 读到最后页后返回，详情页变淡。
- `UnifiedShelfPage` 未读角标显示正确数字。
- `ReaderBottomPanel` 在窄屏不溢出。
- `ReaderTopBar` 长标题省略。

### 手工验收场景

1. 新漫画加入书架，有 5 章，未读角标为 5。
2. 进入第 1 章，只读到第 3 页退出，未读角标仍为 5。
3. 再进入第 1 章读到最后一页退出，未读角标变 4。
4. 在详情页手动取消第 1 章已读，未读角标变 5。
5. 设置自定义标题，回书架看到新标题。
6. 使用自定义标题刷新章节，能看到刷新日志关键词。
7. 网络断开打开未缓存章节，失败页可重试，不误标已读。
8. 快速跳到第 50 页，预加载围绕第 50 页发生，不继续大量加载第 1 页附近。
9. 读到倒数几页，下一章开始预加载。
10. 下一章按钮进入速度快于冷启动。

### 灰度策略

建议使用 feature flag：

- `readerStrictCompleteRead`
- `readerPreloadQueueEnabled`
- `readerNextChapterPreloadEnabled`
- `readerCustomMetadataEnabled`
- `readerRefreshMultiKeywordEnabled`

先默认打开 `readerStrictCompleteRead` 和 `readerCustomMetadataEnabled`，预加载队列可先内部开关验证。

### 预期时间

1.5-3 天。

## 17. 推荐执行顺序

如果按最小高价值闭环推进：

1. Phase 1：修复最后一页才已读。
2. Phase 2：统一未读数和状态聚合。
3. Phase 7：自定义标题/作者/汉化组，接入搜索更新。
4. Phase 4：预加载队列。
5. Phase 3：菜单升级。
6. Phase 5：下一章预加载。
7. Phase 6：阅读偏好扩展。
8. Phase 8：更新策略完整现代化。
9. Phase 9/10：性能和验收收尾。

这样可以先解决用户最敏感的问题：已读状态正确、书架未读数正确、自定义标题能让更新更可靠、阅读加载更顺。

## 18. 关键决策清单

实现前建议确认这些决策：

- 自动已读阈值：严格最后一页，还是连续模式允许最后一页进入视口 70% 即已读。建议第一版严格最后一页。
- 单页章节：首图成功显示后是否立即已读。建议是。
- 自定义标题是否直接覆盖 `comics.title`。建议短期覆盖展示值，同时保留 `source_title/custom_title`。
- 更新搜索关键词是否允许用户单独配置。建议允许，作为高级字段。
- 下一章预加载是否自动拼接到垂直连续阅读。建议第一版不自动拼接，只预加载和加转场。
- 缓存本章和预加载缓存是否同等保护。建议手动下载保护，预加载缓存可清理。

## 20. 最终验收指标

体验指标：

- 打开已缓存章节，首图在 300ms-800ms 内可见。
- 打开未缓存章节，首图优先加载，后续页不会先于首图大量出现。
- 连续阅读时下一页等待感明显降低。
- 详情页已读变淡行为与真实阅读完成一致。
- 书架未读角标与详情页未读章节数一致。

数据指标：

- `reading_progress` 和 `library_episode_state` 不冲突。
- 新增章节默认未读。
- 自定义元数据不会被刷新覆盖。
- 自定义封面保存的是图片本体对应的本地文件，不依赖原始图片 URL 可访问。
- 搜索兜底关键词可追踪。

工程指标：

- 阅读器 UI、状态写入、缓存队列、更新服务职责分离。
- 每个阶段都有可独立合并的 PR/commit。
- 核心状态逻辑有单元测试。
- 预加载和更新服务有日志，出问题能定位。

## 21. 结论

Y300 当前漫画阅读器已经有可演进的基础，最应该先修的是状态语义：不要进入章节就已读，而是让阅读器在最后一页发出完成事件。这个点修正后，详情页变淡、书架未读角标、继续阅读入口都会有稳定地基。

第二个关键点是元数据：自定义标题不只是展示问题，而是更新章节搜索兜底的输入问题。应把自定义标题/搜索关键词提升为漫画域的一等字段，并在刷新服务中优先使用。

第三个关键点是预加载：不要继续用零散的 `Future.wait` 扩展缓存逻辑，而应建立轻量优先级队列。这样后续无论做下一章预加载、失败重试、缓存策略、性能观测，都有清晰挂点。

按本文阶段推进，可以先用 7-12 天完成“状态正确 + 未读正确 + 自定义标题参与更新 + 基础预加载”的核心闭环，再继续把菜单、显示设置、章节转场和性能观测打磨成成熟阅读器体验。
