# 图片与列表加载性能优化方案

> 目标：用"简化"换"性能"。修复书架封面、漫画竖向阅读、帖子详情页三处的图片/列表加载卡顿，
> 同时把当前过度耦合的图片缓存体系拆成职责清晰、可维护、可扩展的两层结构。
>
> 本文档定义方向、架构、设计模式、领域模型与关键接口，并给出分阶段实施计划。
> 它是 [原生模式缓存系统升级方案.md](原生模式缓存系统升级方案.md) §3.1（资产 vs 缓存）的落地与收口，
> 不推翻该方案，而是把"资产 vs 缓存"这一刀切到底。

## 1. 背景与症状

三个表面症状，根因相同：

| 场景 | 症状 | 用户感受 |
| --- | --- | --- |
| 书架/收藏封面 | 快速滑动时看不到封面，停下后才开始加载 | "停下它才开始加载，非常差劲" |
| 漫画竖向阅读 | 来回滚动时图片反复重新加载/解码 | "回到上部途中明显感觉又加载了一遍" |
| 帖子详情页 | 同上，长帖滚动时图片不断重载 | "无论怎么滑都像在加载" |

对照"丝滑"App 的体验：图片加载好后，在很长的上下区域内可任意滚动查看，已加载内容不再重载。

## 2. 根因诊断（基于现有代码）

三条根因，按影响排序：

### 2.1 全局图片缓存走默认值 + 不降采样（症状：来回滑重载）

- 全局 `PaintingBinding.instance.imageCache` 没有任何配置（[main.dart](../lib/main.dart) 中仅有 `WidgetsFlutterBinding.ensureInitialized()`），
  走 Flutter 默认 **100MB / 1000 张** 上限。
- 所有图片按**原始分辨率**解码：[shelf_cover_image.dart](../lib/shared/widgets/shelf/shelf_cover_image.dart) 暴露了
  `cacheWidth/cacheHeight` 但调用方未传；[library_cached_image.dart](../lib/features/cache/presentation/widgets/library_cached_image.dart)
  的 `Image.file`/`Image(NetworkImage)` 完全没有降采样。
- 后果：一张条漫页/论坛大图解码成 bitmap 按**像素面积**计，单张可达数 MB。100MB 预算放不下几张，
  LRU 立即驱逐。滚回上方时解码缓存已空 → 从磁盘重新解码（甚至重新拉网络）。

> ⚠️ 关键认知：`imageCacheMaxBytes` 偏好（[app_storage_keys.dart](../lib/core/config/app_storage_keys.dart#L8)）目前**只驱动磁盘文件的
> `pruneToLimit`**（[default_image_cache_service.dart:419](../lib/features/cache/data/services/default_image_cache_service.dart#L419)），
> 它管的是"磁盘留多少"，**完全没有设置过运行时解码缓存 `imageCache.maximumSizeBytes`**。这两件事被混为一谈了。

### 2.2 显示控件"等"后台队列喂路径（症状：停下才加载封面）

- [ShelfCoverImage](../lib/shared/widgets/shelf/shelf_cover_image.dart) 是**只读本地文件**的：`localPath` 为空就只显示占位图，
  没有网络兜底（注释明确写了"依赖背景预热管线"）。
- `localPath` 的唯一来源是 [ShelfCoverWarmupService](../lib/features/library_shared/domain/services/shelf_cover_warmup_service.dart)（3 并发队列）。
- 而 `UnifiedShelfController._startCoverWarmup` 在**每次可见范围变化时都 `cancel()` 旧 token 再重启**。
  快速滑动时范围一直在变 → 队列永远处于"没下完就被取消重启"的循环 → 停下来范围稳定后才跑完 → 封面才出现。

> 这是一个**架构方向错误**：让"显示"依赖"一个会被频繁取消的后台编排"。
> 显示控件必须能自食其力（本地优先、网络兜底），队列只能是"提前量"优化，不能是"显示前提"。

### 2.3 阅读器预热器预热错了对象（症状：重复下载）

- 引擎层 [image_reader_engine.dart:187](../lib/features/reader_shared/presentation/engine/image_reader_engine.dart#L187)
  调 `precacheWindow` 时传 `localPathResolver: (item) => null`，导致它预热的是**网络** provider 而非已缓存的本地文件。
- 注意：route 层 [continuous_image_reader_route.dart:181](../lib/features/reader_shared/presentation/continuous_image/continuous_image_reader_route.dart#L181)
  传的是 `_cachedLocalPathFor`（正确）。两个调用点行为不一致，引擎侧是 bug。

### 2.4 过度设计放大了前三条

当前 [DefaultImageCacheService](../lib/features/cache/data/services/default_image_cache_service.dart) 是一个 **SQLite 权威层**：
它用**业务 key**（`cover/comic/{id}`、按 owner/role/protected/retentionClass）自行编排下载、裁剪、保护。

问题不在"它存在"，而在"**连最普通的可再生缓存（封面、帖子图、随手翻阅的页）也被它按资产标准托管**"。
这带来两个代价：

1. 显示控件不得不等这个权威层（2.2）。
2. 同一张图在帖子详情 / 阅读器 / 漫画页可能因业务 key 不同而落多份（方案 §14.8 已警示）。

而让 App"图能不能快"这件事，**根本不需要 owner/role/protected**。它只需要：按 URL 存、装不下就 LRU 扔。

## 3. 核心原则：把"资产"和"缓存"彻底切开

这是整份方案的灵魂，也是 [原生模式缓存系统升级方案.md](原生模式缓存系统升级方案.md) §3.1 的收口。
**不按"图片类型"分（封面/帖子图/漫画页），而按"所有权"分成两套性质完全不同的系统：**

| | **缓存层（Cache）** | **资产层（Asset）** |
| --- | --- | --- |
| 装什么 | 封面、帖子图、随手翻阅的阅读器图 | 用户**显式下载**的漫画/小说、用户**自设**的自定义封面 |
| 用户在意吗 | 不在意，丢了重下 | 在意，丢了 = 数据丢失 |
| 该多"聪明" | **越笨越好**：URL key + 全局上限 + LRU，自食其力 | 持久、有清单、用户可管理、**永不自动删** |
| 设计目标 | 性能与简化 | 正确性与可控 |
| 底层依赖 | `flutter_cache_manager` + `cached_network_image` + 全局 `imageCache` | 现有 SQLite 权威模型（搬到这一层才名副其实） |

一句话：**缓存层做减法（做笨），资产层做加法（做重）。** 丝滑来自缓存层变笨，正确性来自资产层独立。

### 3.1 设计原则落点

- **单一职责（SRP）**：显示、缓存编排、资产管理、淘汰策略各自独立，互不内联。
- **依赖倒置（DIP）**：UI 依赖抽象（`AppImageSource`），不依赖 `flutter_cache_manager`/SQLite 具体实现。
- **关注点分离**：`imageCache`（运行时解码缓存）/ 磁盘文件缓存 / 业务索引（仅资产）三件事分开，不再混用一个"上限"概念。
- **开闭原则**：新增图片来源（论坛头图、表情、头像）只新增一种 `AppImageSource`/key 策略，不改显示控件。
- **不要把所有逻辑耦合到一处**：显示控件不做缓存策略，缓存层不认识 owner/role，资产层不碰显示。

## 4. 目标架构

### 4.1 分层与模块边界

```text
┌─────────────────────────────────────────────────────────────┐
│ Presentation 显示层                                          │
│   AppImage（统一图片控件，唯一对外入口）                     │
│   - 输入 AppImageSource，自食其力：内存→磁盘→网络            │
│   - 不知道 owner/role/protected，不依赖任何后台队列          │
└───────────────┬─────────────────────────────────────────────┘
                │ 依赖抽象 AppImageSource / ImagePrefetcher
                ▼
┌─────────────────────────────────────────────────────────────┐
│ Cache 缓存层（可再生，做笨）          features/image_loading  │
│   ImagePrefetcher       —— "提前量"优化，可取消、只重排不清空 │
│   AppImageCacheManager  —— flutter_cache_manager 单例封装     │
│   GlobalImageCacheTuner —— 运行时 imageCache 预算 + 降采样策略│
└─────────────────────────────────────────────────────────────┘
                │（资产层把"用户下载/自定义封面"喂给缓存层做展示）
                ▼
┌─────────────────────────────────────────────────────────────┐
│ Asset 资产层（用户拥有，做重）        features/cache(收窄)    │
│   现 DefaultImageCacheService → 收窄为 ProtectedAssetStore    │
│   只管：自定义封面、已下载章节图。SQLite 权威、owner 删除、   │
│   protected、storage accounting 全部留在这里                 │
└─────────────────────────────────────────────────────────────┘
```

模块归属建议（遵循现有 `features/*` 边界）：

- 新增 `features/image_loading/`：放缓存层全部内容（`AppImage`、`AppImageSource`、`ImagePrefetcher`、
  `AppImageCacheManager`、`GlobalImageCacheTuner`）。它是 business-agnostic 的基础设施，可被任何 feature 依赖。
- 收窄 `features/cache/`：保留资产相关（protected 封面、下载索引、storage accounting、document/snapshot 页面缓存）。
  剥离"普通图片当资产托管"的职责。
- `library_shared` / `comic` / `thread` 只依赖 `features/image_loading` 的抽象，各自提供自己的 key 与 prefetch 触发。

### 4.2 设计模式选型

| 模式 | 用在哪 | 解决什么 |
| --- | --- | --- |
| **Facade** | `AppImage` / `AppImageCacheManager` | 把 `cached_network_image`、`flutter_cache_manager`、headers、URL 规范化藏在背后；UI 只见一个入口 |
| **Strategy** | `AppImageSource` 的子类 + `ImageDownscalePolicy` | 不同来源（网络/本地资产/protected）和不同降采样策略可替换，显示控件不变 |
| **Value Object** | `AppImageSource`、`ImagePrefetchRequest` | 不可变、可比较（== / hashCode），天然适合 key 去重与 `didUpdateWidget` 比对 |
| **Adapter** | `comic`/`thread`/`library_shared` 各自的 prefetch 触发器 | 把业务"可见窗口"翻译成统一 `ImagePrefetchRequest`，复用一个 prefetcher |
| **Singleton（via Riverpod Provider）** | `AppImageCacheManager`、`GlobalImageCacheTuner` | 全应用一个磁盘缓存实例、一处运行时预算 |

> 注意：**不引入新的"队列"框架**。`ImagePrefetcher` 复用 [ComicReaderPreloadQueue](../lib/features/comic/domain/services/comic_reader_preload_queue.dart)
> 已经验证过的"优先级 + `cancelExcept`（只重排不全清）"思路，而不是书架那套"全取消重启"。

### 4.3 领域模型与关键接口

以下为方向性接口草案，签名以可落地为准，实现细节留待编码。

**(a) 统一图片来源（Value Object + Strategy）**

```dart
/// 显示控件的唯一输入。不可变、可比较。
/// 它只描述"这是哪张图、怎么取"，不携带任何 owner/role/protected 业务语义。
sealed class AppImageSource {
  const AppImageSource();

  /// 用于 imageCache / 磁盘缓存 / prefetch 去重的稳定 key（规范化 URL hash 优先）。
  String get cacheKey;
}

/// 普通可再生网络图（封面、帖子图、阅读器图都走这里）。
class NetworkAppImageSource extends AppImageSource {
  const NetworkAppImageSource({
    required this.url,
    this.headerBuilder,
  });
  final String url;
  final ImageRequestHeaderBuilder? headerBuilder; // 复用现有 core/network
  @override
  String get cacheKey => /* normalizedUrlHash(url) */;
}

/// 资产层提供的本地文件（自定义封面、已下载页）。由 Asset 层解析出 path 后注入。
class LocalAssetImageSource extends AppImageSource {
  const LocalAssetImageSource({required this.localPath, required this.identity});
  final String localPath;
  final String identity;
  @override
  String get cacheKey => identity;
}
```

**(b) 缓存层管理器（Facade + Singleton）**

```dart
/// 全应用唯一的磁盘图片缓存底座，封装 flutter_cache_manager。
/// 缓存层不认识 owner/role；它只按 cacheKey 存取文件。
abstract class AppImageCacheManager {
  /// 取本地文件（命中返回，未命中返回 null，不触发下载）。
  Future<File?> getFileFromCache(String cacheKey);

  /// 下载并写入缓存，返回本地文件。失败抛异常由调用方兜底为网络直显/占位。
  Future<File> downloadToCache(NetworkAppImageSource source);

  /// 供资产层调用：把一个 protected 文件登记进缓存目录（同一 URL 不重复落盘）。
  Future<void> putExternalFile(String cacheKey, File file);
}
```

**(c) 运行时解码预算 + 降采样（关注点分离）**

```dart
/// 在 main() 中调用一次。设置 imageCache.maximumSizeBytes（区别于磁盘 pruneToLimit）。
abstract class GlobalImageCacheTuner {
  /// 按设备内存档位返回建议字节数（例：低端 96MB / 中端 192MB / 高端 256MB）。
  int recommendedBudgetBytes();
  void applyTo(ImageCache cache);
}

/// 降采样策略：把"显示尺寸 + DPR"翻译成 cacheWidth/cacheHeight。
/// 封面、阅读器（按屏宽）、缩略图各有不同实现，但显示控件只持有这个抽象。
abstract class ImageDownscalePolicy {
  ({int? cacheWidth, int? cacheHeight}) resolve(Size displaySize, double devicePixelRatio);
}
```

**(d) 预取器（Strategy + Adapter，复用既有思路）**

```dart
class ImagePrefetchRequest {
  const ImagePrefetchRequest({required this.source, required this.priority});
  final AppImageSource source;
  final int priority; // 越小越急：visible < nearAfter < nearBefore < background
}

/// 单例预取器：只做"提前量"。可被取消、可重排，但绝不取消"当前可见"项。
/// 复用 ComicReaderPreloadQueue 的 cancelExcept 语义，不要书架的 cancel-restart。
abstract class ImagePrefetcher {
  /// 提交一批请求；内部按 priority 排序，丢弃落窗外的旧任务（cancelExcept），
  /// 但不清空、不取消可见项。并发上限内调 AppImageCacheManager.downloadToCache。
  void submit(List<ImagePrefetchRequest> window);
}
```

**(e) 资产层收窄（SRP）**

```dart
/// 从 DefaultImageCacheService 收窄而来：只托管"用户拥有"的图片。
/// 它向缓存层提供 LocalAssetImageSource，供 AppImage 直接展示。
abstract class ProtectedAssetStore {
  Future<LocalAssetImageSource?> resolveCustomCover(String workId);
  Future<LocalAssetImageSource?> resolveDownloadedPage({
    required String workId, required String episodeId, required int index,
  });
  Future<int> deleteByOwner({required ImageCacheOwnerType ownerType, required String ownerId});
  // 现有 calculateUsageBytes / storage accounting 留在这里。
}
```

## 5. 分阶段实施计划

原则：**先止血（小改、立竿见影），再重构（拆层、根治），最后清理（去掉过度设计）。**
每个阶段独立可验收、可回滚，前一阶段不依赖后一阶段。

> 进度：✅ Phase 0 ｜ ✅ Phase 1 ｜ ✅ Phase 2 ｜ ✅ Phase 3 ｜ ✅ Phase 4（按三分原则落地，见下）

> **Phase 4 落地说明（依据用户决策）**：缓存层并非一刀切去账本，而是按**三分原则**收口：
> - **资产（protected）**：封面/自定义封面/已下载章节图 —— 留在 SQLite 权威账本，按 owner 精确删，普通清理不动。
> - **长期缓存（sticky）**：表情、论坛轮播图、版块顶部图/图标 —— 可再生但复用率高、需稳定存在与更新；一键清理**保留**，仅在容量压力 ephemeral 清完后才动。
> - **可清缓存（ephemeral）**：帖子正文图/附件、头像、博客图、在线浏览的漫画/小说页 —— 一键清理优先清、prune 优先淘汰。
>
> 工程化做法：新增 `ImageRetentionClassifier`（单一分类来源），修正轮播图/版块顶部图被错标为 ephemeral 的问题；`clearUnprotected`/`pruneToLimit` 改为 retention 感知（spare sticky / ephemeral-first）。数据与存储页的 role 分项统计**保留**（用户需要可管理性），不做减法。

### Phase 0：止血——全局预算 + 降采样（最高性价比，不动架构）

> 目标：症状 2.1（来回滑重载）当场缓解 ~80%。不改任何架构，只补两个被遗漏的设置。

任务：
1. 新增 `GlobalImageCacheTuner`，在 [main.dart](../lib/main.dart) 的 `WidgetsFlutterBinding.ensureInitialized()` 之后调用
   `applyTo(PaintingBinding.instance.imageCache)`，把 `maximumSizeBytes` 设到按机型档位（建议中端 192MB）。
   **明确区分**：这是运行时解码缓存，与 [default_image_cache_service.dart:419](../lib/features/cache/data/services/default_image_cache_service.dart#L419)
   的磁盘 `pruneToLimit` 是两件事，文档与命名都要分开。
2. 给现有显示控件补降采样：
   - [ShelfCoverImage](../lib/shared/widgets/shelf/shelf_cover_image.dart) 的调用方（`ShelfCoverCard`、`unified_shelf_page` 的 `_WorkList`）
     传入 `cacheWidth = (瓦片宽 * devicePixelRatio).round()`。
   - [LibraryCachedImage](../lib/features/cache/presentation/widgets/library_cached_image.dart) 的 `Image.file`/`Image(NetworkImage)`
     增加 `cacheWidth`（阅读器按屏宽 * DPR；封面按显示宽 * DPR）。

设计约束：降采样值由 `ImageDownscalePolicy`（Phase 0 可先用简单内联实现，Phase 2 再抽象）产出，不要在 widget 里散落魔法数。

验收：
- 漫画竖向阅读、帖子详情页来回滚动，已加载图片不再可见地重新解码（用 Flutter DevTools 的 raster/`imageCache` 计数验证）。
- `imageCache.currentSizeBytes` 稳定在预算内，不再频繁触顶驱逐。

回滚：删除 tuner 调用 + 移除 `cacheWidth` 入参即可。

### Phase 1：统一显示控件 AppImage（解耦"显示"与"队列"）

> 目标：症状 2.2（封面停下才加载）根治。显示控件自食其力，不再等任何后台队列。

任务：
1. 在 `features/image_loading/` 新增 `AppImage` + `AppImageSource`（§4.3 a）。`AppImage` 的加载顺序：
   **内存(imageCache) → 磁盘(AppImageCacheManager.getFileFromCache) → 网络(downloadToCache 或直接 NetworkImage)**，
   每一步都自食其力，任意一步成功即显示，全程 `gaplessPlayback: true`。
2. 新增 `AppImageCacheManager`（§4.3 b）封装 `flutter_cache_manager` 为**单应用单例**（Riverpod Provider），
   复用现有 [imageCacheManagerProvider](../lib/features/cache/data/providers/image_cache_providers.dart#L39) 的目录解析。
3. 把 `ShelfCoverImage` 改为 `AppImage` 的薄封装（或直接替换调用点）：**封面有 localPath 用 LocalAssetImageSource，
   否则用 NetworkAppImageSource 兜底**——这一步就消除了"必须等队列喂路径"。
4. `CachedLibraryImage`/`LibraryCachedImage` 的展示职责并入 `AppImage`；保留 `onImageResolved` 尺寸回调（帖子图布局需要）。

设计约束：
- `AppImage` 绝不 import `flutter_cache_manager`/SQLite，只依赖 `AppImageSource` 抽象（DIP）。
- key 用 `AppImageSource.cacheKey`（规范化 URL hash），落实方案 §6.3：同一 URL 不再多份。

验收：
- 断网时，已缓存封面仍秒显（走磁盘）；未缓存封面显示占位而非空白。
- 快速滑动书架，可见封面**边滑边出**，不再"停下才加载"。
- `reader_shared` 仍不 import `comic`/`thread`（保持既有架构约束）。

### Phase 2：统一预取器 ImagePrefetcher（"提前量"，不再 cancel-restart）

> 目标：把书架的"全取消重启"换成"只重排不清空"，并统一漫画/帖子/书架的预取逻辑。

任务：
1. 在 `features/image_loading/` 新增 `ImagePrefetcher`（§4.3 d），并发上限内调 `AppImageCacheManager.downloadToCache`。
   内部排序与丢弃策略**直接借鉴** [ComicReaderPreloadQueue](../lib/features/comic/domain/services/comic_reader_preload_queue.dart)
   的 `cancelExcept`：落窗外的旧任务丢弃，但**绝不取消 priority=visible 的项**。
2. 各业务提供 Adapter，把"可见窗口"翻译成 `List<ImagePrefetchRequest>`：
   - 书架：替换 [ShelfCoverWarmupService](../lib/features/library_shared/domain/services/shelf_cover_warmup_service.dart)
     + `UnifiedShelfController._startCoverWarmup` 的 cancel-restart 逻辑，改为向 `ImagePrefetcher.submit` 提交。
     保留现有 `ShelfCoverWarmupPriority`/`prioritize...` 的优先级计算（那部分是对的），只换执行引擎。
   - 漫画：现有 preload queue 可保留或并入（二选一，见"开放问题"）。
   - 帖子详情：当前无预取，新增"可见楼层前后 N 张"的 Adapter。
3. 抽象 `ImageDownscalePolicy`（§4.3 c），把 Phase 0 内联的降采样值收口到策略对象，按场景注入。

设计约束：
- `ImagePrefetcher` 是 business-agnostic 单例；业务差异全在各自 Adapter 里（SRP + Adapter 模式）。
- prefetch 失败静默吞掉，**永不影响 AppImage 的自食其力展示**。

验收：
- 快速滑动书架/漫画，可见项不再因滚动被取消；停止滚动时前后若干张已预取就绪。
- 删除 `ShelfCoverWarmupService` 的 cancel-restart 路径后，封面首屏与刷新行为不回退。

### Phase 3：修阅读器预热器 + cacheExtent 校准

> 目标：症状 2.3（重复下载）根治，竖向阅读上下缓冲合理。

任务：
1. 修 [image_reader_engine.dart:187](../lib/features/reader_shared/presentation/engine/image_reader_engine.dart#L187) 一侧的
   `localPathResolver: (item) => null`，与 route 侧一致地解析本地路径，让预热器预热**本地文件**而非网络。
2. 校准 `viewportCacheExtentFactor`：当前漫画 0.75、线程默认 0。结合 Phase 0 的大 `imageCache` 预算，
   可把竖向阅读的 cacheExtent 适度提高（如 1.0~1.5 屏），让上下缓冲区图片常驻、滚动更稳。具体值用真机调。

验收：
- 竖向阅读快速上下滚，DevTools 网络面板无对同一图片的重复请求。
- 上下缓冲区图片在 cacheExtent 内常驻，滚回不重解码。

### Phase 4：资产层收窄 + 缓存层去过度设计（简化收口）

> 目标：兑现"资产 vs 缓存"两层架构，删掉缓存层不该有的业务账本，简化 §10 统计与清理。

任务：
1. 把 [DefaultImageCacheService](../lib/features/cache/data/services/default_image_cache_service.dart) 收窄为 `ProtectedAssetStore`（§4.3 e）：
   **只保留** protected（自定义封面）、downloaded（已下载页）、按 owner 删除、storage accounting。
2. **普通可再生图**（cover 远端原图、threadInline、comicPage 在线浏览）不再写业务 SQLite 账本，
   直接走缓存层 `AppImageCacheManager`（URL key + LRU + 全局预算）。
3. 简化"数据与存储"页（[data_storage_page.dart](../lib/features/more/presentation/data_storage_page.dart)）：
   缓存层只报总量 + 一个"清空缓存"按钮；资产层报"每部下载占用 + 自定义封面"，用户手动管理。
   砍掉 §10 中对普通图按 role 的细分统计（用户其实只想知道"能随便清的"和"我下载的"两类）。
4. cache key 统一为规范化 URL hash（落实方案 §6.3、§14.8），删除按业务 key 落多份的路径。

设计约束：
- 资产层是唯一保留 SQLite 权威/owner/protected 的地方；缓存层零账本。
- 删除作品时，资产层按 owner 精确删（用户数据该精确的地方）；缓存层不参与，靠 LRU 自然过期。

验收：
- 一键清缓存：清掉普通图，自定义封面与已下载内容**不受影响**。
- 删除一部已下载漫画：其下载页与自定义封面被精确删除。
- "数据与存储"只剩"缓存总量 / 下载内容 / 自定义封面"三类，用户能看懂。

## 6. 阶段依赖与建议顺序

```text
Phase 0 (止血)  ──► 独立，立刻可做，先上，先爽
Phase 1 (AppImage) ──► 依赖 Phase 0 的 DownscalePolicy 雏形；解耦显示与队列
Phase 2 (Prefetcher) ──► 依赖 Phase 1（AppImage 自食其力后，队列才能安全退化为"提前量"）
Phase 3 (Reader 修复) ──► 可与 Phase 2 并行；独立小修
Phase 4 (拆层简化) ──► 依赖 Phase 1（显示已不依赖权威层）才能安全收窄 SQLite
```

强烈建议：**先把 Phase 0 单独做完并验证手感**，再决定后续节奏。Phase 0 两条改动加起来很小，
但能解决你 80% 的痛感；做完你会对"到底还要不要继续拆层"有更实在的判断。

## 7. 风险与开放问题

| 项 | 说明 | 建议 |
| --- | --- | --- |
| 是否直接用 `cached_network_image` | 它做对的两件事（URL 内存缓存 + memCacheWidth）已被 Phase 0/1 覆盖 | 可在 `AppImage` 内部用它做网络分支实现细节，但**不让它泄漏到 UI**（Facade 包住）；也可不用，自管 NetworkImage。二选一不影响架构 |
| 漫画 preload queue 去留 | 已有成熟的 `ComicReaderPreloadQueue` | Phase 2 可让它实现 `ImagePrefetcher` 接口，或保留独立、仅共享 `AppImageCacheManager`。倾向后者，减少回归风险 |
| `imageCache` 预算档位 | 不同机型内存差异大 | 用 `dart:io` 估算或保守固定 192MB；低端机降到 96MB。真机实测后定档 |
| cacheExtent 提高的内存代价 | 大 cacheExtent + 大预算可能在超长帖吃内存 | 配合降采样后单图很小，风险可控；仍需真机长帖压测 |
| SQLite 收窄的迁移 | 现有 `cached_images` 表含普通图记录 | Phase 4 提供一次性迁移：普通图记录可直接弃用（文件由缓存层 LRU 接管），保留 protected/downloaded |

## 8. 与现有缓存方案的关系

本方案是 [原生模式缓存系统升级方案.md](原生模式缓存系统升级方案.md) 的**性能向收口**，二者不冲突：

- 该方案 §3.1（资产/缓存/下载分类）、§6.3（URL hash key）、§8.1（复用 fcm/cni 不自研）、§14.8（不按页面复制图片）
  ——本方案把这些**从"图片分类账本"方向，扭到"两层所有权"方向落地**，并明确缓存层零账本。
- 该方案的 Document/Snapshot 页面缓存、表情 catalog、storage accounting 不受影响，继续在 `features/cache`。
- 若两份方案的实施顺序冲突，**本方案 Phase 0~3（纯性能）优先**，Phase 4（拆层）与该方案的图片 role 补全二选一对齐后再动。

## 9. 总览：改完后的样子

- `main.dart` 一处设运行时解码预算；显示按尺寸降采样——来回滑不再重载。
- `AppImage` 一个控件、自食其力——封面边滑边出，不等队列。
- `ImagePrefetcher` 一个预取器、只重排不清空——快滑不再自我取消。
- 缓存层零账本、URL key、LRU——简单、够快、同 URL 不重复落盘。
- 资产层独立、SQLite 权威——用户下载和自定义封面被干净保护，删除精确。
- "数据与存储"只剩用户看得懂的两三类。

> 一句话：**缓存层变笨，资产层变纯，显示层自立。** 性能与可维护性同时拿到，而且没丢任何用户真正在意的数据。
