# 小说阅读器分页算法重构与性能优化方案

> 状态：Phase A/B/C/D/E 已完成（2026-07-20）；Phase F 待实施
>
> 编写日期：2026-07-20
>
> 适用范围：小说阅读器 HTML-first 分页的页片模型、图片隔离、文本填充、真实测量、视口计算、缓存和性能优化
>
> 关联方案：docs/小说阅读器全新分页阅读模式分阶段实施方案.md

## 1. 结论先行

当前分页已经具备 HTML-first 的正确架构方向，但页片算法和测量实现仍然偏保守、偏昂贵：

- 分页 surface 固定扣除 constraints.maxHeight * 0.18 作为底部预留，即使底部菜单不可见也会保留这段空间。
- page breaker 在 flow unit 不适合当前页时直接 flush 当前 buffer；如果后续是不可拆分组件，当前页剩余高度只能被浪费。
- 真实测量适配器每次候选测量都创建新的 OverlayEntry，重新构建 ForumHtmlWidgetPostRenderer，等待 Flutter frame，再读取 RenderBox 高度并销毁 overlay。
- 长文本的二分切分会重复测量包含完整前缀的候选 HTML，导致测量次数和 HTML widget 构建成本快速增长。

因此本方案不采用以下表面修复：

- 不只把 0.18 改成更小的常数。
- 不简单提高 maxMeasurements。
- 不用字符数估算替代 HTML-first 的视觉一致性。
- 不把所有图片和正文强行塞进同一个长 HTML widget。
- 不通过一次性构建全章 widget 来换取“准确分页”。

最终采用混合分页策略：

~~~text
prepared HTML
  -> 语义稳定的 pagination atoms
  -> 一次建立可复用的测量 session
  -> 普通文字使用增量填充和局部精确测量
  -> 普通正文图片作为独立图片页
  -> 表情/小型 inline image 保持行内
  -> 原子组件使用明确的 overflow policy
  -> 生成稳定 page fragments 和 anchor ranges
~~~

目标是同时满足：

1. 普通文字页尽可能填满，不出现算法可以避免的大段空白。
2. 普通图片不干扰前后文字排版，图片尺寸变化不导致整章页边界大范围漂移。
3. 分页过程中不为每一个候选片段重复创建和销毁 HTML renderer。
4. 分页和纵向模式继续使用同一份 prepared HTML、主题适配、图片序列和共享 renderer。
5. 阅读进度仍只来自真实可见页和显式定位，不来自测量、预加载或页面构建。

## 2. 产品行为定义

### 2.1 普通文字

- 段落、标题、引用中的普通文字按照当前可用页高连续填充。
- 一个普通段落放不下时允许在合法 HTML 边界或文本 run 边界拆分。
- 拆分后的两个片段必须保留相同的语义 anchor、文本偏移和 HTML 样式上下文。
- 不为了绝对避免孤行而产生大段空白。标题可以携带至少一行正文，但正文的剩余部分不能因为标题而永久浪费整个页面。
- 页片默认从顶部开始布局，不垂直居中正文。

### 2.2 普通正文图片

普通正文图片指共享图片序列中可读、非表情、非小型 inline image 的图片。

- 每张普通正文图片默认独占一个 page fragment。
- 图片前的文字先结束为文字页，图片后面的文字从新文字页开始。
- 图片使用 BoxFit.contain，不裁切，不因未知宽高把图片后的文字提前推入不可预测的页边界。
- 图片尺寸未知时使用稳定 fallback ratio 生成同一张图片页；真实尺寸到达后只重新计算该图片页，不能任意增加或删除文字页。
- 超过单页可视高度的长图仍保持一个逻辑图片页；如果无法完整 fit，使用明确的页内滚动或查看原图入口，并记录 oversizedImage，不能静默裁切。
- 图片页计入页码，但不计入文本字符偏移；图片的全章 readableImageIndex 保持不变。

这不是为了让每张图片“看起来更大”，而是为了隔离图片的尺寸不确定性，避免图片加载后改变前后大量文字的页边界。

### 2.3 表情和小型 inline image

- 表情、论坛 smiley 和明确标记为 inline 的小图片继续作为 inline run 留在文字流中。
- 表情不能进入普通正文图片序列，也不能单独占一整页。
- 如果 inline 图片没有可靠尺寸，使用固定的 typography-relative fallback box，不允许把高度不确定性传播到整章。

### 2.4 原子组件

表格、折叠块、视频、iframe、复杂 widget 等不能安全拆分的内容使用以下规则：

1. 当前页能容纳时放入当前页。
2. 当前页不能容纳且当前页已经有正文时，结束当前页，在下一页放置。
3. 组件本身超过单页时保留完整组件，并使用 requiresInnerScroll 或明确 overflow 状态。
4. 原子组件造成的空白必须记录原因，区分“有意隔离”与“算法未填满”。

## 3. 当前实现的具体问题

### 3.1 可用高度被固定比例侵占

当前 NovelReaderHtmlPagedSurface 使用：

~~~text
bottomChromeReserve = maxHeight * 0.18
availableHeight = maxHeight - pagePadding * 2 - bottomChromeReserve
~~~

问题在于：

- 18% 不是实际 bottom bar 高度，在小屏、大字体和横屏下误差都很大。
- 底部菜单隐藏时仍然扣除这部分空间。
- page indicator、系统安全区和 bottom menu 的占用没有被拆成可解释的具体 inset。
- 用户看到的“空白”无法判断是 chrome 预留、图片隔离、原子组件，还是分页失败。

### 3.2 page breaker 的贪心边界过粗

当前 breaker 大致是：

~~~text
尝试把完整 unit 放入 buffer
  -> 放不下
  -> flush 当前 buffer
  -> unit 可拆分则二分
  -> unit 不可拆分则创建 overflow page
~~~

它没有：

- 预先知道下一个 unit 的最小高度。
- 在合法范围内对当前页做回溯和局部重排。
- 记录当前页剩余高度和造成 gap 的结构原因。
- 区分图片硬边界和普通 atomic widget 的边界。

因此当下一单元是图片、折叠块或尺寸暂时未知的组件时，当前页可能提前结束。

### 3.3 真实测量成本过高

当前一次测量包含：

~~~text
await endOfFrame
insert OverlayEntry
build ForumHtmlWidgetPostRenderer
wait for a new frame
read RenderBox.height
remove OverlayEntry
~~~

长文本还会对同一个 unit 做最多 12 次二分测量。候选 HTML 通常包含当前 buffer 的完整前缀，所以每次测量都可能重新解析和布局大量已经确认的内容。

这会造成：

- 首次打开分页等待时间长。
- 页面数量越多，布局时间越明显。
- 快速切换字号或主题时，旧测量任务继续占用 UI isolate。
- 多个 layout key 并发时，测量 surface 和缓存更容易互相干扰。

## 4. 目标架构

### 4.1 模块边界

~~~text
NovelReaderDocument / prepared HTML
            |
            v
NovelReaderPaginationAtomExtractor
            |
            v
NovelReaderPaginationAtom[]
            |
            +--------------------+
            |                    |
            v                    v
TextLayoutMeasurer       ImagePageMeasurer
            |                    |
            +---------+----------+
                      v
          NovelReaderPaginationPlanner
                      |
                      v
          NovelReaderPaginationPlan
                      |
                      v
          NovelReaderHtmlPagedSurface
~~~

职责固定如下：

- AtomExtractor：从 prepared HTML 派生结构化分页单元，不访问 SQLite，不持有 Flutter controller。
- MeasureSession：在一个 layout key 生命周期内复用测量资源；不决定页序，不写阅读进度。
- PaginationPlanner：纯分页决策和 page fragment 生成，不持有 Widget、BuildContext 或 PageController。
- PaginationCache：只缓存可重新生成的派生 plan/metrics，不保存正文副本到 SQLite。
- PagedSurface：展示 plan、管理 PageView、处理真实可见页回调和用户交互。
- NovelReaderController：管理章节、偏好和阅读进度，不计算 HTML 页高。

### 4.2 领域模型

建议新增或重构为以下稳定模型：

~~~dart
enum NovelReaderPaginationAtomKind {
  text,
  heading,
  quote,
  image,
  inlineImage,
  atomicWidget,
  spacer,
}

enum NovelReaderImagePagePolicy {
  isolated,
  inline,
}

enum NovelReaderPageGapReason {
  none,
  isolatedImage,
  atomicWidget,
  oversizedWidget,
  chromeInset,
  unknownImageDimension,
}

final class NovelReaderPaginationViewport {
  const NovelReaderPaginationViewport({
    required this.width,
    required this.height,
    required this.topInset,
    required this.bottomInset,
    required this.pagePadding,
    required this.layoutRevision,
  });

  final double width;
  final double height;
  final double topInset;
  final double bottomInset;
  final double pagePadding;
  final int layoutRevision;
}
~~~

NovelReaderPaginationAtom 至少应保存：

- 稳定 atom ID。
- atom 类型和 breakability。
- prepared HTML fragment。
- 起止 NovelReaderTextAnchor。
- 文本长度和可拆分 range。
- 全章 readable image indices。
- image page policy。
- 与语义文档的 node identity。

NovelReaderPageFragment 应额外保存：

- usedHeight：规划时的内容高度。
- availableHeight：规划时的实际可用高度。
- gapHeight：页片底部未使用的高度。
- gapReason：空白来源。
- containsIsolatedImage：是否为图片隔离页。
- requiresInnerScroll：是否存在超出单页的原子内容。
- 全部 anchorRanges 和全章图片索引。

这样开发和测试可以直接回答“为什么这页有空白”，而不是依赖截图猜测。

## 5. 图片隔离算法

### 5.1 图片分类

图片分类必须复用现有 prepared render document 的图片序列和 ForumImageKind 语义：

~~~text
普通 readable image
  -> isolated image atom

remote smiley / sticker / inline image
  -> inlineImage atom

data URI 或无法进入可读图片序列的装饰图
  -> 按现有 HTML renderer 规则处理，不计入正文图片序列
~~~

不能通过 URL 后缀再次猜测图片类型；分类结果必须来自已有 HTML preparation/image pipeline。

### 5.2 图片页生成

对每一个 isolated image atom 执行：

~~~text
flush text buffer
create image page
start a new text buffer
~~~

图片页的高度算法：

~~~text
usableImageBox = viewport - image page padding - page chrome inset
known dimensions
  -> preserve aspect ratio + BoxFit.contain
unknown dimensions
  -> stable fallback aspect ratio
resolved dimensions later
  -> update image page metrics only
~~~

图片页必须保持稳定的逻辑页数量。尺寸更新不能把一张图片拆成多页，也不能把相邻文字重新切成完全不同的页序；如果图片确实需要内部滚动，使用固定的 overflow policy。

### 5.3 图片与文字空白的可接受边界

以下空白是有意的：

- 图片页前后的 hard boundary。
- 图片本身为了保持比例的上下留白。
- 原子组件超出页面后使用内部滚动造成的边界空间。
- 系统安全区和实际可见 bottom chrome 所需的 inset。

以下空白是算法缺陷：

- 普通文字后还有能够放入剩余高度的普通文字，却提前结束页面。
- bottom menu 隐藏时仍按大比例扣除空间。
- 图片加载前，图片高度 fallback 把前后普通文字推开。
- 测量超时后静默创建半空页。

## 6. 高效测量方案

### 6.1 MeasureSession 接口

不要让 page breaker 每次调用 OverlayEntry。新增可复用测量 session：

~~~dart
abstract interface class NovelReaderPaginationMeasureSession {
  Future<NovelReaderPaginationMeasureResult> measure(
    NovelReaderPaginationMeasureRequest request,
  );

  Future<void> dispose();
}

abstract interface class NovelReaderPaginationMeasureSessionFactory {
  NovelReaderPaginationMeasureSession create({
    required NovelReaderPreparedChapter chapter,
    required NovelReaderPaginationKey key,
  });
}
~~~

一个 session 只对应一个 paginationKey。它可以持有一个复用的 offstage measure host，但不能每个候选创建新的 overlay。

### 6.2 分层测量

采用三层测量，减少真实 HTML renderer 的调用次数：

#### 第一层：结构预估

- 解析 atom 的文本长度、字体参数、行高、可用宽度。
- 计算普通文本的粗略行数和预计高度。
- 读取图片 dimension index 或稳定 fallback ratio。
- 只用于快速决定“显然放得下/显然放不下”，不直接作为最终 page boundary。

#### 第二层：增量精确测量

- 只有满足 6.3 中安全子集条件的纯文字 atom 才允许使用 TextPainter 或等价的共享 typography layout adapter 做快速范围测量。
- 快速范围测量只负责预估和缩小候选范围，不能在没有真实 renderer 校验时直接决定最终 page boundary。
- 一个已确认的前缀不再随每次候选重新布局。
- 只有当前 atom 的边界和当前页剩余空间需要测量。
- 测量结果按 layoutKey + atomId + startOffset + endOffset 缓存。

#### 第三层：复杂 HTML 校验

- 表格、折叠、复杂引用和含 widget 的片段使用现有 ForumHtmlWidgetPostRenderer。
- 使用一个持久化的 probe host，更新候选内容后等待一次布局完成；复用 host 只减少 OverlayEntry 的创建销毁，不代表 HtmlWidget 会自动复用候选 HTML 的 BuildTree 或布局结果。
- probe 必须使用与最终页面相同的 preparedDocument、theme、ForumHtmlReaderPreferences、customStylesBuilder、customWidgetBuilder、WidgetFactory、图片 fallback 和 viewport constraints。
- 只对最终候选或结构预估不确定的片段调用，不对每一个二分候选都重新插入 overlay。

### 6.3 `flutter_widget_from_html_core` 0.17.2 约束

分页实现必须以当前锁定的 `flutter_widget_from_html_core: ^0.17.2` 的真实行为为边界，而不是把它当作带有分页 API 的 HTML 排版引擎。

#### 6.3.1 渲染模型

`HtmlWidget` 的主要流程是：

~~~text
HTML
  -> HtmlParser / DOM
  -> BuildTree / WidgetFactory
  -> RichText、WidgetSpan、Column 或 Custom Widget
  -> Flutter layout
~~~

因此必须遵守以下事实：

- `HtmlWidget` 不暴露 HTML range 到行数、行高或分页边界的公共 API。
- `WidgetFactory.buildText` 最终创建 `RichText`；图片和其它 inline widget 可能成为 `WidgetSpan`，不能用只处理文字的 TextPainter 完整替代。
- `RenderMode.column`、`RenderMode.listView` 和 `RenderMode.sliverList` 是内容容器模式，不是分页模式。`listView` 可以延迟部分 item 的显示，但不能消除 HTML BuildTree 和候选 Widget 的构建成本。
- `buildAsync` 可以把 HTML 解析放入异步流程，但 WidgetFactory 构建和 Flutter layout 仍然需要在 UI isolate 上完成。
- `enableCaching` 只缓存一个 HtmlWidget State 内的 Widget tree；候选 HTML、主题、字体或渲染触发条件变化后不能当作跨候选 metrics cache 使用。

`ForumHtmlWidgetPostRenderer` 是 Y300 的最终视觉布局权威。分页 probe 可以是它的 offstage 复用实例，但不能建立一套结果看起来相近、实际 CSS/Widget 语义不同的第二套 renderer。

#### 6.3.2 TextPainter 安全子集

TextPainter 快速路径只允许处理同时满足以下条件的 atom：

- 只包含普通文本、明确可复现的基础 inline style 和合法的文本链接。
- 不包含 `img`、`WidgetSpan`、自定义 Widget、表格、列表 marker、折叠块、代码块、复杂引用或需要独立布局的块级元素。
- whitespace、字体、字号、行高、文本方向、段落间距和对齐方式都能使用与 `ForumHtmlStylePolicy` 相同的规则生成。
- 不依赖图片解码尺寸、异步 widget、CSS layout shift 或 renderer 回调。

以下内容必须直接走真实 `ForumHtmlWidgetPostRenderer`，不能只用 TextPainter 判定分页：

- inline image、普通正文图片、表情和任何 `WidgetSpan`。
- `customWidgetBuilder` 产生的 `ForumCollapseBlock` 或其它自定义 Widget。
- 表格、列表、`pre/code`、复杂引用、flex、padding/border/background 组合和可能改变块高的 HTML。
- 需要保留 HTML 语义、链接手势、选择行为或自定义图片点击行为的片段。

安全子集的 TextPainter 结果只能作为 optimistic estimate。若真实 renderer 校验超出可用高度，必须回退到真实 range 测量并记录 `rendererValidationMismatch`，不能静默接受不同的 page boundary。

#### 6.3.3 Probe 与 WidgetFactory 生命周期

Phase C 的 MeasureSession 可以复用一个稳定的 offstage probe，但必须满足：

- 一个 session 只服务一个 paginationKey；每次候选带有 generation 和 candidate identity，迟到结果不能写入新 plan。
- probe 更新 HTML 时显式触发 HtmlWidget 的 rebuild triggers 或替换候选子树，不能假设 `enableCaching` 会识别自定义样式、图片 hint 或 WidgetFactory 状态变化。
- probe 使用与最终页面完全相同的 prepared HTML 语义、`ForumHtmlStylePolicy`、`ForumHtmlCachedImageWidgetFactory`、图片 fallback aspect ratio、dimension index 和 viewport constraints。
- 测量阶段的图片请求、图片点击、collapse 交互、链接跳转和阅读进度回调必须被禁用或变成无副作用记录；测量不能改变图片缓存拥有者或阅读状态。
- 如果复用有状态的 WidgetFactory，必须在每个候选开始前重置候选相关状态，尤其是自动图片序号；更优先使用 prepared HTML 中稳定的 readable image index。
- host 的复用目标是减少 OverlayEntry 和 element tree 的创建开销，不得把“复用 host”描述为无需重新解析或重新布局候选 HTML。

#### 6.3.4 图片几何一致性

最终页面和 probe 必须共享同一套图片几何策略：

- HTML 明确 width/height 时沿用 `ImageSource` 和现有 `AspectRatio` 语义。
- 未知尺寸时沿用 `ForumImageLayoutHint` 的 fallback aspect ratio。
- 解码尺寸导致的 layout shift 必须只更新对应图片页 metrics，不能在分页完成后把前后文字重新合并到其它页。
- 测量阶段不能因为没有传入 `ForumImageDimensionIndex`、fallback resolver 或 layout-shift policy 而使用另一种图片高度。

只有当最终页面和 probe 的图片高度策略一致时，“图片尺寸变化不改变文字页数量”这个目标才成立。

### 6.4 文本切分

普通文字不应把任意原始 HTML 字符串直接截断。建议先生成带样式上下文的 inline runs：

~~~text
HTML text node
  -> InlineRun(text, style, link, anchor, offset range)
  -> line layout
  -> page range
  -> legal HTML fragment serializer
~~~

切分优先级：

1. 段落/块边界。
2. 句子结束或自然空白边界。
3. inline run 边界。
4. 最后才允许字符级切分。

每一页只对“当前未完成的 atom”寻找最大可用范围。已确认的前序页不重复参与测量。

## 7. 分页规划算法

### 7.1 算法总览

~~~text
prepare atoms and measurements
for atom in atoms:
  if atom is isolated image:
    flush text page
    emit image page
    continue

  if atom is normal text/heading/quote:
    append as much as remaining height allows
    split only the current atom when necessary
    continue

  if atom is atomic widget:
    if it fits:
      append
    else:
      flush current page
      emit atomic page or overflow page

flush final text page
~~~

### 7.2 普通文字的贪心填充

对普通文字采用“带局部精确切分的 greedy fill”：

1. 计算当前页 remainingHeight。
2. 如果整个 atom 的预估高度小于等于剩余高度，直接加入，并在必要时做一次真实校验。
3. 如果整个 atom 放不下：
   - 若 atom 可拆分，使用当前 atom 的 line/range metrics 找到能放入剩余高度的最大范围。
   - 发出当前页片。
   - 继续从 atom 剩余范围开始下一页。
4. 如果剩余高度小于最小可读片段高度，直接结束页面，避免产生只有极短内容的页片。
5. 不对已经发出的页面重新测量。

伪代码：

~~~text
while atom has remaining range:
  estimate = measureRange(atom, offset, end)
  if estimate.height <= remaining:
    append(atom[offset..end])
    break

  splitEnd = largestRangeThatFits(
    atom,
    offset,
    end,
    remaining,
  )

  if splitEnd > offset:
    append(atom[offset..splitEnd])
    emit page
    offset = splitEnd
  else:
    if current page is not empty:
      emit page
    else:
      append minimum readable line
      emit overflow-safe page
      offset = nextOffset
~~~

二分查找只发生在当前 atom 的当前范围内，并使用同一个 MeasureSession 的缓存。安全纯文本 atom 可以先用 inline-run metrics 缩小范围；复杂 atom 或校验不一致时仍需交给真实 renderer。无论采用哪条路径，都不允许把完整的已确认前缀 HTML 在每一次候选中无界拼接并重新创建新的 renderer。

### 7.3 标题和引用

- 标题是 heading atom，尽量与其后的第一段正文保持在同页。
- 如果标题和第一行正文无法一起放入，标题可以单独位于下一页，但不为了保留完整段落而牺牲上一页的大量空间。
- 引用整体作为可拆分的结构：引用内部普通文字可拆分，引用中的图片仍按图片隔离策略处理。
- 折叠块保持现有展开/收起语义。分页阶段不把折叠内容无条件展开成普通文本，也不在未知 widget 高度时创建无限空页。

### 7.4 空白控制指标

每一个非图片页都计算：

~~~text
fullness = usedHeight / availableHeight
~~~

建议验收阈值：

- 普通文字页的 fullness >= 0.82，除非下一单元是图片或原子组件。
- fullness < 0.65 的普通文字页必须有 gapReason，并在测试中解释。
- 图片隔离页不使用普通文字页的 fullness 阈值。
- 不能通过把字体或行高压缩到用户设置之外来提高 fullness。

## 8. 视口和底部控件

### 8.1 禁止按屏幕比例扣减

不再使用 bottomChromeReserveFraction 作为长期策略。改为由共享 reader shell 提供实际 chrome metrics：

~~~dart
final class ReaderChromeInsets {
  const ReaderChromeInsets({
    required this.top,
    required this.bottom,
    required this.safeAreaBottom,
  });

  final double top;
  final double bottom;
  final double safeAreaBottom;
}
~~~

计算规则：

~~~text
bottomInset = safeAreaBottom + visibleOpaqueBottomChromeHeight
             + pageIndicatorReservedHeight
~~~

要求：

- 底部菜单隐藏时不扣除整个底部菜单高度。
- page indicator 如果是 overlay，使用其真实高度，而不是屏幕百分比。
- chrome 变化是否触发重排必须由 reader shell 明确决定。默认保持阅读 viewport 稳定，避免打开菜单导致页码整体变化。
- 设备 safe area、横屏 cutout 和系统导航栏都进入 paginationKey。

### 8.2 页片布局

- 页面内容从顶部开始，使用明确的 pagePadding。
- 不使用 Center 让短正文垂直居中。
- page indicator 使用 overlay，不把不必要的整块底部空间交给正文布局。
- 如果正文确实短，允许自然空白，但不将其与算法空白混为一谈。

## 9. 重排、图片尺寸和进度

### 9.1 Pagination key

paginationKey 至少包含：

- episode/content hash
- viewport width/height
- top/bottom chrome insets
- typography signature
- theme signature
- image dimension revision
- renderer revision
- atomization revision

### 9.2 图片尺寸更新

普通 isolated image 页应尽量保持页数量不变：

- fallback 尺寸只影响该图片页的 fit box。
- 已知尺寸到达后更新 image page metrics。
- 不让图片高度把相邻文字重新拼接到另一页。
- 如果布局必须重建，使用 anchor 恢复正文位置，并保留旧页片直到新 plan 可用。

### 9.3 进度语义

以下事件可以更新阅读进度：

- PageView 实际稳定显示某个 page index。
- 用户显式搜索、书签定位完成。
- 退出或进入后台时 flush 当前真实页。

以下事件禁止更新阅读进度：

- atom measurement。
- layout plan 生成。
- 图片尺寸回调。
- page builder 构建邻页。
- 图片预加载和解码。

图片独立页仍然是阅读器逻辑页，但不能因为图片进入缓存就把它视为用户已经阅读。

## 10. 性能设计

### 10.1 关键指标

建议在 debug/profile 中记录以下指标，不记录正文：

~~~text
prepareDuration
atomizationDuration
measureSessionCreateDuration
textRangeMeasureCount
complexHtmlMeasureCount
imageMeasureCount
pageCount
averageTextPageFullness
lowFullnessPageCount
layoutDuration
cacheHit
cancelledPlanCount
~~~

目标值：

- 同一个 layout key 的 plan 只有一次实际计算。
- 普通文本不为每一个候选创建 OverlayEntry。
- endOfFrame 不出现在普通范围测量的热路径中。
- 安全纯文本的快速测量调用次数与文本 range 数量相关；复杂 HTML 的真实 renderer 校验次数有上限、可缓存，并且不应随所有二分候选线性增长，但不能假设它严格等于复杂 atom 数量。
- 记录 `textFastPathCount`、`rendererValidationCount` 和 `rendererValidationMismatchCount`，区分预估、真实布局和两者不一致。
- 旧 plan 在主题/字号切换后可取消或被 generation 丢弃。
- 首屏能先显示布局状态，不能阻塞应用其它页面启动。

### 10.2 缓存分层

1. PreparedChapterCache：缓存当前生命周期内的 prepared HTML 和 render document。
2. AtomMetricsCache：按 layout key、atom ID、文本 range、图片 dimension revision 缓存测量结果。
3. PaginationPlanCache：容量受限 LRU，缓存完整 plan。
4. Flutter image cache：继续使用现有 owner/protected 语义。

所有缓存都必须：

- 有容量上限。
- 在 content hash、theme、typography、viewport 或 renderer revision 变化时失效。
- 不写入 novel_episode_content、作品 metadata 或下载目录。
- 不保存 Cookie、请求头或正文以外的敏感数据。

### 10.3 并发和取消

- 相同 paginationKey 使用 single-flight。
- 不同 key 的旧任务在新 key 产生后可以取消；不能让旧任务继续占用大量 renderer 测量资源。
- NovelReaderPaginationPlanner 必须是无共享可变状态的，或者每次 plan 使用独立 run context，避免章节切换和主题切换互相覆盖。
- 迟到的 measurement result 需要携带 generation，只能写入对应 plan。
- provider dispose 时释放 measure session 和未完成任务。

## 11. 错误和降级

### 11.1 可恢复错误

- 测量超时：取消当前 plan，显示“分页计算超时”，提供重试和回到滚动。
- 图片尺寸未知：使用固定 fallback，不阻塞整章。
- 复杂 widget 过高：生成 overflow page，并允许页内滚动。
- plan cache 失效：重新规划，不读取不匹配的旧 pageIndex。

### 11.2 不允许的错误处理

- 不把失败候选当作高度 0。
- 不静默创建空白页。
- 不把超大的原子 widget 静默裁切。
- 不因图片请求失败清空文字正文。
- 不因分页失败删除阅读进度、书签或 SQLite 正文。

## 12. 接口与依赖方向

建议最终接口如下：

~~~dart
abstract interface class NovelReaderPaginationPlanner {
  Future<NovelReaderPaginationPlan> plan({
    required NovelReaderPreparedChapter chapter,
    required NovelReaderPaginationKey key,
    required NovelReaderPaginationViewport viewport,
    required NovelReaderPaginationMeasureSession measureSession,
  });
}

abstract interface class NovelReaderPaginationMeasureSessionFactory {
  NovelReaderPaginationMeasureSession create({
    required NovelReaderPreparedChapter chapter,
    required NovelReaderPaginationKey key,
  });
}
~~~

依赖规则：

- domain 不依赖 Flutter、HTML Widget、OverlayEntry 或 PageController。
- planner 只接收 atom、metrics 和 measure port，不直接创建 renderer。
- measure session 可以依赖 Flutter 和现有 HTML renderer，但不能写 repository。
- PagedSurface 不能自己计算章节顺序，也不能直接查询 SQLite。
- 阅读进度由现有 controller/committer 接收 NovelReaderPaginationPosition。

## 13. 分阶段实施顺序

### Phase A：采样和证据基线

> 状态：已完成（2026-07-20）。

目标：先知道空白来自哪里、慢在哪里。

交付：

- 增加 usedHeight/availableHeight/gapReason/fullness 诊断。
- 记录 atom 类型、单元高度、测量次数和每次测量耗时。
- 采集短章、长章、图片章、折叠章和大字号样本。
- 不改变用户行为，不先调低安全阈值。

验收：

- 任意低 fullness 页都能解释原因。
- 能区分 chrome gap、isolated image gap、atomic widget gap 和 algorithm gap。

实际交付：

- NovelReaderPageFragment 记录 usedHeight、availableHeight、gapHeight、fullness、gapReason 和 containsIsolatedImage。
- NovelReaderPaginationPlan 记录 atom 数量/类型分布、实际测量次数、累计测量耗时、文字页平均 fullness、低 fullness 页数量和 gap reason 分布。
- 每个 plan 最多保留 64 条有界测量样本。样本只包含稳定 atom ID、atom 类型、测量高度和耗时，不记录正文 HTML、Cookie、请求头或本地路径。
- 当前页面结束、图片硬边界、原子组件和现有算法提前 flush 分别标记 naturalEnd、isolatedImage、atomicWidget 和 algorithmBoundary，低 fullness 页不再只能依赖截图猜测。
- 本阶段只建立证据基线，没有提前移除每候选 Overlay 测量，也没有调整 18% chrome reserve；它们仍按计划留给 Phase C/D。

### Phase B：Atom 模型和图片隔离

> 状态：已完成（2026-07-20）。

目标：建立稳定的文本/图片/原子组件边界。

交付：

- 新增 NovelReaderPaginationAtom 和 extractor。
- 普通正文图片独立 page fragment。
- 表情保持 inline。
- 图片 fallback 尺寸不改变文字页计数。

验收：

- 一张图片前后文字页边界稳定。
- 图片尺寸从未知变为已知时，不出现大范围错页。
- 图片失败时正文仍可读。

实际交付：

- 新增 NovelReaderPaginationAtom、NovelReaderPaginationAtomKind、NovelReaderImagePagePolicy 和 NovelReaderPaginationAtomExtractor。
- extractor 只消费已有 prepared flow units 和全章 ForumHtmlReadableImageSequence。普通 readable image 从 mixed text/image HTML 中拆出独立 atom；论坛表情没有 readable index，继续留在 inline atom，不依赖 URL 后缀重新猜测类型。
- page breaker 改为消费 atom：普通图片前先 flush 文字页，图片独立生成 page fragment，图片后从新的文字页开始；图片页继续保留原始 prepared HTML、全章 readable image index、共享 renderer 和图片点击能力。
- mixed HTML 的前后文字各自保留合法 wrapper、原语义 node 和连续 text offset；图片使用独立稳定 image anchor，零长度原子 range 也能在重排后恢复到图片页。
- 已知/未知 HTML 图片尺寸都保持同样的文字页数量。尺寸只影响图片页自身的高度/overflow 诊断，不把前后文字重新并入图片页。
- 分页 renderer revision 从 1 升至 2，旧布局保存的 page index 不会被误认为属于图片隔离后的新布局；恢复继续回退到 anchor/percent。
- Phase B 没有实现 MeasureSession 或新的 greedy fill，测量性能和普通文字空白治理继续由 Phase C/D 负责。

### Phase C：可复用测量 session

> 状态：已完成（2026-07-20）。

目标：去掉每个候选一个 OverlayEntry 的热路径。

交付：

- 引入 MeasureSession 和 atom/range metrics cache。
- 普通文本候选通过 session 的 range metadata 和 metrics cache 增量复用测量。
- 复杂 HTML 复用一个 probe host。
- 任务带 generation 并可取消。

验收：

- 普通文本测量不再每次插入 overlay。
- 同一 range 第二次测量命中缓存。
- 主题/字号切换不会被旧测量结果覆盖。

实际交付：

- 新增 `NovelReaderPaginationMeasureSession` 和
  `NovelReaderPaginationMeasureSessionFactory`。page breaker 每次只为一个
  `paginationKey` 创建 session，session 结束、超时或被 dispose 时移除唯一的
  offstage `OverlayEntry`。
- `NovelReaderHtmlPaginationMeasureAdapter` 复用一个 probe host 连续测量候选，
  不再为每一个候选插入和销毁 OverlayEntry。probe 明确使用
  `ForumHtmlWidgetPostRenderer`，并关闭 `HtmlWidget` 的异步构建，避免把 loading
  widget 的高度误当成正文高度。
- 新增容量受限的 `NovelReaderPaginationMeasureCache`。缓存键包含 layout identity、
  episode、atom、range 和候选 HTML；相同候选使用 single-flight，缓存命中不会
  再触发真实 renderer 测量。`NovelReaderPaginationPlan` 和诊断记录测量请求数、
  measurement cache hit 数和样本是否来自缓存。
- 每个 probe 候选使用递增 token；旧候选的 post-frame 回调、超时回调和 dispose
  回调不能完成新候选。session dispose 会取消尚未完成的 probe 测量；coordinator
  现有 generation 仍负责拒绝迟到的旧 plan，跨 coordinator 的主动任务取消留给
  Phase E 的并发与取消收口。
- 为 `ForumHtmlWidgetPostRenderer` 增加可选的 `buildAsync` 和 `enableCaching`
  透传参数，仅测量 probe 使用同步构建和显式缓存策略，普通纵向/分页最终页面
  保持原有默认行为。
- 按 `flutter_widget_from_html_core 0.17.2` 的约束，Phase C 没有启用通用
  `TextPainter` HTML 快速路径。普通文字候选仍以共享 HTML renderer 为最终高度
  权威；TextPainter 安全子集和 greedy fill 继续留给 Phase D，并必须先通过真实
  renderer 校验。

### Phase D：文本 greedy fill 和空白治理

> 状态：已完成（2026-07-20）。

目标：提高普通文字页 fullness，同时保留合法 HTML 和可恢复 anchor。

交付：

- 当前 atom 局部切分。
- 标题/引用的最小可读规则。
- gapReason 和 fullness 约束。
- 真实 chrome inset 取代屏幕比例预留。

验收：

- 普通文字页没有可解释之外的大段空白。
- 字号、横屏、小屏和安全区下页边界稳定。
- 打开/关闭阅读菜单不会错误恢复到不同章节或末页。

实际交付：

- page breaker 不再因为完整的可拆分 atom 放不进当前页就立即 flush。它会把当前
  page buffer 一并纳入当前 atom 的局部范围测量，尽可能填满剩余高度；只有没有
  可放入的最小范围时才结束当前页并继续下一页。
- heading atom 不再被字符级切分。标题完整内容优先在当前页或下一页放置；确实
  超过单页时按原子/overflow policy 处理，不产生半个标题页。
- 保留现有 HTML renderer、wrapper、anchor range 和真实测量结果，不用压缩字号、
  行高或段间距来人为提高 fullness。分页器现有 `algorithmBoundary`、
  `isolatedImage`、`atomicWidget` 和 `naturalEnd` gap reason 继续解释有意空白。
- 新增共享 `ReaderChromeInsets`，包含 top、可见 bottom chrome、safe-area bottom
  和 page indicator reserved height。它们按实际像素进入 `NovelReaderPaginationKey`。
- 小说分页 surface 移除 `bottomChromeReserveFraction=0.18`。当前顶部/底部菜单和页码
  指示器都是 overlay，不参与正文 layout，默认 `ReaderChromeInsets.zero()`，因此
  菜单隐藏时不再固定扣除屏幕高度；未来存在真正占位 chrome 时由 reader shell
  显式传入 inset。
- 分页 surface 只在显式传入 inset 时扣除对应空间，并把 inset 放入 page padding 和
  layout key，避免同一页片在不同实际视口下错误复用。
- 搜索定位测试改为验证目标页和有效 anchor 范围，不再绑定 greedy fill 产生的某个
  固定 `node-N` 页首，避免把合法重排误判为回归。

### Phase E：性能、缓存和回归

> 状态：已完成（2026-07-20）。

目标：让长章节可以长期使用。

交付：

- prepared/metrics/plan 分层缓存。
- LRU 上限、single-flight、取消和 generation。
- profile 指标和性能基线。
- 进度只由真实可见页提交。

验收：

- 重进同一布局命中 plan cache。
- 主题、字号、viewport 改变后旧 plan 不污染新 plan。
- 长章节的测量次数和总时长显著低于当前实现。

实际交付：

- 新增 `NovelReaderPreparedChapterCache` 和
  `NovelReaderCachingHtmlPreparationService`。准备结果按正文、章节、主题、显示
  配置、来源和语义文档 hash 组成的稳定身份做容量受限 LRU；分页与滚动模式共享
  同一个页面生命周期缓存，缓存只保存可重新生成的 prepared document，不写入
  `novel_episode_content`、作品 metadata 或下载目录。
- `NovelReaderPaginationMeasureCache` 从单次 breaker 运行提升为可注入的共享
  metrics cache。页面级缓存可以跨隔离的 breaker/session 复用精确的
  layout + atom + range + candidate HTML 测量；缓存仍有固定容量，layout key
  变化不会错误命中旧尺寸。
- preparation、metrics 和 plan 三层都使用 single-flight。相同准备请求、相同
  测量候选和相同 pagination key 不会重复启动底层工作；LRU 读操作刷新最近使用
  顺序，超过容量时只淘汰最旧的派生结果。
- coordinator 增加 generation 与 cooperative cancellation。清理、重试、主题/字号
  重排和 surface dispose 会取消 pending token；支持取消的 breaker 在测量间让出并
  停止，旧 generation 即使从兼容的 legacy breaker 迟到返回也不能进入 plan cache。
  HTML breaker 每个请求使用隔离实例，避免不同 layout 并发时共享可变 page buffer。
- 诊断增加 preparation、atomization、measure-session 创建耗时，以及 renderer
  validation、fast-path 和 mismatch 计数。当前仍以共享 HTML renderer 为唯一高度
  权威，因此 `textFastPathCount` 和 mismatch 在尚未启用安全 TextPainter 子集时为
  0；指标不会记录正文、Cookie、请求头或本地敏感路径。
- 进度提交链路没有接入上述缓存或测量回调；缓存命中、widget 构建、图片预加载、
  plan 生成和取消都不会写入阅读进度，位置仍只由真实可见页和显式定位提交。
- 自动化覆盖准备缓存 single-flight、跨 session 的 metrics 命中、旧 generation
  取消与不缓存，以及小说分页/页面回归。长章节的最终帧表现仍需 Phase F 真机
  profile 验收，不能用 widget test 的耗时替代真机结论。

## 14. 测试计划

### 14.1 Domain/service

- atom extractor 正确区分普通文字、标题、引用、普通图片、表情和原子组件。
- 普通图片总是形成独立 image page，表情不形成独立页。

### 14.2 Widget

- 计算出的实际 chrome inset 与 MediaQuery/reader shell 一致。
- 底部菜单隐藏时不扣除 18% 的固定高度。
- 页面从顶部开始，不被 Center 垂直居中。
- 普通文字页 fullness 达到目标阈值或拥有明确 gap reason。
- 图片页使用 BoxFit.contain，不裁切，不影响前后文字页。
- LTR/RTL 逻辑页码一致。
- PageView 预加载和邻页构建不写阅读进度。

### 14.3 离线和数据兼容

- 水合后的 SQLite 正文断网仍可生成 atom、plan 和 page fragment。
- 旧阅读进度没有 paginationKey 时安全降级。
- 同 layout key 恢复 page index，重排后使用 anchor/percent。
- 作品清理继续删除阅读进度和书签，不留下分页缓存脏数据。
- 不向 SQLite 写入页片 HTML 或图片字节。

### 14.4 性能验收

- 记录 1000 段文字、混合图片长章和复杂折叠章的：
  - prepare duration
  - atomization duration
  - measure count
  - complex HTML measure count
  - plan duration
  - cache hit rate
  - low fullness page count
- 首次分页、缓存命中和主题重排分别测试。
- 用 profile build 验证 UI isolate 没有长时间连续阻塞。
- 不用 pumpAndSettle 作为性能结论；需要记录真实耗时和帧表现。

## 15. Review 清单

代码 review 必须重点确认：

- 是否仍然在候选测量中反复创建 OverlayEntry。
- 是否仍然把完整 buffer HTML 拼接后进行每一次二分测量。
- 是否把 TextPainter 当成完整 HTML renderer，覆盖了 WidgetSpan、CSS margin、列表、表格或自定义 Widget。
- 是否把 HtmlWidget 的 buildAsync、enableCaching 或 RenderMode.listView 误认为分页或跨候选布局缓存。
- probe 是否与最终页面使用了不同的 ForumHtmlStylePolicy、图片 fallback、dimension index 或 WidgetFactory 状态。
- 是否仍然使用屏幕比例代替实际 chrome inset。
- 是否把普通图片错误地当作普通文字或可拆分 fragment。
- 是否把表情计入普通正文图片序列。
- 是否为提高 fullness 改变用户字号、行高或段间距。
- 是否将 measurement/build/precache 事件写入阅读进度。
- 是否让旧章节、旧 layout key 或旧 PageStorage 位置污染新 plan。
- 是否引入了第二套 HTML parser、主题或图片 renderer。
- 是否把 plan、metrics 或 HTML 写入 SQLite 正文或作品 metadata。

## 16. 完成定义

只有同时满足以下条件，算法重构才算完成：

1. 普通文字页的大段无理由空白消失，所有低 fullness 页都有明确 gap reason。
2. 普通正文图片独立成页，图片尺寸变化不会造成前后文字大范围错页。
3. 表情和 inline image 仍可正常渲染，不污染正文图片索引。
4. 分页不再为每一个候选创建和销毁 HTML overlay。
5. 长章节测量次数、布局耗时和 UI 帧阻塞显著低于当前基线。
6. prepared HTML、主题、链接、图片和缓存仍与纵向阅读共用同一条管线。
7. 分页失败有明确的重试和纵向 fallback，不显示空白假成功页面。
8. 阅读进度只来自真实可见页和显式用户定位。
9. LTR/RTL、字号、主题、窗口变化、离线正文和旧进度恢复均通过自动化测试。
10. Android/iOS 真机矩阵通过后，才允许考虑改变默认阅读模式或扩大灰度范围。
