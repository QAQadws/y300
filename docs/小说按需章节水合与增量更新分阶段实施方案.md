# 小说按需章节水合与增量更新分阶段实施方案

> 状态：Phase 0-6 已完成
> 日期：2026-07-13
> 适用范围：小说模块，以及收藏同步、统一详情页和原生帖子详情页中为小说提供的最小适配边界
> Phase 0 基线：`docs/小说按需章节水合Phase0基线与ADR.md`

## 1. 文档目的

本方案将小说链路从“收藏同步时全量抓取和解析”调整为：

1. 收藏同步复用每个收藏本来就会取得的 <code>version=4</code> 帖子详情；识别为小说后只消费首楼并建立来源元数据，不追加小说专属请求。
2. 用户第一次进入小说详情页时，才按楼主 ID 抓取全部楼主楼层并生成章节。
3. 之后详情页下拉刷新和“更新”统一执行增量同步。
4. 章节可以选择在小说阅读器中打开，或者跳转到原生帖子详情的对应楼层。

本文档固定需求关系、架构边界、领域模型、接口、存储结构、状态机、失败语义、测试矩阵和分阶段交付顺序。与以下旧文档冲突时，以本文档为新目标：

- <code>docs/小说解析流程.md</code>
- <code>docs/小说detail页下拉刷新梳理.md</code>
- <code>docs/漫画与小说同步策略优化分阶段实现方案.md</code> 中的小说部分

## 2. 需求规范化与关键决策

### 2.1 收藏同步的单次 <code>version=4</code> 详情复用

收藏模块现有的通用详情加载和分类链路保持不变：

1. 收藏同步至少使用一次默认 API <code>version=4</code> 加载每个收藏帖的通用 <code>ThreadDetailData</code>。
2. 同一份详情提供 <code>fid/typeid/tag</code> 等信息，由 <code>ThreadContentClassifier</code> 判断 comic、novel 或 forum。
3. 分类为小说后，<code>NovelFavoriteContentIngestHandler</code> 直接接收已经加载的 <code>FavoriteDetailContext.detail</code>，不得再次请求帖子详情。
4. 小说元数据 parser 只允许读取 <code>detail.posts.first</code>，提取发布者名称、发布者 ID、来源目录、简介，以及可选的首楼封面候选。
5. <code>version=4</code> 响应里的第二楼及后续楼层对小说一律忽略；这些楼层可能存在版本兼容或正文格式错误，不能用于章节生成，也不能让其解析失败阻断首楼元数据入库。

因此，新小说在收藏同步期间的网络语义是“复用收藏主链已经产生的通用详情请求，总计零个额外小说元数据请求”。通用请求的具体次数仍由 favorites 模块的同步策略决定，并继续受其 execution context/governor 管理；小说 ingest 是纯消费已加载数据的本地流程，不再需要网络执行器。

### 2.2 首次章节抓取的触发时机

新收藏小说在元数据入库后可能是 0 章节，用户无法先点击章节触发加载。因此把需求中的“第一次点击进入一个帖子”规范为：

> 用户第一次从小说书架或收藏页点击一本小说并进入 <code>NovelDetailPage</code> 时，触发该作品的首次章节水合。

详情页先展示本地已有的标题、发布者名称、发布者 UID 和简介，再显示章节加载进度。禁止在多页、700ms 节流的抓取期间长期显示全屏空白。

### 2.3 首楼目录的职责

首楼目录保留为来源元数据，但不再控制章节生成：

- 可以解析并保存来源目录，供诊断、来源核对和未来扩展。
- 目录标记仍可作为简介解析的右边界。
- 本期不把目录项渲染成章节占位项。
- 目录链接文字不再作为章节标题。
- 章节顺序和章节集合只由带 <code>authorid</code> 的楼主楼层响应决定。
- 稳定章节身份始终是 <code>tid + pid</code>。

如果未来需要展示原站目录，应增加独立的“来源目录”查看能力，不应重新耦合到章节解析主链。

### 2.4 首次抓取全部楼主楼层

首次水合取得首楼发布者 ID 后，逐页请求：

~~~text
module=viewthread
tid=<tid>
page=<page>
version=1
ppp=200
authorid=<publisherId>
~~~

必须抓取服务端确认的全部过滤后页面。页面请求严格串行，同一 run 中相邻请求在上一次完成后至少间隔 700ms。

不再使用当前 10 页上限静默截断。可以保留极高的防御上限，但达到上限必须显式失败，不能把不完整结果标记为完成。

### 2.5 章节标题

每一个有效楼主楼层对应一个章节。标题取该楼层正文的第一个有意义句子：

- 跳过空块、纯目录链接块、单独的“简介/目录”标记和论坛签名。
- 以中文或英文句末标点、连续省略号或换行为句子边界。
- 折叠多余空白。
- 最长 36 个 Unicode grapheme cluster。
- 超长时保留前 35 个 grapheme 并追加 <code>…</code>。
- 无可见文字时使用 <code>第 N 章</code>，PID 只出现在诊断或来源副标题中。

新策略不依赖目录标题、heading、章节正则或旧 PID 可见兜底标题。

### 2.6 两种章节打开模式

小说详情页提供分段模式：

- 阅读器：章节点击进入 <code>NovelReaderPage</code>。
- 原帖楼层：根据 <code>tid + pid</code> 定位并进入原生 <code>ThreadDetailPage</code>。

默认模式是阅读器。模式在小说模块内全局持久化，不为每本小说复制设置。“继续”按钮始终进入阅读器；模式只改变章节行点击行为。

原帖模式不自动标记章节已读。已读状态仍由阅读器进度或用户手动操作决定。

### 2.7 增量刷新

详情页下拉刷新和“更新”使用同一个 application service：

- 未完成首次水合：重试 initial full。
- 已完成首次水合：执行 incremental。
- 增量从上一次成功的最后一页开始重叠抓取，而不是从最后一页加一开始。
- 增量只 upsert 返回的 PID，不删除本次响应中缺席的历史 PID。
- 所有页面成功并提交后才推进 checkpoint。

## 3. 目标与非目标

### 3.1 目标

1. 收藏同步中每个收藏帖只复用既有的通用 <code>version=4</code> 详情；小说分支不追加网络请求。
2. 小说元数据只读取该详情的首楼，收藏同步不解析或持久化其余小说楼层。
3. 高成本章节抓取延迟到首次打开小说详情。
4. 所有章节水合和增量更新请求固定使用 <code>version=1</code>；<code>version=4</code> 只作为收藏通用详情的首楼元数据来源。
5. 章节抓取使用服务端 <code>authorid</code> 过滤，并在本地再次验证作者 ID。
6. 使用 <code>ppp=200</code> 抓取全部楼主楼层。
7. 章节标题统一为正文首个有意义句子。
8. PID 幂等 upsert 保留阅读进度、书签、下载和已读状态。
9. 支持阅读器和原帖楼层两种章节打开模式。
10. 后续详情刷新只抓取 checkpoint 重叠页及后续页。
11. 漫画、普通帖子、搜索和收藏列表差分逻辑不发生行为变化。

### 3.2 非目标

- 不修改漫画 catalog、当前帖、递归或搜索队列策略。
- 不修改 <code>ThreadContentClassifier</code> 的小说分类规则。
- 不把小说章节同步接入论坛搜索调度器。
- 不使用 <code>version=4</code> 的第二楼及后续楼层生成小说章节。
- 不在收藏分类完成后追加小说专属元数据请求。
- 不在每次收藏同步时刷新已经入库的小说。
- 不在本期重建小说图片离线下载能力。
- 不把首楼目录恢复成章节权威来源。
- 不为不同小说保存不同的章节打开模式。

## 4. 当前问题基线

### 4.1 首次导入存在重复和提前请求

当前新小说大致经历：

~~~text
通用收藏详情 version=4 -> 分类
  -> upsertNovelBySeed: version=1, page=1, ppp=200
  -> refreshEpisodes(full): version=1, page=1..N, ppp=200
~~~

目标改造要同时消除两类成本：收藏详情之后的小说专属重复请求，以及用户可能永远不会打开的小说所产生的全量章节抓取。

### 4.2 解析职责过重

现有 <code>NovelEpisodeDiscoveryService</code> 同时处理目录优先、楼主过滤、heading/正则标题、封面、简介、兜底标题和章节计划。目标架构应拆成：

- 来源元数据管线。
- 楼主章节同步管线。
- 章节标题策略。
- 正文渲染管线。

### 4.3 刷新入口语义不一致

- 统一小说详情页当前走增量。
- 阅读器“刷新当前章节”实际触发整书全量刷新。
- 未被当前统一页面使用的旧 controller 仍保留全量路径。

最终实现不应长期保留两套生产刷新链。

### 4.4 抓取页码不能用于原帖跳转

<code>authorid + ppp=200</code> 返回的页码是“只看楼主、每页 200 楼”的过滤页码。原生帖子详情页使用普通帖子页码，两者不是同一坐标系。

禁止把 <code>NovelEpisodeItem.sourcePage</code> 直接传给 <code>ThreadDetailPage.initialPage</code>。原帖跳转必须通过稳定的 <code>tid + pid</code> 定位真实普通页码。

## 5. 目标架构

### 5.1 端到端流程

~~~text
帖子收藏成功
  -> FavoriteSyncService 使用默认 version=4 加载通用详情
  -> 公共分类复用同一份 ThreadDetailData
  -> NovelFavoriteContentIngestHandler 接收 FavoriteDetailContext.detail
  -> NovelSourceMetadataIngestService.ingestFromFavoriteDetail
  -> NovelSourceMetadataParser 只读取 posts.first
  -> works + novel_source_state + source intro
  -> 通知小说/收藏书架
  -> 结束，不追加请求、不抓章节

首次进入 NovelDetailPage
  -> 先加载本地 header
  -> NovelChapterHydrationController.ensureHydrated
  -> NovelChapterSyncService.initialFull
  -> version=1 + ppp=200 + authorid, page=1..lastPage
  -> NovelAuthorPostEpisodeBuilder
  -> staging
  -> 原子提升为正式 episodes/content
  -> 刷新详情页

详情页下拉刷新/更新
  -> NovelChapterSyncService.incremental
  -> 从 lastCompletedAuthorPage 重叠抓取
  -> 按 PID upsert，不删除历史缺席 PID
  -> 成功后推进 checkpoint
~~~

### 5.2 分层

~~~text
presentation
  NovelDetailPage
  NovelChapterHydrationController
  NovelDetailAdapter

application
  NovelSourceMetadataIngestService
  NovelSourceMetadataRecoveryService（仅 legacy/损坏数据）
  NovelChapterSyncService
  NovelChapterOpenCoordinator

domain
  NovelSourceMetadata
  NovelChapterSyncCheckpoint
  NovelChapterTitlePolicy
  NovelAuthorPostEpisodeBuilder
  gateway/repository ports

data
  ApiNovelThreadGateway
  SqfliteNovelSourceStateRepository
  SqfliteNovelEpisodeStagingRepository
  LocalNovelRepository
  ThreadPostLocator adapter
~~~

领域层不依赖 Flutter Widget、Riverpod、Dio 或 sqflite。

### 5.3 设计模式和原则

| 模式/原则 | 用法 |
|---|---|
| SRP | 元数据、章节抓取、标题、持久化和路由分别负责 |
| DIP | service 依赖 gateway/repository 接口，不依赖 API/SQLite 实现 |
| Ports and Adapters | API、SQLite、楼层定位都是领域端口的 adapter |
| Strategy | 标题生成和章节打开模式可独立替换 |
| State Machine | 显式记录 metadataOnly、hydrating、ready、failed |
| Unit of Work | 多页结果先 staging，全部成功后短事务提升 |
| Idempotency | episodeId 只由 novelId 和 PID 构成 |
| Single-flight | 同一 novelId 的并发水合/刷新 join 同一个 run |
| Fail closed | 不完整抓取不推进 checkpoint，不标记 ready |
| Open/Closed | 共享详情页通过可选 capability 增强，漫画无需实现 |

元数据 parser 只读取收藏链路已经取得的 <code>ThreadDetailData.posts.first</code>。发布者名称和 ID 以首楼的 <code>ThreadPost.author/authorId</code> 为准；<code>sourceApiVersion</code> 在正常收藏 ingest 中必须是 4，便于诊断数据来源。parser 不遍历、验证或转换第二楼及后续楼层。

封面不是新解析主线，但为了不让优化造成现有小说封面回归，元数据 parser 可复用现有图片 source pipeline，把首楼第一张有效普通正文图作为 cover candidate。封面缓存失败不应让元数据事务失败，数据库先保存远端 URL，缓存结果后续独立回写。

### 6.2 水合状态机

~~~dart
enum NovelChapterHydrationState {
  metadataOnly,
  hydrating,
  ready,
  failed,
  legacyNeedsRebuild,
}
~~~

| 当前状态 | 事件 | 下一状态 | 说明 |
|---|---|---|---|
| metadataOnly | 首次进入详情 | hydrating | 创建 initial full run |
| legacyNeedsRebuild | 首次进入详情 | hydrating | 用新标题策略重建 |
| hydrating | 所有页成功并提交 | ready | 同时写 checkpoint |
| hydrating | 网络/解析/事务失败 | failed | 正式章节不变 |
| failed | 重试 | hydrating | 清理旧 staging 后新 run |
| ready | 下拉刷新/更新 | ready | incremental，失败只记录错误 |

应用启动发现持久化状态是 hydrating 但没有活跃 run 时，应将其视为进程中断并转成 failed，不能永久卡在 loading。

### 6.6 来源种子与章节请求 governor

收藏详情请求由 favorites 层在分类前完成，小说模块无需定义通用远端执行器。小说领域只保留中立的来源种子，以及专门约束章节页请求的 governor 端口：

~~~dart
class NovelSourceSeed {
  const NovelSourceSeed({
    required this.fid,
    required this.tid,
    this.typeid,
    this.tagName,
  });

  final String fid;
  final String tid;
  final String? typeid;
  final String? tagName;
}

abstract interface class NovelSyncRequestGovernor {
  Future<T> schedule<T>(Future<T> Function() request);
}
~~~

- 收藏通用 <code>version=4</code> 请求继续走 <code>FavoriteSyncExecutionContext</code>，小说 ingest 不接触 governor。
- 首次水合和详情增量共同使用 provider-scoped <code>NovelSyncRequestGovernor</code>，默认 cooldown 为 700ms。
- governor 只包裹 <code>loadAuthorPostsPage</code> 的实际远端动作；DOM 解析、staging 和事务不节流。
- 生产 provider 必须显式注入同一个 governor 实例，避免同时打开两本小说形成两条独立 700ms 队列。

现有位于 data models 的 <code>NovelRefreshSeed</code> 应迁移或替换为领域层中立的 <code>NovelSourceSeed</code>，避免 application service 反向依赖 data 层。

## 7. 端口与应用服务

### 7.1 语义化 NovelThreadGateway

~~~dart
abstract interface class NovelThreadGateway {
  Future<ThreadDetailData> loadAuthorPostsPage({
    required String tid,
    required String authorId,
    required int page,
    int postsPerPage = 200,
  });
}
~~~

| 操作 | 必须参数 | 禁止参数 |
|---|---|---|
| loadAuthorPostsPage | module=viewthread, tid, page, version=1, ppp=200, authorid | version=4、缺失 authorid |

provider 继续在小说模块组合。favorites 不依赖该 gateway；它只把已经加载的通用详情传给小说 ingest。

### 7.2 NovelSourceMetadataIngestService

~~~dart
abstract interface class NovelSourceMetadataParser {
  NovelSourceMetadata parseFirstPost({
    required NovelSourceSeed seed,
    required ThreadDetailData detail,
    required DateTime ingestedAt,
  });
}

abstract interface class NovelSourceMetadataIngestService {
  Future<NovelSourceMetadata> ingestFromFavoriteDetail({
    required NovelSourceSeed seed,
    required ThreadDetailData detail,
  });
}
~~~

职责：

1. 接收 <code>FavoriteDetailContext</code> 中已加载的 <code>version=4</code> 详情，禁止经由该 service 发起网络请求。
2. 只取得 <code>detail.posts.first</code>；验证首楼存在且 PID、作者 ID 可用，但不触碰其余楼层。
3. 从首楼提取 subject、publisher name/id、first PID、目录快照、简介和可选封面候选。
4. 一个事务写入 works、novel_shelf_items 和 novel_source_state。
5. 来源简介只写 source intro，不覆盖用户编辑简介。
6. 新解析 miss 不清空上一次非空来源值。
7. 记录来源 API 版本为 4；通过注入的 clock 写入 <code>ingestedAt</code>，不伪装成网络完成时间，也不持久化整份原始详情。

<code>NovelSourceMetadataParser</code> 必须是纯函数，不读取 clock、repository 或 provider；`ingestedAt` 由 service 注入，使 parser 的结果仍可确定测试。<code>NovelSourceMetadataIngestService</code> 负责编排 parser、clock 和原子写入端口。

收藏 handler 调用该 service 后只声明书架刷新 task，不再调用 <code>refreshEpisodes()</code>。

现有 <code>NovelFavoriteIngestService</code> 可以作为 favorites 与新 application service 之间的兼容 facade，但应收窄为：

~~~dart
abstract interface class NovelFavoriteIngestService {
  Future<String> upsertFromThreadDetail({
    required ThreadDetailData detail,
    String? sourceTagName,
  });
}
~~~

移除 <code>FavoriteSyncExecutionContext</code> 参数，因为该 facade 不再发出远端请求。实现只负责构造 <code>NovelSourceSeed</code>、调用 <code>NovelSourceMetadataIngestService</code> 并返回 <code>novelId</code>；不得继续调用旧 <code>upsertNovelBySeed()</code> 或 <code>refreshEpisodes()</code> 网络路径。

### 7.3 Legacy 元数据恢复边界

旧数据或损坏数据可能没有 publisherId，导致无法构造 author-filtered 请求。这不是正常收藏 ingest，应通过独立恢复用例处理：

~~~dart
abstract interface class NovelSourceMetadataRecoveryService {
  Future<NovelSourceMetadata> recover(String novelId);
}
~~~

恢复 adapter 复用现有默认帖子 JSON repository，以 <code>version=4</code> 加载第一页，并把结果交给同一个 <code>NovelSourceMetadataParser</code>。它只在 <code>publisherId</code> 缺失时运行，只消费首楼，并受明确的重试/错误 UI 控制。禁止把恢复请求隐藏进每次增量更新，也禁止回退为不带 <code>authorid</code> 的章节抓取。

### 7.4 NovelChapterSyncService

~~~dart
abstract interface class NovelChapterSyncService {
  Stream<NovelChapterSyncProgress> watchProgress(String novelId);

  Future<NovelChapterSyncResult> synchronize(
    NovelChapterSyncRequest request,
  );
}
~~~

职责和约束：

- 按 novelId single-flight。
- 注入 provider-scoped 的 700ms <code>NovelSyncRequestGovernor</code>；不同 novelId 的 run 也复用同一请求队列，避免并发打开两本小说时形成双倍请求速率。
- 第一请求立即执行，后续请求在前一请求完成后等待剩余 cooldown。
- 只节流网络，不节流 DOM 解析和 SQLite。
- 发布 preparing、fetchingPage、parsingPage、committing、completed、failed 进度。
- Widget 只订阅 run，不拥有 run；页面离开不强制取消持久化任务。

### 7.5 NovelAuthorPostEpisodeBuilder

~~~dart
abstract interface class NovelAuthorPostEpisodeBuilder {

    required int orderIndex,
~~~

### 7.6 原帖楼层路由

~~~dart

  Future<ThreadRouteTarget> resolve({
    required NovelEpisodeItem episode,
  });
~~~

流程：

1. 用 sourceTid/sourcePid 构造 <code>mod=redirect&goto=findpost</code> URL。

### 7.7 持久化 Unit of Work 端口

metadata ingest service 不应分别调用三个 repository 后假设它们天然原子。定义一个面向用例的写入端口：

~~~dart
abstract interface class NovelMetadataWriteRepository {
  Future<void> upsertMetadataSnapshot({
    required NovelSourceSeed seed,
    required NovelSourceMetadata metadata,
  });
}
~~~

SQLite adapter 在一个 transaction 中完成 works、默认书架关系和 novel_source_state 更新。

章节同步同样使用面向 run 的端口：

~~~dart
abstract interface class NovelChapterSyncRepository {
  Future<void> beginRun({
    required String runId,
    required String novelId,
    required NovelChapterSyncMode mode,
  });

  Future<void> stageEpisodes({
    required String runId,
    required List<NovelEpisodeDraft> episodes,
  });

  Future<NovelChapterSyncResult> promote({
    required String runId,
    required NovelChapterSyncRequest request,
    required NovelChapterSyncCheckpoint checkpoint,
  });

  Future<void> discardRun(String runId);
}
~~~

application service 不拼 SQL，也不跨网络持有 transaction。repository adapter 负责 staging 清理、正式表提升和 checkpoint 原子提交。

## 8. 网络与分页策略

### 8.1 收藏同步

~~~text
GET api/mobile/index.php
  ?module=viewthread
  &tid=<tid>
  &page=1
  &version=4
~~~

这是收藏同步对所有候选收藏执行的既有通用详情请求，不是小说模块新发的请求。分类结果为小说时，handler 将同一个 <code>ThreadDetailData</code> 对象交给元数据 ingest；不得再次调用 gateway、repository 或 API client。

该请求继续使用收藏 run 现有 governor 和 request kind。迁移完成后，若 <code>novelSeedDetail</code>/<code>novelEpisodePage</code> 仅服务于旧收藏小说抓取，应删除其生产调用点；不要改名制造一个实际不存在的小说元数据请求。

### 8.2 首次全量水合

~~~text
for page in 1..remoteLastPage:
  GET api/mobile/index.php
    ?module=viewthread
    &tid=<tid>
    &page=<page>
    &version=1
    &ppp=200
    &authorid=<publisherId>

  wait for the remaining 700ms cooldown
~~~

终止和防御规则：

- 优先使用 lastPage/hasMore。
- 响应页码和 next page 必须单调前进。
- 中间页为空视为异常，除非分页元数据明确确认结束。
- posts 少于 200 不能单独作为终止依据。
- 防御上限命中时显式失败，不标记 ready。
- 整页作者 ID 全部不匹配时失败。

### 8.3 增量同步

~~~text
startPage = max(1, checkpoint.lastCompletedAuthorPage)
request startPage..newLastPage
stage all returned PID drafts
promote only when every page succeeds
preserve historical PID rows absent from this run
advance checkpoint after commit
~~~

重抓最后成功页用于发现后来追加在该页末尾的新楼层。

publisherId 缺失时先执行独立的 <code>version=4</code> 首楼 metadata recovery；禁止回退为不带 authorid 的全帖抓取。

### 8.4 元数据刷新边界

普通章节 incremental 不额外请求 page=1 metadata，避免每次更新都增加一条固定请求。元数据写入或重新取得只允许发生在以下边界：

- 首次收藏入库：复用该轮收藏同步已经取得的 <code>version=4</code> 详情，不追加请求。
- legacy 数据或损坏数据缺少 publisherId：显式执行一次独立 <code>version=4</code> recovery。
- 后续若明确增加并由用户主动触发“重新同步来源信息”：使用通用 <code>version=4</code> 首楼语义，并与章节 incremental 分离。

章节增量成功不会自动覆盖发布者、来源目录或来源简介；这些字段属于独立元数据管线。

## 9. 持久化设计

### 9.1 novel_source_state

小说特有状态进入独立表，不污染漫画表或通用 works：

~~~sql
CREATE TABLE novel_source_state (
  novel_id TEXT PRIMARY KEY,
  publisher_id TEXT,
  publisher_name TEXT,
  first_post_pid TEXT,
  source_intro TEXT,
  source_catalog_json TEXT NOT NULL DEFAULT '[]',
  metadata_source_version INTEGER,
  hydration_state TEXT NOT NULL DEFAULT 'metadataOnly',
  metadata_ingested_at INTEGER,
  chapters_hydrated_at INTEGER,
  last_completed_author_page INTEGER NOT NULL DEFAULT 0,
  last_seen_pid TEXT,
  last_sync_at INTEGER,
  last_error TEXT,
  FOREIGN KEY (novel_id) REFERENCES works(work_id) ON DELETE CASCADE
);
~~~

<code>source_catalog_json</code> 只是来源快照，不参与章节 SQL 查询。正常收藏 ingest 和显式 recovery 将 <code>metadata_source_version</code> 写为 4，用于证明元数据来源；legacy 迁移无法确认来源时保留 null，禁止用默认值伪造版本。该字段不是后续章节请求的版本配置。

### 9.2 novel_episode_sync_staging

网络期间不能持有 SQLite 长事务。每页解析后写 staging，全部成功后短事务提升：

~~~sql
CREATE TABLE novel_episode_sync_staging (
  run_id TEXT NOT NULL,
  novel_id TEXT NOT NULL,
  episode_id TEXT NOT NULL,
  source_tid TEXT NOT NULL,
  source_pid TEXT NOT NULL,
  author_filtered_page INTEGER NOT NULL,
  episode_title TEXT NOT NULL,
  order_index INTEGER NOT NULL,
  dateline_text TEXT,
  raw_html TEXT NOT NULL,
  plain_text TEXT NOT NULL,
  paragraph_json TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (run_id, episode_id)
);

CREATE INDEX idx_novel_episode_stage_run
  ON novel_episode_sync_staging(run_id, order_index);
~~~

提升规则：

- initialFull：upsert 全部 staging 章节，并删除该作品不在本 run 的旧章节。
- incremental：只 upsert 本 run 章节，不删除历史缺席章节。
- 正式 episodeId 不变，因此 shared 已读、书签、下载和进度保留。
- 提升和 checkpoint 更新在同一事务内。
- 失败只清理 staging，正式章节不变。
- 下次启动清理超过 24 小时的孤立 staging。

### 9.3 来源简介和用户简介

- novel_source_state.source_intro：自动解析值。
- library_work_state.intro_text：用户编辑值。
- 展示优先级：用户值 > 来源值 > 不显示。
- 自动同步永远不覆盖用户值。

### 9.4 数据库迁移

当前数据库版本为 28，建议升到 29：

1. 增量创建 novel_source_state。
2. 增量创建 staging 表和索引。
3. 已有且有章节的小说标记为 legacyNeedsRebuild。
4. 已有但无章节的小说标记为 metadataOnly。
5. works.author 可回填 publisher_name，publisher_id 首次进入时补取。
6. 禁止 28 -> 29 使用重建数据库，避免书架、进度和下载状态丢失。

## 11. 同步算法

### 11.1 initialFull

~~~text
ensure ingested metadata and publisherId exist
if publisherId is absent, run explicit version=4 first-post recovery
join existing inflight run for novelId
create runId
mark hydration=hydrating
clear stale staging for novelId

page = 1
nextOrder = 0
loop:
  governed loadAuthorPostsPage
  validate page and author identity
  sort posts in response order
  map valid posts to drafts
  stage drafts by stable PID
  stop only when pagination confirms end

short transaction:
  promote staging
  prune stale official episodes
  update checkpoint
  set hydration=ready
  delete staging

notify shelf/detail
~~~

### 11.2 incremental

~~~text
require hydration=ready
startPage = checkpoint.lastCompletedAuthorPage
nextOrder = max(existing order_index) + 1

fetch startPage..newLastPage
stage drafts

short transaction:
  existing PID -> preserve order_index, update title/content/source metadata
  new PID -> append with nextOrder
  do not delete absent old PID
  advance checkpoint
  delete staging
~~~

标题是来源派生值，楼主修改正文首句后，重叠页可以更新标题。未来若支持自定义章节标题，应增加 custom title 字段，不应通过“永远保留旧标题”混淆来源值和用户值。

### 11.3 失败语义

- 网络失败：记录 runId、mode、page 和错误类型，不推进 checkpoint。
- 中间页异常为空：失败，不把不完整结果提交。
- 作者不匹配：单条跳过并诊断；整页均不匹配则失败。
- 标题提取失败：使用顺序兜底，不中断整书。
- SQLite 提升失败：正式表和 checkpoint 一起回滚。
- 日志不保存完整 HTML、cookie、auth 或正文文本。

## 15. 性能与并发约束

1. 同一 novelId 单飞；不同小说可以有独立业务 run，但所有小说章节网络请求共享 provider-scoped governor。
2. provider-scoped governor 保证整个应用内小说 author-page 请求总速率不超过既定 700ms pacing；DOM/SQLite 仍可并行。
3. 每页请求后立即解析并写 staging，不把整书 raw HTML 长期留在内存。
4. UI 只订阅进度摘要，不保存每楼解析中间态。
5. 章节列表继续使用现有 SliverList 懒构建。
6. 700ms 只限制远端请求，不限制本地事务和 UI。

## 16. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| version=1 下 authorid 分页不稳定 | 遗漏或死循环 | 真实 fixture、页码单调验证、显式失败 |
| version=4 后续小说楼层格式异常 | 收藏导入被无关正文阻断 | 元数据 parser 只读取 posts.first，并用多楼损坏 fixture 锁定边界 |
| 楼主改名 | 名称过期 | authorId 为身份；metadata recovery 更新名称 |
| 多作者合作发帖 | 新楼层不属于原 authorId | 本期不自动合并多作者，记录明确诊断 |
| 首句不适合做标题 | 可读性下降 | 跳过标记/目录块、36 grapheme 截断 |
| 大型小说首次水合耗时 | 等待较长 | ppp=200、可见进度、staging、可重试 |
| 应用中断 | 半成品 | staging + 状态机，正式表不暴露半成品 |
| filtered page 用于原帖跳转 | 跳错楼 | 接口强制 tid+pid locator |
| 旧自动简介和用户简介无法区分 | 优先级模糊 | 保留旧 intro_text 为高优先级，新自动值只写 source_intro |

## 17. 最终验收标准

### 网络

- 每个收藏继续使用既有的通用 version=4 detail 请求；分类为小说后额外网络请求数为 0。
- 小说元数据只来自该 version=4 detail 的首楼，第二楼及后续楼层不参与解析或持久化。
- 首次详情水合全部使用 version=1/ppp=200/authorid。
- 所有 author-filtered 页被抓取，请求间隔为 700ms。

### 数据

- 详情头显示发布者名称和 UID。
- 来源目录可以保存，但不生成章节或控制标题。
- 简介优先级为用户值大于来源值。
- 每个有效楼主 PID 形成稳定章节。
- 标题来自首个有意义句子并正确省略。

### UI

- 首次进入先显示元数据和可见进度。
- 章节可在阅读器/原帖楼层间切换。
- 原帖模式按 PID 定位，不使用过滤页码。
- 下拉刷新和更新均为增量。

### 隔离

- 漫画 catalog、搜索队列和刷新策略不变。
- 普通帖子详情和分页行为不变。
- 收藏 fullDiff/incremental 列表策略不变。
- 搜索模块不增加小说任务。
- Flutter analyze 及小说、收藏、统一详情、帖子详情和漫画回归通过。
