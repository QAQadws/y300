# 原生帖子详情下一阶段最该补路线图

## 1. 文档目的

本文用于回答“当前原生帖子详情页还差什么，以及接下来最该补什么”。它不是单个 bug 修复清单，而是一份分阶段工程路线图，目标是在不推翻现有 UI 的前提下，把原生帖子详情页整理成稳定、可诊断、可扩展的论坛阅读架构。

当前已经完成的方向包括：

- 帖子详情从“一楼一个巨大组件”升级为 `ThreadDetailRenderEntry` 驱动的阅读流。
- 正文按 `postHeader` / `postBodySegment` / `postFooter` / `pagination` 拆成列表 entry。
- 长文本正文按约 600 字切 segment，阅读态不启用 `SelectionArea`。
- 长按正文提供 `选择复制` 和 `全部复制`，选择复制进入独立页面。
- 正文图片和表情已开始纳入缓存尺寸记录，并且阅读态已引入资源布局锁定策略，避免当前滚动过程中被异步尺寸回写打断。

接下来最该补的不是继续给页面增加更多开关，也不是推翻现在的 segment 架构，而是把“阅读流稳定性、资源生命周期、复制能力、图片阅读器入口、显示设置”整理成同一条可维护管线。

## 2. 总体判断：现在最缺的是什么

### 2.1 最缺一：资源展示生命周期没有完全收敛

图片和表情现在已经有缓存、尺寸记录、布局锁定，但仍需要进一步明确：

- 当前页面应该什么时候使用网络图，什么时候切本地缓存图。
- 图片从远端显示切到本地文件时是否允许触发视觉闪烁。
- 缓存尺寸何时进入 render plan，何时只记录给下一次使用。
- 表情 catalog、表情图片缓存、帖子正文表情渲染、草稿预览应如何共用同一套资源模型。

资源问题不只是“有没有缓存”，更关键是“缓存命中后是否改变当前布局和当前展示源”。

### 2.2 最缺二：RenderPlan 还没有成为唯一事实来源

目前 `ThreadPostBodyRenderPlan` 已经出现，但它还应继续承担更多派生数据：

- segment 切分结果。
- 全楼图片组。
- 图片布局 hint。
- 表情布局 hint。
- 纯文本复制快照。
- 后续繁简转换与显示设置签名。

只有这些都从同一份 plan 派生，后续图片阅读器、复制、字号调整、段距调整才不会各自重新解析 HTML。

### 2.3 最缺三：没有足够的性能诊断闭环

“某个固定位置卡顿”通常不是单一原因，可能来自：

- entry 首次 build 太重。
- 图片解码或本地/远端展示源切换。
- RichText 过长或过多。
- 滚动中触发 `setState`。
- 目标楼层定位、分页回顶、ScrollController 操作。
- 折叠组件、投票组件或其它楼尾组件重新布局。

现在靠肉眼猜成本太高。下一阶段必须补最小可用的诊断工具，让问题可以被记录和复现。

### 2.4 最缺四：复制、阅读、图片阅读器需要明确分工

阅读页的首要目标是流畅；复制页的首要目标是可选择；图片阅读器的首要目标是沉浸和资源预取。三者不应互相拖累。

建议保持：

- 阅读页：lazy segment，禁用正文选择系统。
- 复制页：单楼完整正文，一次性渲染，启用 `SelectionArea`。
- 图片阅读器：从 render plan 的图片组进入，不依赖 widget 树临时拼接。

## 3. 核心设计原则

### 3.1 阅读态优先稳定

阅读态中已经构建出来的 entry 不应因为异步资源结果改变高度。图片和表情可以记录真实尺寸，但默认只服务下一次构建或下一次打开。

### 3.2 原始数据、语义数据、显示数据分层

建议继续保持这条链路：

```text
raw HTML
  -> ThreadPostBodyDocument
  -> normalized document
  -> ThreadPostBodyRenderPlan
  -> ThreadDetailRenderEntry
  -> Widget rendering
```

繁简转换、字号、行高、段距属于显示层设置，不应该回写到 raw HTML 或 parser 输出。

### 3.3 Widget 不拥有缓存策略

Widget 可以展示本地文件或网络图片，但不应该决定缓存过期、强制刷新、保护策略、owner/role 分类。缓存策略应放在 repository/service/cache policy 中。

### 3.4 复制能力独立于阅读性能

不要为了默认阅读页可拖选而重新引入大范围 `SelectionArea`。默认阅读页保持轻量；用户主动选择复制时再进入独立复制页面承担成本。

### 3.5 可诊断优先于继续猜

后续每个性能相关阶段都应该能回答：

- 这一屏构建了哪些 entry？
- 哪些 entry 在滚动中重建？
- 哪些资源在滚动中触发了布局变化或展示源切换？
- 这次卡顿前后是否发生了 scroll jump / animate？

## 4. 推荐目标架构

### 4.1 Domain：正文语义与渲染计划

建议把帖子正文领域模型稳定为以下方向：

```dart
  final ThreadPostBodyDocument document;
  final List<ThreadPostBodySegment> segments;
  final List<ThreadPostImageBlock> images;
  final ThreadPostImageGroup imageGroup;
  final ThreadPostPlainTextSnapshot plainTextSnapshot;
  final String settingsSignature;
  final String resourceHintSignature;

```

```dart
class ThreadPostBodySegment {
  const ThreadPostBodySegment({
    required this.index,

```

### 4.2 Domain：资源布局 hint

资源布局 hint 用于回答“首次构建时这个资源应该占多少空间”。它不是图片缓存本身，也不是展示组件状态。

```dart
enum ThreadResourceLayoutHintSource {
  htmlAttribute,
  cachedDimension,
  smileyCatalog,
  contentDefault,
}

class ThreadBlockImageLayoutHint {
  const ThreadBlockImageLayoutHint({
    required this.aspectRatio,
    required this.source,
    required this.lockForCurrentBuild,
  });

  final double aspectRatio;
  final ThreadResourceLayoutHintSource source;
  final bool lockForCurrentBuild;
}

class ThreadInlineImageLayoutHint {
  const ThreadInlineImageLayoutHint({
    required this.width,
    required this.height,
    required this.source,
    required this.lockForCurrentBuild,
  });

  final double width;
  final double height;
  final ThreadResourceLayoutHintSource source;
  final bool lockForCurrentBuild;
}
```

设计要求：

- 阅读态使用 `lockForCurrentBuild = true`。
- 复制页可以使用更精确但可能更重的策略。
- 未知正文大图使用 7/10 漫画比例占位。
- 表情优先使用 HTML 尺寸或 smiley catalog 尺寸；未知尺寸不要在阅读态异步改行高。

### 4.3 Domain：图片阅读器入口

为后续点击帖子图片进入自制阅读器预留统一请求模型：


帖子详情页只构造 request，不实现阅读器缓存策略。

### 4.4 Data / Cache：资源尺寸与展示源

建议明确两个接口：

```dart
abstract class ThreadResourceDimensionRepository {
  Future<ThreadImageDimension?> getByCacheKey(String cacheKey);

  Future<void> recordResolvedDimension({
    required String cacheKey,
    required int width,
    required int height,
  });
}
```

```dart
abstract class ThreadImageDisplaySourceResolver {
  Future<ThreadImageDisplaySource> resolve({
    required ImageCacheRequest request,
    required ThreadImageDisplayPolicy policy,
  });
}
```

```dart
class ThreadImageDisplaySource {
  const ThreadImageDisplaySource.local(this.path);
  const ThreadImageDisplaySource.remote(this.url);

  final String value;
}

enum ThreadImageDisplayPolicy {
  preferExistingLocal,
  remoteThenCacheForNextOpen,
  localOnlyIfReadyBeforeBuild,
}
```

关键点：

- 避免“先显示远端图，缓存完成后立刻切本地图”导致闪烁。
- 阅读态建议采用 `localOnlyIfReadyBeforeBuild` 或“当前 widget 生命周期不切换展示源”策略。
- 缓存写入可以继续发生，但展示源切换要有明确策略。

### 4.5 Presentation：Entry/Segment 渲染边界

阅读页继续使用：

```text
ListView.builder
  postHeader
  postBodySegment
  postFooter
  pagination
```

约束：

- `ThreadDetailContent` 负责持有页面级 render plan cache。
- `ThreadPostBodySegmentView` 只渲染当前 segment。
- `ThreadPostBodySegmentView` 不做 HTML parse，不做 normalize，不做缓存策略判断。
- 图片点击、链接点击、长按复制通过 callback 上抛。
- 楼头和楼尾只出现一次，正文 segment 在视觉上拼成同一张楼卡。

## 5. 分阶段实现计划

## Phase 0：冻结当前基线与回归测试

### 目标

先把当前“600 字 segment + 独立复制页 + 阅读态资源布局锁定”作为基线固定下来，避免后续优化时反复回退。

### 主要工作

- 保留 `ThreadDetailRenderEntry` 架构。
- 保留阅读页禁用 `SelectionArea`。
- 保留长按正文进入复制动作抽屉。
- 保留 `ThreadPostResourceLayoutPolicy.lockedForReading`。
- 补齐关键测试名，使后续失败时能快速定位是阅读、复制、图片、表情还是分页回顶。

### 验收

- 长文本楼只在滚动到后续 segment 时构建。
- 默认阅读页没有 `SelectionArea`。
- 选择复制页可以单楼跨块选择。
- 多图 block 不因缓存尺寸异步返回改变当前高度。

## Phase 1：收敛图片展示源切换，解决闪烁

### 为什么最该补

即使高度不变，图片仍可能因为“远端图显示 -> 缓存完成 -> 本地文件显示”发生短暂闪烁。这个问题属于展示源生命周期，不应靠页面层反复修补。

### 主要工作

- 为 `CachedLibraryImage` 或其上层新增 display source policy。
- 阅读态资源在当前 widget 生命周期中确定一次展示源：
  - 如果首次构建前已有本地文件，显示本地。
  - 如果没有本地文件，显示远端，并在后台写缓存。
  - 写缓存成功不立刻切换当前 widget 的展示源。
- 非阅读态、书架封面等场景可以继续使用本地优先策略。

### 建议接口

```dart
class CachedLibraryImageDisplayPolicy {
  const CachedLibraryImageDisplayPolicy({
    required this.switchToLocalAfterRemoteResolved,
    required this.preferLocalOnFirstBuild,
  });

  static const reading = CachedLibraryImageDisplayPolicy(
    preferLocalOnFirstBuild: true,
    switchToLocalAfterRemoteResolved: false,
  );

  static const defaultLibrary = CachedLibraryImageDisplayPolicy(
    preferLocalOnFirstBuild: true,
    switchToLocalAfterRemoteResolved: true,
  );

  final bool preferLocalOnFirstBuild;
  final bool switchToLocalAfterRemoteResolved;
}
```

### 测试重点

- 阅读态远端图显示后，缓存完成不会切换到本地 provider。
- 已有本地缓存时，首次构建直接使用本地。
- 书架封面等默认场景不被破坏。

## Phase 2：把资源 layout hint 前置到 RenderPlan

### 目标

减少 widget 进入视口后才各自查缓存尺寸。资源尺寸应尽量在 render plan 构建时形成 hint，widget 只消费 hint。

### 主要工作

- 新增 `ThreadPostResourceLayoutHintResolver`。
- 为 block image 和 inline image 生成 layout hint。
- render plan cache key 增加 `resourceHintSignature`。
- hint resolver 可以异步读取缓存尺寸，但结果进入 plan 后保持不可变。

### 建议接口

```dart
class ThreadPostResourceLayoutHintResolver {
  const ThreadPostResourceLayoutHintResolver({
    required this.dimensionRepository,
    required this.smileyCatalogRepository,
    this.defaultBlockImageAspectRatio = 0.7,
  });

  Future<ThreadBlockImageLayoutHint> resolveBlockImage(
    ThreadPostImageBlock image,
  );

  Future<ThreadInlineImageLayoutHint?> resolveInlineImage(
    ThreadPostInlineImage image,
  );
}
```

### 边界

- 不在每个 image widget 内主动查尺寸。
- 不为了等 hint 阻塞首屏太久；可以先用默认 hint，下一次打开再用缓存 hint。
- 不把 hint 写回 parser model。

## Phase 3：RenderPlan 生命周期与缓存失效策略

### 目标

让帖子正文 parse、normalize、segment、hint 合成只在必要时发生。

### 建议缓存 key

```dart
class ThreadPostBodyRenderPlanCacheKey {
  const ThreadPostBodyRenderPlanCacheKey({
    required this.tid,
    required this.pid,
    required this.messageHash,
    required this.renderSettingsSignature,
    required this.resourceHintSignature,
  });

  final String tid;
  final String pid;
  final String messageHash;
  final String renderSettingsSignature;
  final String resourceHintSignature;
}
```

### 失效条件

- 当前页帖子列表替换。
- post message 改变。
- 字号、行高、段距、繁简转换模式改变。
- 主动刷新资源 hint。

### 不应失效

- 图片加载成功。
- 图片尺寸写入缓存。
- 评分/点评/投票折叠。
- 收藏、回复、评分提交状态变化。

## Phase 4：滚动诊断工具

### 目标

把“某个固定位置卡顿”从主观感受变成可复制日志。

### 建议事件模型

```dart
class ThreadDetailDiagnosticEvent {
  const ThreadDetailDiagnosticEvent({
    required this.time,
    required this.type,
    this.entryKey,
    this.pid,
    this.scrollOffset,
    required this.message,
  });

  final DateTime time;
  final ThreadDetailDiagnosticEventType type;
  final String? entryKey;
  final String? pid;
  final double? scrollOffset;
  final String message;
}

enum ThreadDetailDiagnosticEventType {
  entryBuild,
  renderPlanCreate,
  imageDisplaySourceSelected,
  imageDimensionRecorded,
  inlineImageHintSelected,
  scrollJump,
  scrollAnimate,
  targetPostScroll,
}
```

### UI 入口

更多页增加开发诊断开关：

- 帖子详情滚动诊断。
- 显示当前页面诊断日志。
- 一键复制诊断日志。

### 验收

当用户反馈某个位置卡顿时，可以拿到：

- 卡顿附近正在构建的 entry。
- 是否发生图片展示源切换。
- 是否发生 scroll jump/animate。
- 是否发生 render plan 重建。

## Phase 5：复制能力语义完善

### 目标

复制能力保持独立页面，不影响阅读性能；同时提高纯文本复制结果质量。

### 纯文本规则

- 普通文本按 block 顺序拼接。
- quote 前后保留换行，后续可配置引用前缀。
- 链接优先复制显示文本，显示文本为空时复制 URL。
- block 图片默认省略，可配置为 `[图片]` 或图片 URL。
- inline 表情优先复制 BBCode，其次 alt/title，最后省略。
- 编辑提示保留原文本。

### 建议接口

```dart
class ThreadPostPlainTextExtractOptions {
  const ThreadPostPlainTextExtractOptions({
    this.blockImagePolicy = ThreadBlockImageTextPolicy.omit,
    this.inlineImagePolicy = ThreadInlineImageTextPolicy.preferBbCode,
    this.quotePolicy = ThreadQuoteTextPolicy.keepTextWithBlankLines,
  });

  final ThreadBlockImageTextPolicy blockImagePolicy;
  final ThreadInlineImageTextPolicy inlineImagePolicy;
  final ThreadQuoteTextPolicy quotePolicy;
}
```

## Phase 6：图片阅读器数据入口

### 目标

先打通数据入口，不急着实现阅读器 UI。

### 主要工作

- `ThreadPostBodyRenderPlan` 产出 `ThreadPostImageGroup`。
- 点击图片时传递 `ThreadImageOpenRequest`。
- request 包含 tid、pid、postNumber、referer、cacheKey、initialIndex。
- 阅读器未来通过 request 读取本地缓存、触发预取、记录进度。

### 验收

- 任意 segment 中点击图片，都能拿到全楼图片组。
- 图片 index 不因 segment 拆分而错乱。
- 同作者连续楼层合并图片的现有行为需要明确归属：是帖子详情聚合策略，还是阅读器入口策略。

## Phase 7：繁简转换与显示设置

### 目标

接入繁简转换、字号、行高、段距，但不污染 parser 和原始 HTML。

### 建议模型

```dart
class ThreadPostBodyRenderSettings {
  const ThreadPostBodyRenderSettings({
    this.fontSize,
    this.lineHeight,
    this.paragraphSpacing,
    this.blockSpacing,
    this.conversionMode = ThreadTextConversionMode.none,
  });

  final double? fontSize;
  final double? lineHeight;
  final double? paragraphSpacing;
  final double? blockSpacing;
  final ThreadTextConversionMode conversionMode;

  String get signature;
}
```

### 实现策略

- 繁简转换作为 display transformer。
- render settings signature 进入 render plan cache key。
- 设置变更后重新生成显示 plan，但不改 raw HTML。
- 复制纯文本可以选择复制原文或显示转换后的文本，默认建议先复制原文，后续再加设置。

## Phase 8：资源预取重新评估

### 目标

在滚动诊断、展示源策略和图片阅读器入口稳定后，再判断是否需要重新引入资源预取。当前帖子详情阅读页不保留预热队列，也不在 body segment 构建时顺带调度后台加载。

### 策略

- 先通过诊断日志确认卡顿不是由正文 build/layout、图片展示源切换或 scroll jump 引起。
- 如果后续确实需要预取，应从图片阅读器或明确的视口窗口出发重新设计，而不是恢复旧的帖子详情 preload queue。
- 预取只能做低优先级文件缓存，不参与当前 widget 的尺寸回写和展示源切换。
- 滚动速度快、内存压力高、页面离开或切页时必须停止预取。
- 超长图不做滚动期间主动解码，只允许提前拿到文件或 metadata。

### 接口方向

暂不定义新的 public API。下一次实现时应先补诊断指标和验收条件，再选择放在图片阅读器、cache service 还是帖子详情 presentation adapter 中。

## Phase 9：缓存系统与数据存储页联动

### 目标

让帖子正文图片、表情、头像、HTML snapshot、解析 snapshot 在“数据与存储”中有清晰分类。

### 分类建议

- forum html document cache
- forum parsed snapshot cache
- thread inline images
- remote smiley images
- avatars
- library covers
- comic pages
- novel inline images
- drafts
- downloads

### 原则

- 下载内容和用户书架状态不是普通缓存。
- 表情 catalog 属于长期远端能力缓存，不使用 assets 兜底。
- 表情图片可以低淘汰优先级，因为发帖预览和帖子阅读都频繁使用。

## 6. 推荐执行顺序

最推荐的实际顺序是：

1. `Phase 1`：先修图片展示源切换，解决闪烁。
2. `Phase 2`：把资源 layout hint 前置到 render plan。
3. `Phase 4`：补滚动诊断工具，之后遇到卡顿先看日志。
4. `Phase 3`：整理 render plan cache 生命周期。
5. `Phase 5`：完善复制文本语义。
6. `Phase 6`：预留图片阅读器入口。
7. `Phase 7`：接繁简转换和显示设置。
8. `Phase 8`：在稳定后重新评估是否需要资源预取。
9. `Phase 9`：并入完整缓存系统与数据存储展示。

这样安排的原因是：先稳住当前用户最能感知的阅读问题，再给未来功能补结构，不在卡顿未定位时贸然加预加载。

## 7. 每阶段通用验收要求

每个阶段都应至少满足：

- 不改变帖子详情当前主要 UI 布局。
- 不在阅读页重新启用大范围 `SelectionArea`。
- 不让图片/表情异步结果改变当前已显示 entry 高度。
- 不让 repository/cache 策略进入 widget。
- 相关测试覆盖目标行为。
- 运行必要的 `flutter test` 和 `flutter analyze`。
- 更新 `docs/开发文档.md` 顶部记录行为变化。

## 8. 当前最小下一步建议

如果只做下一步，建议做 `Phase 1：收敛图片展示源切换`。

原因：

- 这能直接改善“图片概率闪烁”的体感。
- 改动边界集中在 `CachedLibraryImage` / `LibraryCachedImage` 和帖子详情调用策略。
- 不需要推翻 segment 架构。
- 不需要新增 UI。
- 能为后续图片阅读器和可能的资源预取打下更干净的展示源模型。

完成后，再做 `Phase 2`，把尺寸 hint 从 widget 内部进一步迁移到 render plan，这样帖子详情才算真正从“边渲染边猜尺寸”升级到“先计划，再渲染”。
