# 漫画阅读器评论页分阶段实施方案

> 文档状态：分阶段实施中
> 编写日期：2026-07-19
> 适用范围：漫画阅读器、论坛帖子 API、帖子 HTML 正文渲染、共享图片阅读内核
> 当前基线：漫画阅读器已经通过 `ReaderCapability` 接入共享 `ImageReaderEngine`；论坛 API 已能解析 `viewthread` JSON 的 `postlist`、`replies` 和 `ppp`；解析模式帖子页已经具备 HTML-first 正文、主题适配、表情图片识别、头像缓存和图片预热能力。

> 当前实施进度：Phase 0、Phase 1 与 Phase 2 已完成；Phase 3 起仍待实施。

## 0. 方案摘要

本方案为漫画阅读器增加一个与来源帖子关联的评论页：

```text
漫画最后一张图片
  -> 后台尝试加载来源帖子的回帖
  -> 评论末尾内容面出现
  -> 只排除楼主首楼，保留后续所有顶层回帖
  -> 展示头像、用户名、时间和正文
  -> 正文直接复用解析模式 HTML renderer，文字、表情和正文图片均按现有规则渲染
  -> LTR/RTL 继续滑动进入下一章节
  -> 评论页显示期间预加载下一章节前几张图片
```

垂直模式与分页模式的交互不同：

```text
垂直模式
  -> 最后一张图片下方显示“查看评论”按钮
  -> 点击后把评论列表展开在当前阅读流末尾
  -> 请求失败时只提示“无法查看评论”，不破坏当前漫画阅读

LTR/RTL
  -> 最后一张图片之后追加一个逻辑末尾页
  -> 末尾页显示加载中、评论列表或失败/下一章节提示
  -> 用户继续横向滑动进入下一章节
```

本方案的关键判断是：**评论页不是一张图片，也不是一个新的普通 Flutter 路由，而是图片阅读序列中的中性末尾内容面**。因此它应通过共享阅读器的中性扩展接入，不能把漫画评论、论坛 API、评论 HTML 解析全部塞进 `ComicReaderController` 或 `ImageReaderEngine`。

本文件既是实施方案，也是阶段验收边界。已完成阶段的实现必须继续遵守本文的依赖方向；后续实施必须严格按阶段推进，并在每个阶段完成单元测试、组件测试和必要的真机验证后再进入下一阶段。

本次修订对原始需求中的图片策略作出明确更新：最初的“不渲染普通图片、只保留表情”不再作为目标；根据最新裁定，`message` 中所有正文 HTML 都直接交给现有解析模式 renderer，普通正文图片与表情均按既有规则显示。评论页只排除首楼、点评数据和帖子级操作。

## 1. 需求规范化

### 1.1 业务对象

评论页的来源是当前漫画章节的 `sourceTid`，不是漫画作品 ID，也不是章节的本地 `episodeId`：

| 对象 | 作用 | 示例 |
| --- | --- | --- |
| 漫画作品 | 组织多个章节 | `comicId` |
| 漫画章节 | 当前阅读单元 | `episodeId` |
| 来源帖子 | 漫画章节对应的论坛帖子 | `sourceTid` |
| 楼层 | 来源帖子中的一个 `postlist` 元素 | `pid` |
| 评论项 | 首楼以外、经过清洗后用于评论页展示的顶层楼层 | `pid + authorId` |

同一个作品的不同章节可能对应不同帖子，因此评论会随章节变化。评论页缓存、请求状态和展示列表必须以 `sourceTid` 与当前阅读会话为边界，不能只用 `comicId`。

### 1.2 评论筛选规则

评论页只展示来源帖子中的回帖，不展示楼主首楼：

1. 优先使用 `post.first == '1'` 判断楼主首楼。
2. 若服务端某次返回缺少 `first` 字段，则用首楼 `pid` 做兜底。
3. 不根据用户名、作者 ID 或 `position == 1` 单独判断楼主；楼主可能在多个回帖中发言，不能误删楼主的后续回帖。
4. 跨页按 `pid` 去重，避免分页边界或服务端重试造成重复评论。
5. 不把 `replies` 当作已加载评论数量。`replies` 是服务端声明的回帖总数，实际展示数量以分页合并后的有效回帖为准。
6. `replies == 0` 或过滤后没有有效回帖时，展示稳定的空状态，而不是错误状态。

给定示例中的 `replies = 39`、`ppp = 20`，如果 `postlist` 包含首楼，则完整帖子数量为 `40`，预计需要：

```text
pageCount = ceil((replies + 1) / ppp) = ceil(40 / 20) = 2
```

最终应得到最多 39 条非楼主评论。实现时仍必须同时尊重服务端的 `lastPage`、`nextPageUrl` 或实际空页结果，不能只信任一个数字。

### 1.3 评论项展示内容

每条评论只展示：

- 头像。
- 用户名。
- 发布时间文本。
- 可选的楼层序号，例如 `5#`。
- 正文内容。

明确不展示或不提供：

- 评分区域、评分按钮和评分结果。
- 点评、回复某人的操作按钮和点评列表。
- 帖子收藏、回复、分享、复制楼层链接等帖子操作。
- 评分、点评、帖子级图片阅读和图片下载入口。

“不要显示点评”指忽略 API 中的 `comments`、`commentcount` 等楼中楼点评数据，只取顶层 `postlist` 楼层。评论正文中的普通文本、链接、表情和图片属于该楼的 `message`，交给现有 HTML renderer 按正文规则显示；评论页不额外增加点评或回复操作。

评论页不新增“什么是表情包”的判断逻辑。表情、普通正文图片和其它 `message` 中可渲染的 HTML 内容，统一由现有解析模式 HTML renderer 决定是否以及如何渲染。评论页本身只负责提供楼层数据、主题上下文和最小化的帖子回调。

### 1.4 头像规则

评论项不使用帖子 JSON 中可能存在的作者头像字段作为可信来源，统一根据 `authorid` 构造论坛头像地址：

```text
https://bbs.yamibo.com/uc_server/data/avatar/{a}/{b}/{c}/{d}_avatar_middle.jpg
```

其中用户 ID 先规范化为 9 位数字，再按 `3 + 2 + 2 + 2` 分组：

| `authorid` | 规范化 | 头像路径 |
| --- | --- | --- |
| `422014` | `000422014` | `000/42/20/14_avatar_middle.jpg` |
| `8` | `000000008` | `000/00/00/08_avatar_middle.jpg` |

规则要求：

- 只接受纯数字 `authorid`。
- 空 ID、非数字 ID、匿名用户或头像请求失败时使用论坛默认头像。
- 头像请求继续走 `ForumCachedAvatar` 和现有 avatar cache role。
- 头像 URL 构造器放在论坛共享/线程领域工具中，不散落在评论卡片和 controller。
- 不把用户 ID、完整头像 URL 或 Cookie 写入普通诊断日志。

### 1.5 触发时机

评论请求必须是非阻塞的：

- 分页模式中，当前逻辑图片索引到达最后一张时，触发一次当前 `sourceTid` 的评论加载。
- 进入最后一张时立即开始请求，不等待用户再次点击；这样用户继续滑动时，评论页有机会已经准备好。
- 垂直模式中到达末尾按钮附近时可以提前准备 page 1；“点击查看评论”负责展开评论面，不重复创建请求。
- 同一阅读会话、同一 `sourceTid` 只允许一个加载任务；重复 build、重复可见回调和重复点击必须复用 in-flight Future。
- 章节切换、退出阅读器或 `sourceTid` 改变时取消或使旧请求失效。
- 请求失败不改变漫画图片列表、不标记章节失败、不清空已显示的图片。

### 1.6 失败行为

| 场景 | LTR/RTL | 垂直模式 |
| --- | --- | --- |
| 正在请求 | 末尾页显示轻量加载状态 | 按钮显示加载状态且不可重复点击 |
| 成功且有评论 | 显示评论列表 | 展开评论列表 |
| 成功但无评论 | 显示“暂无评论”和下一章提示 | 展示空状态和下一章入口 |
| 无网络/HTTP 失败/解析失败 | 末尾页显示“评论暂不可用，滑动进入下一章节” | 点击后 Snackbar：“无法查看评论” |
| 可重试失败 | 允许末尾页或按钮重试，不自动高频重试 | 再次点击按钮重新请求 |
| 没有下一章节 | 显示“已是最后一章”，不创建无效跳转 | 保留现有最后章节状态 |

失败是评论能力的局部失败，不应让整个 `ComicReaderPage` 进入 error state。用户仍然可以返回、打开原帖、查看当前图片、使用显示设置和切换章节。

## 2. 当前基线与复用边界

### 2.1 现有可复用组件

当前代码已经提供以下基础设施：

- `ComicReaderPage`：漫画阅读器页面装配层。
- `ComicReaderController`：章节、图片、阅读进度、书签和章节切换业务状态。
- `ComicReaderCapability`：把漫画业务能力注入 `ImageReaderEngine`。
- `ImageReaderEngine`：共享垂直流、LTR/RTL 分页、overlay、进度、模式切换、显示设置和图片预加载。
- `ReaderContent` 与 `ContinuousImageItem`：当前图片序列模型。
- `ReaderImageSessionPreloadCoordinator`：阅读会话附近图片的缓存/解码预热。
- `ThreadRepository` / `ApiThreadRepository`：论坛 `viewthread` API 解析入口。
- `ThreadPost` / `ThreadDetailData`：`postlist`、作者、作者 ID、正文、楼层号和分页字段的现有数据模型。
- `ThreadPostBodyParser`、`ThreadPostBodyRenderPlanner` 和 HTML-first renderer：正文结构化解析与主题适配。
- `ForumImageSourcePipeline` 及现有图片请求分类：区分普通正文图片、附件图片、头像和表情。
- `ForumCachedAvatar`、`forumDefaultAvatarImage`：头像缓存和默认头像展示。
- `ThreadDetailNativePalette`、`ForumNativeSurfaceShadows`：与解析模式帖子页一致的主题和表面视觉 token。
- `TransientFeedback` / Snackbar：失败提示和一次性状态反馈。

### 2.2 复用与隔离边界

不能直接把完整解析模式帖子页（包含页面 AppBar、controller 和分页）嵌入漫画阅读器，原因如下：

- 完整帖子页包含 AppBar、分页、评分、点评、回复、收藏、原帖导航和楼层操作。
- `ThreadDetailContent` 的主体是完整帖子列表，不符合评论页独立列表的生命周期和阅读器接入边界。
- 评论页不应把评分、点评、回复、收藏和帖子级操作带入阅读器。
- 论坛详情 controller 的滚动、历史记录和帖子分页生命周期与漫画阅读会话不同。
- 直接让漫画 controller 持有 `ThreadDetailData` 会把论坛 API 细节、评论分页和阅读器章节切换耦合到一个状态对象。

Phase 2 的正确复用方式是“复用公开的单楼层卡片，关闭可选交互，再新增评论列表组合层”：

- `ComicCommentCard` 把 `ComicCommentItem` 转换为 `isFirst=false`、没有 `comments/poll/ratingSummary` 的 `ThreadPost`。
- 它直接复用 `ThreadPostCard`，所以头像、作者头部、楼层号、HTML-first 正文、主题适配和正文图片管线继续由解析模式维护。
- `ThreadPostCard` 的作者回调现在是可选的；评论传入 `null`，不会出现点击无效果的头像或用户名操作。
- `ComicCommentCard` 自己只增加 `AutomaticKeepAliveClientMixin`，列表使用 `ListView.builder` 惰性构建；不复制帖子页的楼高/正文渲染实现。
- 每条评论使用 `comic-comment-<sourceTid>-<pid>` 作为合成渲染 owner，避免每条评论的正文图片都从索引 0 开始而共享错误缓存键；资源仍使用 `threadInline`。

```text
复用：ThreadPostCard、头像、palette、surface、HTML-first 正文 renderer、阅读显示设置、API 请求基础设施
新增：评论领域模型、评论分页 loader、评论卡片、评论会话、阅读器末尾内容面
不复用：完整 ThreadDetailPage、ThreadDetailContent controller、评分/点评/回复 footer、完整帖子级操作
```

### 2.3 API 入口边界

评论需要的是 Discuz API 的 `viewthread` JSON，不应为了评论页发起 HTML 请求再解析完整网页：

```text
module=viewthread
tid=<sourceTid>
page=<page>
```

具体请求仍复用当前 `ApiClient`、Cookie、请求头和错误映射。小说的 `version=1` 约束与本方案无关，不得因为新增评论请求而修改小说请求链路。

建议为评论增加明确的 API repository 或 API adapter，使用 `ApiThreadRepository` 的解析能力，但不要让评论页面依赖当前帖子详情页所选的 HTML repository。这样可以保证“评论请求是 JSON 请求”的契约稳定，也避免 HTML-first 缓存与 API 分页混用。

## 3. 目标架构

### 3.1 分层关系

```text
reader_shared
  ReaderFlowTail / ReaderEndSurface
  ReaderSequencePosition
  ImageReaderEngine 对末尾内容面的中性编排

thread
  ThreadReplyPage API adapter
  authorid 头像 URL builder
  评论正文对现有 HTML renderer 的轻量适配
  论坛头像、主题和 HTML renderer 原子能力

comic/domain
  ComicCommentItem
  ComicCommentPage
  ComicCommentLoadState
  ComicCommentLoader 契约

comic/data
  ComicCommentApiRepository 或 ThreadReplyApiAdapter
  分页、去重、错误映射、缓存/请求复用

comic/presentation
  ComicCommentSessionController
  ComicCommentCard / ComicCommentListSurface
  ComicReaderCapability 的末尾面和下一章回调

ComicReaderController
  仍只负责章节、图片和漫画阅读状态
  通过小型 comment session port 使用评论能力
```

依赖方向必须保持：

```text
ImageReaderEngine -> reader_shared 抽象
ComicReaderCapability -> reader_shared + comic comment port
ComicCommentLoader -> forum/thread API port
reader_shared 不依赖 comic、thread 或论坛字段
```

### 3.2 领域模型

建议新增以下稳定模型。字段名称可根据现有命名规范调整，但职责不能合并。

```dart
class ThreadReplyPage {
  const ThreadReplyPage({
    required this.tid,
    required this.page,
    required this.perPage,
    required this.replyCount,
    required this.posts,
    this.lastPage,
    this.hasNext,
  });

  final String tid;
  final int page;
  final int perPage;
  final int replyCount;
  final List<ThreadPost> posts;
  final int? lastPage;
  final bool? hasNext;
}

class ComicCommentItem {
  const ComicCommentItem({
    required this.pid,
    required this.authorId,
    required this.authorName,
    required this.dateline,
    required this.floorNumber,
    required this.rawMessage,
    required this.avatarUrl,
  });

  final String pid;
  final String authorId;
  final String authorName;
  final String dateline;
  final int floorNumber;
  final String rawMessage;
  final String? avatarUrl;
}

enum ComicCommentLoadStatus {
  idle,
  loadingInitial,
  loadingMore,
  ready,
  empty,
  failed,
}

class ComicCommentViewState {
  const ComicCommentViewState({
    required this.sourceTid,
    required this.status,
    required this.items,
    required this.loadedPages,
    required this.expectedPages,
    required this.isComplete,
    this.errorMessage,

  final String sourceTid;

```

领域层不保存 `BuildContext`、`Widget`、`ScrollController`、`PageController` 或 `SnackBar`。UI 文案和显示策略由 presentation 层决定；领域层只返回稳定状态和错误码。

### 3.3 评论 repository 契约

评论请求需要支持单页获取，而不是让 UI 自己拼接 URL：

```dart
abstract interface class ThreadReplyPageRepository {
  Future<ApiResult<ThreadReplyPage>> getReplyPage({
    required String tid,
    required int page,
  });
}

abstract interface class ComicCommentLoader {
  Future<ComicCommentLoadResult> loadAll({
    required String sourceTid,
    required CancellationToken cancellationToken,
  });
}
```

`ThreadReplyPageRepository` 属于论坛数据边界，负责：

- 调用 `viewthread` API。
- 将动态 JSON 值转换为类型稳定的分页模型。
- 读取 `replies`、`ppp`、`postlist` 和服务端分页提示。
- 将 HTTP、认证、限流和解析错误转换为 `ApiFailure`。

`ComicCommentLoader` 属于评论业务用例，负责：

- 计算预期页数。
- 加载所有需要的页。
- 过滤首楼。
- 按 `pid` 去重并保持论坛顺序。
- 把 `ThreadPost` 映射为 `ComicCommentItem`。
- 处理取消、单飞、超时和局部失败。

为了避免高回复数帖子必须等到所有页面完成后才显示任何内容，loader 应允许 session controller 接收分页快照：page 1 成功后即可进入 `loadingMore` 并展示已加载评论，剩余页面在列表末尾显示轻量 loading；只有全部页面成功后才进入 `ready/isComplete=true`。后续页面失败时可以保留已加载评论，但必须显示“评论未完整加载”和重试入口，不能把局部结果伪装成完整评论。

这两个接口不能合并为一个“万能评论 service”，否则分页协议和 UI 会话状态会重新耦合。

### 3.4 头像 URL builder

建议放在 `thread/domain/services/forum_avatar_url_builder.dart` 或既有论坛共享 domain 工具中：

```dart
abstract interface class ForumAvatarUrlBuilder {
  Uri? buildMiddleAvatar(String authorId);
}
```

实现只做 ID 规范化和 URL 构造，不发网络请求，也不判断 Widget 是否已销毁。`ForumCachedAvatar` 继续负责缓存、占位图和失败回退。

### 3.5 评论正文渲染策略

评论正文直接复用现有解析模式 HTML 正文实现，不新增 `stickersOnly` 或“评论图片过滤器”。`message` 本身就是论坛返回的 HTML 正文，评论页只需要把它交给已经存在的正文组件。

优先使用现有 `ForumHtmlContentView`，而不是为了评论页构造完整的 `ThreadPostCard`：

```dart
ForumHtmlContentView(
  html: comment.rawMessage,
  sourceId: 'comic-comment-${comment.pid}',
  imageHeaderBuilder: imageHeaderBuilder,
  imageCacheOwnerId: sourceTid,
  contentImageKind: ForumImageKind.threadInline,
  theme: commentTheme,
  onOpenLink: null,
)
```

它已经负责：

- 读取 `forumHtmlReaderPreferencesControllerProvider` 中的论坛正文显示设置。
- 使用用户设置的字号缩放，当前默认字号 `1.15`。
- 使用用户设置的行高、段距、简繁转换和作者字号保留策略。
- 通过 `ForumHtmlRenderThemeFactory` 和 `ForumHtmlThemeContext` 适配浅色/深色主题。
- 复用 `ForumHtmlRenderPreparer`、`ForumHtmlWidgetPostRenderer`、图片缓存和图片尺寸布局能力。
- 复用现有表情、普通正文图片、引用、链接文本、隐藏文字和其它 HTML 语义。

因此第 6 条需求的最终裁定是：

- `message` 中的表情和普通正文图片都可以按现有正文规则渲染。
- 评论页不额外判断某个图片是不是表情包，也不因为它是普通图片就删除。
- 头像仍由评论卡片单独用 `ForumCachedAvatar` 渲染，不混入 `message`。
- 评论页不提供正文图片的图片阅读器入口、下载入口、点评入口或帖子操作；正文首先保证“能像解析模式正文一样显示”。如果后续需要评论正文图片的点击阅读，应复用现有共享图片阅读器另行裁定，不能在本阶段偷偷新增嵌套导航。
- `comments`、`commentcount` 和其它楼中楼数据完全不传给正文 renderer。
- `spoiler/concealedText` 继续遵守现有隐藏文字语义，不因评论页的主题适配而把隐藏文字强制变为可见。

这里的“复用显示设置”不是复制一份设置快照，而是让评论正文处在与解析模式帖子页相同的 Riverpod provider 作用域中。用户在“外观与文字”中修改论坛正文设置后，评论卡片应随 provider 更新重建；prepared document 的 identity 必须包含正文设置和 theme signature，避免继续使用旧字号或旧主题。

### 3.6 两套显示配置的边界

评论页会同时处在“图片阅读器”和“论坛 HTML 正文”两个显示系统中，不能把它们混成一份偏好：

| 配置 | 负责内容 | 评论页如何使用 |
| --- | --- | --- |
| `ReaderPreferences` | 阅读模式、图片适配、阅读背景、图片页间距、图片页码 | 由外层 `ImageReaderEngine` 继续负责；评论 tail 使用同一阅读背景和容器，不把评论伪装成图片，也不使用图片适配/图片页码 |
| `ForumHtmlReaderPreferences` | HTML 正文字号缩放、行高、段距、简繁转换、作者字号保留 | 由 `ForumHtmlContentView` 直接读取，评论正文和解析模式帖子正文保持一致 |
| `Theme.of(context)` / `ForumHtmlThemeContext` | 当前浅色/深色主题、正文、引用、代码块和链接颜色 | 评论卡片和 HTML body 使用与解析模式帖子页一致的主题 palette/factory |

因此，用户在解析模式正文显示设置中调整字号或行高，评论正文应立即采用新值；用户在图片阅读器显示设置中调整阅读模式或页码显示，不应把评论正文错误地当成图片页来计数。阅读背景和外层 surface 则必须跟随当前 reader，不另存一套评论专用背景偏好。

## 4. 评论请求与分页设计

### 4.1 加载流程

推荐的 `ComicCommentLoader` 流程：

```text
loadAll(sourceTid)
  -> 校验 sourceTid
  -> 先请求 page=1
  -> 读取 replies、ppp、lastPage/nextPage
  -> 计算候选总页数
  -> 用有限并发请求其余页面
  -> 每页解析并按 pid 去重
  -> 过滤 isFirst 首楼
  -> 按 page + position/number 排序
  -> 映射 ComicCommentItem
  -> 返回 ready / empty
```

page 1 不能被特殊处理成“只取评论”。它可能包含楼主和一部分回帖，必须先正常合并，再统一按楼层身份过滤。

### 4.2 页数推断

页数计算优先级：

1. 服务端明确的 `lastPage`。
2. 服务端明确的 `nextPageUrl` 链路。
3. `ceil((max(replies, 0) + 1) / max(ppp, 1))`。
4. 如果元数据不完整，则在返回页数小于 `ppp` 时停止；若刚好等于 `ppp`，继续请求下一页，直到收到空页或服务端确认无下一页。

需要防御：

- `ppp` 为 0、负数、字符串或缺失时使用安全默认值 20。
- `replies` 为负数时按 0 处理。
- 页数设置合理的上限，例如 `maxPageRequests`，上限触发时返回可诊断的 `truncated` 状态，而不是无限请求。默认上限应足够覆盖正常帖子，但不能允许异常服务端数据让应用无界发请求。
- 不使用 `ThreadDetailData.hasMore` 直接驱动全量评论，因为它面向帖子详情滚动，不能表达“首楼 + 回帖总数”的精确分页语义。

### 4.3 并发与限流

- page 1 先请求，得到总页数后再请求后续页。
- 后续页使用有限并发，建议默认 2，不要一次发出几十个 `viewthread` 请求。
- 同一个 `(sourceTid, page)` 单飞。
- 不与收藏同步、漫画刷新队列或帖子详情页面共享一个无界请求队列。
- 使用现有网络请求头、Cookie 和错误映射；不要把用户 Cookie 拼到评论 URL。
- 请求失败时保留已经成功的页，但本次“全部评论”状态应标记为失败或部分失败，不能误报完整成功。

### 4.4 去重与顺序

合并时使用 `pid` 作为唯一键：

```text
page order -> post.number/position -> pid
```

如果 `pid` 缺失，不能用作者名 + 正文作为稳定 ID；该项应被忽略并记录计数型诊断信息。评论排序默认正序，与论坛楼层顺序一致，不受漫画阅读的 LTR/RTL 影响。

### 4.5 生命周期与取消

评论会话必须有独立的 epoch 或 cancellation token：

```text
enter episode A
  -> request A
switch to episode B
  -> invalidate A
  -> request B when B reaches its end
late A response
  -> ignored; cannot update B or reopen comments
```

provider dispose、页面返回、章节切换和手动重试都要进入同一套取消/失效逻辑。任何异步回调在更新状态前必须确认：

- session 仍然 mounted。
- sourceTid 仍然一致。
- episodeId 仍然一致。
- request generation 仍然一致。

## 5. 评论页 UI 与主题

### 5.1 视觉目标

评论卡片沿用截图所示的轻量楼层结构：圆角淡色表面、左侧头像、右侧用户名/时间、右上角楼层号、下方正文。它应看起来属于帖子解析模式，但不复制完整帖子页的所有信息密度。

推荐结构：

```text
┌──────────────────────────────────────┐
│ 头像   用户名                         5# │
│        2025-09-14 23:09                  │
│                                          │
│        评论正文和表情                    │
└──────────────────────────────────────┘
```

设计约束：

- 不在卡片之间放分割线；卡片间距表达分组。
- 整行作为语义整体，不把头像、正文、楼层拆成互相独立的按钮。
- 卡片圆角和背景使用 `ThreadDetailNativePalette`，深色主题下也有明确表面层级。
- 用户名和正文必须允许换行，长用户名和超长楼层号不得溢出。
- 不使用固定高度；正文长度、表情和字体设置变化时卡片自然增高。
- 评论列表使用 `ListView.builder` 或等价惰性列表，不一次把所有 HTML widget 全部 build。

### 5.2 建议的组件边界

```text
ComicCommentListSurface
  -> 评论加载态/空态/失败态/列表态
  -> 下一章节提示或入口

ComicCommentCard
  -> surface + padding + row layout
  -> ForumCachedAvatar
  -> author/date/floor metadata
  -> ComicCommentBody

ComicCommentBody
  -> ForumHtmlContentView + 现有论坛正文显示设置
  -> 不提供图片打开回调
  -> 不提供评分/点评/回复和帖子级回调
```

`ComicCommentCard` 不应依赖 `ThreadDetailPageState`，只接收 `ComicCommentItem`、主题 palette 和必要的图片 header builder。这样它既可以在阅读器末尾测试，也可以在独立 debug fixture 中展示。

### 5.3 主题适配和文本设置

评论正文必须复用当前论坛正文主题适配策略：

- 由 `ForumHtmlThemeContext` 显式提供 surface、正文前景、链接、引用和代码块颜色。
- 深色主题检查正文颜色与背景的对比度。
- `concealedText` 只保留“故意与背景同色”的语义，不自动改成可见。
- 正文字号、行高、段距和简繁转换读取已有论坛正文偏好。
- 主题切换时评论 renderer 的 prepared document 必须按 theme signature 失效并重建。
- 正文图片、表情和文字都经过同一套主题适配；评论页不新增资源过滤策略。

### 5.4 头像和资源缓存

- 头像请求使用 `ForumCachedAvatar`，owner ID 使用纯数字 `authorId`。
- 头像失败只回退默认头像，不让评论卡片进入失败态。
- 表情走既有 `remoteSmiley`/forum inline cache role；评论页离开后由正常缓存清理策略处理。
- 正文图片按现有 `threadInline` 资源语义进入 HTML/图片缓存管线，不升级为漫画页、章节下载或用户导出资源。
- 评论内容不是漫画离线下载内容，不写入漫画章节图片表，也不改变章节下载状态。

## 6. 阅读器末尾内容面设计

### 6.1 为什么不能只复用 `verticalTrailingBuilder`

现有 `verticalTrailingBuilder` 足以把一个下一章节过场卡放在垂直图片列表末尾，但它不能完整解决本需求：

- LTR/RTL 的 `PageView` 当前 itemCount 只有图片数量，无法滑动到评论页。
- 评论页是有内部列表的内容面，不是简单的一张按钮卡片。
- 末尾面不是漫画图片，不应伪造 `ContinuousImageItem`、图片缓存键或图片页码。
- Slider、当前页、逻辑索引和末尾面的显示语义需要分离。

因此需要在 `reader_shared` 增加中性“末尾内容面”能力，而不是在 `ComicReaderPage` 外面再叠一层手势监听。

### 6.2 中性接口建议

建议新增类似以下的共享抽象，具体命名可以遵循当前 reader_shared 文件组织：

```dart
enum ReaderSequencePositionKind { image, tail, advance }

class ReaderSequencePosition {
  const ReaderSequencePosition.image(this.index)
      : kind = ReaderSequencePositionKind.image,
        tailId = null,
        advanceId = null;

  const ReaderSequencePosition.tail(this.tailId)
      : kind = ReaderSequencePositionKind.tail,
        index = null,
        advanceId = null;

  const ReaderSequencePosition.advance(this.advanceId)
      : kind = ReaderSequencePositionKind.advance,
        index = null,
        tailId = null;

  final ReaderSequencePositionKind kind;
  final int? index;
  final String? tailId;
  final String? advanceId;
}

abstract interface class ReaderTailSurface {
  String get id;

  /// Horizontal page surface for LTR/RTL.
  Widget buildPaged(BuildContext context);

  /// Vertical trailing surface. It can expose a button, an empty state or a
  /// bounded list without leaking comic/comment types into reader_shared.
  Widget buildVertical(BuildContext context);

  Future<void> onVisible();

  Future<void> onAdvance();
}
```

实际接口不应让 `reader_shared` 依赖 `ComicCommentViewState`。推荐由 `ReaderCapability` 返回 reader_shared 能识别的 `ReaderTailSurface` 或 `ReaderTailSurfaceBuilder`，评论状态和业务动作由 `ComicReaderCapability` 的闭包提供。

### 6.3 分页模式的逻辑索引

分页模式必须区分图片索引和末尾面：

- 图片逻辑索引仍为 `0..imageCount-1`。
- 评论末尾面逻辑位置为 `tail('comments:<sourceTid>')`。
- 有下一章时，评论末尾面之后追加 `advance('next:<episodeId>')` 过渡节点；没有下一章时不追加。
- 当前图片进度、章节阅读进度和 Slider 最大值仍只使用图片数量。
- 当前处于评论页时，顶部页码/进度指示器显示“评论”，不能显示虚假的 `imageCount + 1`。
- Slider 跳转仍只能跳到图片；从最后一张图片滑动才进入末尾面。
- LTR 与 RTL 只改变物理 PageView 方向，不改变 `image(index)` 和 `tail` 的逻辑顺序。
- 用户从末尾面继续滑到 advance 过渡节点时触发 `onAdvance`。过渡节点提供稳定的加载表面，成功后切换到下一章节；不通过 PageView 越界通知、overscroll 阈值或额外手写拖动手势猜测用户意图。

分页模式实际序列为：

```text
image(0) ... image(N-1) -> tail(comments) -> advance(next episode)
```

评论页内部使用垂直惰性列表，外层 PageView 只处理横向手势。需要使用 Flutter 的轴向手势仲裁并通过组件测试验证：评论上下滚动不会进入下一章，明确的横向滑动才能从 tail 到达 advance 节点。

需要扩展的 engine 状态至少包括：

```text
image(index)
tail(loading/ready/failed)
advance(idle/loading/failed)
advancingToNextEpisode
```

末尾面切换和章节切换都要有 request generation，防止上一章节的评论列表在下一章节页面出现。

### 6.4 垂直模式

垂直模式的评论面位于最后一张图片之后：

- 初始显示一个稳定高度的“查看评论”入口，避免评论请求期间改变图片布局。
- 点击后转为 loading、ready、empty 或 failed 状态。
- 评论卡片按外层阅读流顺序排列，不能在 `ListView` 中再嵌套一个无限高度的滚动 `ListView`。
- 如果评论数量可能很大，应将现有连续图片列表逐步改为可插入 tail sliver 的 `CustomScrollView`，评论卡片使用独立 `SliverList`；不要用 `shrinkWrap: true` 把所有评论一次性构建出来。
- 点击评论按钮不是图片位置 seek，不得更新漫画当前图片索引为虚假的尾页索引。
- 评论加载失败时显示 Snackbar “无法查看评论”，同时保留重试入口和下一章节能力。

### 6.5 下一章节切换

`onAdvance` 必须与现有章节切换逻辑共享同一个业务入口：

- 不在末尾面内自行查询章节数据库。
- 由 `ComicReaderController` 或独立的 `ComicReaderFlowCoordinator` 获取下一章节。
- 无下一章时显示“已是最后一章”，不创建空页面。
- 有下一章时由共享 reader 创建中性 advance 过渡节点；节点首次可见只触发一次章节切换命令。
- 有下一章时取消当前评论 session，切换 `episodeId/sourceTid`，重置 reader tail 状态。
- 新章节首帧可以复用已有预加载图片，但不能把旧章节图片状态混入新章节。
- 是否恢复下一章既有阅读进度，沿用现有漫画阅读恢复策略；“滑动进入下一章”不应绕过已有进度持久化规则。

## 7. 下一章节预加载

### 7.1 目标

当用户看到评论页时，下一章节的前几张图片应已开始进入现有预加载管线，使用户从评论页滑入下一章节时减少等待。

预加载是体验优化，不是章节下载：

| 能力 | 目的 | 是否完整章节 | 是否改变下载状态 |
| --- | --- | --- | --- |
| 评论页期间的 lookahead | 滑入下一章时减少首帧等待 | 否，只取前几张 | 否 |
| 阅读会话预加载 | 附近图片解码更快 | 否 | 否 |
| 用户明确章节下载 | 长期离线阅读 | 是 | 是 |

### 7.2 推荐接口

不要让评论卡片直接调用漫画 repository。建议由阅读器能力提供一个预加载意图：

```dart
class ReaderAdjacentPreloadRequest {
  const ReaderAdjacentPreloadRequest({
    required this.ownerId,
    required this.imageRequests,
  });

  final String ownerId;
  final List<ImageCacheRequest> imageRequests;
}

abstract interface class ReaderAdjacentPreloadSink {
  Future<void> preload(ReaderAdjacentPreloadRequest request);
}
```

漫画侧负责：

1. 找到下一章节。
2. 读取已存在的前几张图片元数据；必要时只请求下一章节图片目录，不请求整章正文。
3. 将前 `N` 张映射为现有 `ImageCacheRequest`/`ForumImageLoadSpec`。
4. 交给共享 `ReaderImageSessionPreloadCoordinator`。

不在评论功能中重新定义 `N`。应读取共享阅读器当前的相邻图片预加载窗口和并发策略；如果未来需要调整窗口，只修改共享策略，避免漫画评论页、漫画图片页和公共图片阅读器出现三个不同的“前几张”定义。

### 7.3 触发与取消

- 评论末尾页首次可见时触发一次。
- 垂直模式评论按钮成功展开时触发一次。
- 评论页请求失败也可以预加载下一章，因为两者互不依赖。
- 没有下一章时不发预加载。
- 章节切换、退出、登录态变化和新的预加载请求到来时取消旧任务或使其结果失效。
- 预加载失败不改变评论状态，不显示阻塞错误；仅进入诊断计数。
- 预加载不能触发章节已读、阅读进度、下载状态或历史记录写入。

## 8. 状态机与并发控制

### 8.1 评论会话状态

建议将评论状态从 `ComicReaderViewState` 中拆出，避免漫画图片状态每次评论加载变化都重建全部图片：

```text
Idle
  -> Preparing(sourceTid)
  -> LoadingPage(1)
  -> LoadingRemainingPages
  -> Ready(items)
  -> Empty
  -> Failed(errorCode)
```

页面显示状态由 `ComicCommentSessionController` 管理，漫画 controller 只接收：

- 当前评论尾页是否可用。
- 末尾面进入下一章节的命令。
- 预加载相邻章节的命令。

### 8.2 单飞与 generation

以下操作必须单飞：

- 同一 `sourceTid` 的评论全量加载。
- 同一 `(sourceTid, page)` 的 API 请求。
- 同一章节的下一章 lookahead 预加载。
- 同一末尾面的章节 advance。

推荐使用：

- `Map<CommentSessionKey, Future<ComicCommentLoadResult>>` 合并请求。
- `int generation` 或 `CancellationToken` 丢弃迟到结果。
- `Completer`/共享 Future 处理通知、生命周期和 UI 点击同时触发的恢复。
- dispose 时取消 subscription、timer 和 image preload task。

### 8.3 状态转换约束

- `Ready` 只表示评论页数据成功合并，不表示所有头像都下载成功。
- 头像和表情是逐项资源，失败时使用局部占位，不回滚评论列表。
- `Failed` 只表示评论 API 或评论解析失败；不能把下一章预加载失败写入评论错误。
- `Empty` 不是网络错误，应展示空状态。
- 评论页打开后再来一条迟到 API 结果，必须通过 pid 合并，而不能追加重复楼层。
- 章节切换后旧评论状态必须立即从 reader tail 脱离，不能继续显示旧 sourceTid。

## 9. 分阶段实施计划

### Phase 0：基线、样本和 ADR

目标：冻结需求语义，建立可以逐阶段验收的样本和架构决策。

工作项：

- 保存脱敏后的 `viewthread` JSON fixture，至少包含：`replies=39`、`ppp=20`、首楼、跨页回帖、表情正文、普通图片正文和异常 authorid。
- 记录 `authorid=422014` 与 `authorid=8` 的头像 URL 期望值。
- 记录 `replies=0`、`postlist=[]`、缺少 `first`、重复 `pid`、异常 `ppp` 的 fixture。
- 确认当前漫画 `sourceTid` 对应的章节切换和 reader owner key。
- 写入 ADR：评论页是 reader tail surface，不是图片、不单独打开完整帖子页、不持久化评论正文。
- 写入 ADR：评论正文直接复用 `ForumHtmlContentView` 和解析模式正文显示设置；头像独立使用 avatar cache；点评数据不进入评论正文。
- 写入 ADR：`ThreadReplyPageRepository` 与 `ComicCommentLoader` 分层。

验收标准：

- 团队可以用 fixture 明确算出 2 页、39 条有效回帖。
- 首楼、重复楼、普通图片、表情和异常头像的预期结果都有文字定义。
- 没有任何代码依赖评论 UI 去猜 `replies/ppp` 页数。

### Phase 1：论坛 API adapter 与评论领域模型

目标：在没有接入阅读器 UI 的情况下，可靠获得完整评论列表。

工作项：

- 新增 `ThreadReplyPageRepository`，固定使用 API `viewthread` JSON 请求。
- 新增 `ThreadReplyPage`，解析 `tid/page/ppp/replies/postlist` 和可用分页提示。
- 新增 `ComicCommentItem`、`ComicCommentLoadResult`、稳定错误码。

- 新增 `ForumAvatarUrlBuilder`，覆盖 422014、8、空 ID、非数字 ID。
- 增加请求单飞和 session generation。

测试：

- JSON fixture page 1 + page 2 合并后得到 39 条。
- 首楼不会因为与回帖作者相同而被错误过滤。
- 重复 pid 只保留一条。
- `replies=0` 返回 empty，不是 failure。
- page 2 失败返回 failure/partial，不能伪造 ready。
- 取消后迟到结果不会更新状态。

### Phase 2：评论卡片和现有 HTML 正文渲染接入

目标：先把评论列表做成独立、可测试的解析模式风格组件。

工作项：

- 复用 `ThreadDetailNativePalette`、论坛 surface shadow、`ThreadAuthorAvatar`/`ForumCachedAvatar` 和 `forumHtmlReaderPreferencesControllerProvider` 的现有显示设置。
- 评论正文继续经过解析模式的 HTML-first renderer；其 `message` 中的表情和普通正文图片都使用 `ForumImageKind.threadInline`，不新增图片分类策略。
- 评论卡片不挂载评分、点评、回复和帖子级操作回调；`comments/commentcount` 不参与渲染。
- 评论卡片使用 `AutomaticKeepAliveClientMixin`，列表使用 `ListView.builder`，保持帖子页已有的保活思路；阅读器尾部的滚动锚定和图片尺寸 store 仍留到后续 reader_shared 阶段接入。
- 对超长正文、换行、图片、表情、深色主题、HTML 显示设置、无操作卡片和部分失败列表做组件测试；隐藏文字继续由已有 HTML 主题适配测试负责，评论层不改写其语义。

测试：

- 视觉结构接近参考图：头像、用户名、时间、楼层号、正文层级清晰。
- `message` 中的普通图片和表情都能通过解析模式复用的 HTML-first renderer 渲染，并使用 `threadInline` 资源语义。
- 评论页不会构建点评、评分或帖子操作组件。
- `concealedText` 在深色主题下不会因为对比度修正而泄露。
- authorid 头像失败只显示默认头像。

### Phase 3：reader_shared 末尾内容面

目标：让共享图片阅读器支持中性非图片尾部内容，不引入漫画和论坛类型。

工作项：

- 增加 `ReaderSequencePosition` 和末尾 surface builder/port。
- LTR/RTL `PageView` 支持逻辑图片序列之后的 tail page。
- 垂直图片流支持稳定的 tail surface，并保留现有图片 anchor、尺寸和滚动恢复语义。
- 当前页指示器在 tail 时显示“评论/末尾内容”，Slider 仍只操作图片逻辑索引。
- RTL 只反转物理方向，不修改评论列表顺序和图片逻辑索引。
- 增加 tail visible、retry、advance 和 disposal 的中性回调。
- 保证没有 tail 时漫画和公共图片阅读器行为完全不变。

测试：

- LTR 从最后一张滑到 tail，再从 tail advance。
- RTL 同样可以到达 tail，且评论顺序不反转。
- 垂直模式 tail 位于最后图片之后，点击不修改图片索引。
- Slider 不出现 `imageCount + 1` 的伪页码。
- tail 的迟到异步结果不覆盖新的 reader owner。
- 既有公共图片阅读器和漫画 reader 测试全量回归。

### Phase 4：漫画评论会话接入

目标：在不改变漫画图片、书签、进度和章节下载语义的前提下，接入评论 tail。

工作项：

- 新增 `ComicCommentSessionController`，按 episode/sourceTid 管理评论状态。
- `ComicReaderCapability` 只通过接口/闭包提供 tail surface，不直接解析 JSON。
- 最后一张图片可见时启动评论 page 1 加载。
- 分页模式展示 loading/ready/empty/failed tail。
- 垂直模式在末尾显示“查看评论”按钮，点击后加载/展示评论。
- 失败只显示局部错误；垂直点击失败使用 Snackbar “无法查看评论”。
- 同一会话重复进入末尾时复用已加载结果，不重复发请求。
- 退出和章节切换时清理评论订阅、generation 和暂存状态。

测试：

- 最后一张触发一次请求，非最后图片不触发评论请求。
- 请求期间图片仍可操作，Reader 不进入全局 loading。
- LTR/RTL tail 失败时仍能显示进入下一章的提示。
- 垂直失败时显示 Snackbar，reader 图片状态不改变。
- sourceTid 改变后旧评论不会出现在新章节。

### Phase 5：评论页滑入下一章与共享预加载窗口

目标：实现评论页之后无缝进入下一章节，并在评论页期间预加载下一章前几张图片。

工作项：

- tail surface 可调用统一的 `advanceToNextEpisode` flow。
- LTR/RTL 从评论 tail 继续滑动时进入下一章，不需要点击额外按钮。
- 评论页首次可见或垂直评论成功展开时，复用共享阅读器现有的相邻图片预加载窗口。
- 复用 `ReaderImageSessionPreloadCoordinator`，不新增漫画私有预加载队列。
- 预加载不写入章节下载状态、不标记已读、不改变当前章节进度。
- 下一章加载失败回到明确的章节切换错误，不丢失当前评论页。
- 无下一章时显示“已是最后一章”。

测试：

- 评论 tail visible 后收到共享预加载窗口的相邻图片预加载请求。
- 同一章节重复显示评论只产生一次 lookahead 任务。
- 预加载结果能被下一章 reader session 复用。
- LTR 和 RTL 的 advance 方向都正确。
- vertical 仍能继续使用现有下一章节入口，不能被评论 tail 卡住。
- 预加载失败不影响评论列表和下一章按钮。

### Phase 6：性能、缓存和异常硬化

目标：在真实大帖子、弱网和频繁切换章节下保持稳定。

工作项：

- 对高回复数帖子使用有限并发和逐项/分页渲染，避免一次性构建全部 HTML widget。
- 将评论 API 结果限制在阅读会话内存缓存，默认短 TTL；不把评论正文写入漫画数据库。
- 头像、表情和正文图片继续由现有 HTML/图片缓存管线按各自资源语义处理。

- 在 debug 诊断中记录 tid、page、post count、filtered first count、deduplicated count、duration 和 error code，不记录正文、Cookie、token 或完整 URL。
- 检查评论页在深色主题、字号放大、系统字体和屏幕阅读器下的可用性。
- 处理 Android/iOS 低内存时 decoded image cache 被回收的情况，评论页不能依赖漫画图片仍在内存。

测试与验收：

- 39、200、1000 条回复的滚动和内存基线。
- 网络切换、断网恢复、应用切后台、章节快速切换和页面销毁。
- Android 和 iOS 至少各验证一次 LTR、RTL、垂直三种模式。
- 检查图片请求日志，确认评论正文图片使用 `threadInline` 语义，不被误记为 `comicPage`、章节下载或当前图片导出。

### Phase 7：体验收口与长期维护

目标：把评论页变成稳定的产品能力，并清理临时兼容代码。

工作项：

- 统一加载、空态、失败和下一章文案。

## 11. 诊断、性能与安全约束

### 11.1 诊断字段

debug 日志建议使用独立前缀，例如 `[ComicComments]`，只记录：

- `sourceTid` 的内部摘要或脱敏值。
- `page`、`expectedPages`、`loadedPages`。
- `rawPostCount`、`filteredFirstCount`、`deduplicatedCount`。
- `status`、`durationMs`、稳定 error code。
- `preloadCount`、`preloadDurationMs`。

禁止记录：

- 评论正文。
- Cookie、auth、formhash、token。
- 用户完整个人资料。
- 完整头像 URL（可记录 host 和分类结果）。
- 原始 API 响应。

### 11.2 性能预算

- page 1 请求不阻塞最后一张图片显示。
- 评论列表使用惰性构建，首屏只构建可见评论及小范围预取。
- 评论正文 prepared document 按 pid 和主题 signature 缓存，不因父级普通重建重复解析。
- 评论正文不额外过滤普通图片；正文资源仍由现有 HTML renderer 的准备、缓存和尺寸布局流程统一处理。
- 头像、表情和正文图片允许异步加载，单个资源失败不触发整个列表进入错误态。
- 下一章 lookahead 必须复用共享预加载窗口，不能演变成整章下载。
- 评论请求并发默认 2，必须可配置并有上限。

### 11.3 安全与内容边界

- API 返回的 HTML 只能经过现有安全 HTML renderer，不引入 WebView 执行脚本。
- 评论正文继续使用现有 HTML renderer 的资源解析和安全边界，不新增“只允许表情”的过滤器。
- 头像继续使用确定性论坛头像 URL；`message` 中的图片、表情和其它 HTML 资源是否可渲染由现有正文 renderer 决定。
- `authorid` 只用于确定性头像路径，不接受正文中的任意 URL 作为头像来源。
- 隐藏文字、剧透、concealedText 等语义保持现有行为；评论页不因为简化 renderer 而自动泄露。
- 评论不写入漫画章节正文、漫画图片表或长期下载文件。

## 12. 失败方案与取舍

### 12.1 直接打开完整帖子解析页

不采用。它会带来重复 AppBar、帖子操作、评分、图片、分页滚动和历史记录，而且无法自然表达“评论页滑入下一章”。完整帖子页仍可作为用户主动打开原帖的入口，但不是阅读器尾部内容。

### 12.2 把评论伪装成一张特殊图片

不采用。这样会污染图片总数、Slider、图片缓存键、当前页下载和阅读进度，也会让屏幕阅读器无法正确识别评论列表。

### 12.3 把评论列表直接加进 `ComicReaderViewState`

不采用。漫画图片状态和评论分页状态的更新频率、缓存生命周期和错误语义不同；混合后会导致每个评论页变化都重建图片 reader，并让 controller 变成跨领域巨型状态对象。

### 12.4 在 `ComicReaderPage` 外部加第二套 PageView

不采用。第二套手势系统会重新引入 LTR/RTL、缩放、位置恢复、键盘/无障碍和下一章节切换不一致的问题。末尾内容面应由共享阅读内核统一仲裁。

### 12.5 直接使用 `ThreadPostCard`

不采用。它是完整帖子楼层组合，包含需求中明确不需要的 footer 和操作。应复用其公开原子组件与主题 token，新增 `ComicCommentCard`。

### 12.6 为评论页复制一套正文 renderer

不采用。评论页如果复制一套正文 renderer，就会与解析模式帖子的字号、行高、段距、简繁转换、主题适配和 HTML 语义逐渐分叉。直接使用 `ForumHtmlContentView`，让现有模块决定正文图片、表情、引用和隐藏文字的渲染行为，评论页只组合楼层元数据和正文 surface。

## 14. 完成定义

全部实现完成前，以下条件必须同时满足：

1. 漫画最后一张图片可非阻塞地触发对应 `sourceTid` 的 JSON 评论请求。
2. 所有分页回帖可合并，楼主首楼不会展示，重复楼不会重复展示。
3. `authorid=422014` 和 `authorid=8` 头像路径正确，异常 ID 有默认头像。
4. 评论卡片只展示头像、名字、时间、楼层号和正文。
5. `message` 正文通过现有 HTML renderer 展示，普通图片和表情遵循解析模式正文规则。
6. 主题适配、字号、行高、段距、简繁转换和隐藏文字语义与解析模式正文一致。
7. LTR/RTL 可从最后一张滑入评论 tail，再滑入下一章节；评论失败时仍显示下一章节提示。
8. 垂直模式末尾有查看评论入口，失败时显示“无法查看评论”的 Snackbar，不能破坏图片阅读。
9. 评论页可见期间只预加载下一章节前几张图片，不触发整章下载、已读或进度写入。
10. 章节切换、返回、切后台和迟到响应不会产生旧评论串页或 disposed controller 错误。
11. 公共图片阅读器、漫画阅读器已有的图片预加载、进度跳转、缩放和下载当前图片行为不回归。
12. API、正文、头像、reader tail、评论卡片和漫画编排均有独立测试，Flutter analyze 和相关测试通过。

---

## 15. 实施顺序结论

推荐严格按以下顺序执行：

```text
Phase 0  冻结 JSON / 首楼 / HTML 正文复用 / tail ADR
   ->
Phase 1  先让评论数据在领域层可靠落地
   ->
Phase 2  单独完成评论卡片和现有 HTML 正文接入
   ->
Phase 3  给共享 reader 增加中性 tail，不接具体业务
   ->
Phase 4  漫画最后一张触发评论并显示 tail
   ->
Phase 5  评论 tail 之后滑入下一章并预加载 lookahead
   ->
Phase 6  性能、并发、主题、无障碍和异常硬化
   ->
Phase 7  真机验收、文档收口和删除临时实现
```

这样安排可以把最容易失控的三个问题分开验证：

- 论坛分页数据是否完整。
- 评论正文是否真正复用现有 HTML renderer 和论坛显示设置，且图片不被误归类为漫画页资源。
- 非图片内容是否能在三种阅读模式下成为稳定的阅读序列尾部。

只有这三个基础问题分别稳定后，才将评论能力接入漫画章节切换和下一章预加载，避免在一个巨型 controller 中同时调试网络、HTML、图片、手势和章节状态。
