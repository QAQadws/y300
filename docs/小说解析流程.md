# 小说解析流程

> 当前状态：按需章节水合 Phase 0-6 已完成（2026-07-13）
> 章节 API 固定使用 `version=1 + ppp=200 + authorid`；收藏通用详情仍使用 `version=4`。

## 一、生产架构

小说生产链分为四个职责独立的流程：

1. 收藏同步复用通用 `version=4` 详情，只读取首楼并保存来源元数据。
2. 首次进入小说详情时，抓取全部楼主楼层并建立正式章节。
3. 详情页和阅读器的“更新作品”共用 checkpoint 增量同步。
4. 阅读器只读取已提交的本地章节正文，并用 HTML-first renderer 展示。

```text
收藏同步 version=4 detail
  -> NovelSourceMetadataIngestService（仅 posts.first）
  -> works + novel_shelf_items + novel_source_state

首次进入详情 / 非 ready 状态重试
  -> NovelChapterSyncService.initialFull
  -> version=1 + ppp=200 + authorid, page 1..lastPage
  -> staging -> 原子 promote -> checkpoint

详情更新 / 阅读器“更新作品”
  -> NovelChapterUpdateService
  -> ready: incremental(checkpoint last page..new last page)
  -> non-ready: initialFull
  -> staging -> 原子 promote -> checkpoint

打开章节
  -> LocalNovelRepository 读取正式 episode/content
  -> NovelReaderBootstrapService
  -> HTML-first 阅读器
```

## 二、收藏首楼元数据摄取

收藏模块先为候选收藏加载通用帖子详情并分类。分类为小说后，`NovelFavoriteContentIngestHandler` 将同一个 `ThreadDetailData` 交给小说 ingest，不新增小说网络请求。

`NovelSourceMetadataParser` 只允许读取 `detail.posts.first`，提取：

- 作品标题、fid、tid。
- 发布者名称和 UID。
- 首楼 PID。
- 来源简介。
- 来源目录快照。
- 首楼普通正文图中的封面候选。

`version=4` 的第二楼及后续楼层不参与章节生成，也不会被预解析。来源目录只保存在 `novel_source_state.source_catalog_json`，不生成章节、不提供章节标题、不控制顺序。

元数据写入通过一个 SQLite transaction 同时更新 `works`、默认 `novel_shelf_items` 和 `novel_source_state`。用户简介仍保存在 `library_work_state.intro_text`，展示优先级为用户简介高于来源简介。

## 三、楼主章节同步

### 3.1 请求合同

所有章节页面必须经 `NovelThreadGateway.loadAuthorPostsPage` 请求：

```text
module=viewthread
tid=<sourceTid>
page=<authorFilteredPage>
version=1
ppp=200
authorid=<publisherId>
```

- `authorid` 来自收藏首楼；旧数据缺失时只允许显式 metadata recovery 获取一次 `version=4` 首楼。
- 所有小说共享 provider-scoped 700ms governor，网络请求严格串行。
- author-filtered 页码只用于同步 checkpoint，不能用于原帖楼层跳转。

### 3.2 章节构建

`NovelAuthorPostEpisodeBuilder` 对服务端过滤结果再次校验作者 UID。每个有效 PID 对应一个稳定章节：

```text
episodeId = <novelId>:<pid>
```

标题来自正文首个有意义句子，最多 36 个 Unicode grapheme；过长使用省略号，无可见文字时使用顺序兜底标题。正文保留 attach 展开后的 HTML，同时保存 plain text 和 paragraphs，供搜索、摘要和阅读器使用。

旧 `NovelEpisodeDiscoveryService` 的 catalog-first、heading、章节正则和 PID 可见兜底标题不再进入生产 provider 或 `NovelRepository` 合同。相关类和测试只作为历史算法兼容基线，不得重新接入收藏、详情或阅读器生产链。

### 3.3 staging 与原子提交

每页解析后写入 `novel_episode_sync_staging`，网络期间不持有长事务。全部页面成功后，`SqfliteNovelChapterSyncRepository.promote` 在一个短事务内完成正式章节、正文、状态和 checkpoint 更新。

- `initialFull`：upsert 本次完整章节集合，并删除不在新集合中的旧错误章节。
- `incremental`：只 upsert 本次返回的 PID，不删除缺席历史 PID。
- 已有 PID 更新来源标题、正文和页信息，但保留原 `order_index` 与共享已读、下载、书签、阅读进度。
- 新 PID 从当前最大 `order_index + 1` 开始追加。
- 任一页面或 transaction 失败都不推进 checkpoint，不暴露 staging 半成品。

## 四、详情与阅读器更新

`NovelChapterUpdateService` 是用户主动更新作品的唯一 application service：

1. 读取 `novel_source_state`。
2. publisherId 缺失时执行显式 metadata recovery。
3. `ready + 有效 checkpoint` 选择 incremental。
4. 其它水合状态选择 initialFull。
5. 委托同一个 `NovelChapterSyncService` 执行。

小说详情的下拉刷新、header 更新按钮和更多菜单刷新均经 `NovelDetailAdapter.refreshWork` 调用该 service。阅读器错误页动作命名为“更新作品”，也调用同一个 service；更新成功后重新读取当前章节，失败时保留当前可读正文。

生产 `NovelRepository` 只负责本地书架、章节、正文、偏好、进度、书签和封面路径，不再暴露 `upsertNovelBySeed` 或 `refreshEpisodes`。生产 `novelRepositoryProvider` 也不再创建 legacy gateway、catalog discovery 或旧规则链。

## 五、阅读器正文

阅读器通过 `NovelReaderBootstrapService` 优先读取下载章节，否则读取本地正式 `novel_episode_content`。正文继续使用共享 DOM、attach 展开和 `ForumHtmlWidgetPostRenderer` 的 HTML-first 管线；章节同步不会重建分页 surface，也不会修改阅读偏好和进度提交语义。

## 六、原帖楼层模式

章节的 `sourcePage` 是 author-filtered 抓取页，不是普通帖子页。原帖模式只使用 `tid + pid` 经 `ThreadPostLocator/findpost` 定位普通页，再打开 `ThreadDetailPage(initialPage, targetPid)`。定位失败必须显示错误并提供显式打开帖子首页的备选，不允许直接使用 `sourcePage` 跳转。

## 八、Review 重点

- 收藏分类为小说后没有额外章节请求。
- 章节请求始终包含 `version=1 + ppp=200 + authorid`。
- 初次水合抓取全部楼主页；增量只抓 checkpoint 重叠页及后续页。
- 失败不推进 checkpoint、不删除旧章节、不破坏用户状态。
- 详情和阅读器均使用 `NovelChapterUpdateService`。
- 生产 provider 图中没有 legacy gateway、catalog-first discovery 或旧 detail/shelf controller。
- 漫画 catalog/search、普通帖子和收藏差分策略不受影响。
