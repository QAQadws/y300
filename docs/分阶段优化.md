# Shelf 页面分阶段优化方案

## 1. 背景与目标

当前瓶颈集中在两个体验点：

1. 第一次进入 shelf 页面时，需要先等待一段时间才能看到书架内容。
2. 进入后封面出现顺序杂乱、速度慢；切换分类 tab 时有“消失再出现”的感觉，不像成熟书架应用那样第一屏封面已经稳定存在。

这份方案基于以下源码阅读：

- 当前项目：`lib/features/library_shared/presentation/pages/unified_shelf_page.dart`、`lib/features/library_shared/presentation/controllers/unified_shelf_controller.dart`、`lib/features/comic/presentation/adapters/comic_shelf_adapter.dart`、`lib/features/novel/presentation/adapters/novel_shelf_adapter.dart`、`lib/features/favorites/presentation/adapters/favorite_shelf_adapter.dart`、`lib/features/favorites/data/local_favorite_repository.dart`、`lib/features/cache/presentation/widgets/library_cached_image.dart`、`lib/features/cache/data/default_image_cache_service.dart`、`lib/features/library_shared/domain/services/library_cover_cache_service.dart`。
- Mangayomi：`.information/mangayomi_lib/modules/library/library_screen.dart`、`.information/mangayomi_lib/modules/library/providers/library_filter_provider.dart`、`.information/mangayomi_lib/modules/library/widgets/library_gridview_widget.dart`、`.information/mangayomi_lib/modules/widgets/custom_extended_image_provider.dart`。
- Mihon：`.information/mihon-0.19.9/data/src/main/sqldelight/tachiyomi/view/libraryView.sq`、`.information/mihon-0.19.9/app/src/main/java/eu/kanade/tachiyomi/ui/library/LibraryScreenModel.kt`、`.information/mihon-0.19.9/app/src/main/java/eu/kanade/tachiyomi/data/cache/CoverCache.kt`、`.information/mihon-0.19.9/app/src/main/java/eu/kanade/tachiyomi/data/coil/MangaCoverFetcher.kt`、`.information/mihon-0.19.9/app/src/main/java/eu/kanade/tachiyomi/data/coil/MangaCoverKeyer.kt`。

最终目标：

- 首次进入 shelf：不要等待网络封面下载；只等待必要的本地元数据查询。
- 首屏封面：优先从内存、本地路径、磁盘缓存快速显示；远程下载只在后台排队。
- tab 切换：分类页、滚动位置和已显示封面保持稳定，不出现明显空白或重载感。
- 工程结构：元数据查询、封面解析、封面预热、UI 展示职责分离，后续漫画、小说、收藏共用同一套能力。

建议目标值：

- 有本地数据时，`进入页面 -> 元数据可见` 控制在 300ms-800ms。
- 首屏已有本地封面时，首屏封面可见率接近 100%，且不依赖网络。
- 无本地封面时，首屏封面按视口顺序加载，避免随机散点式出现。
- tab 切换后不清空旧页面，滚动位置和已解码图片继续保留。

## 2. 参考项目结论

### 2.1 Mangayomi 的可迁移经验

Mangayomi 的书架体验主要来自三类设计：

- 过滤和排序被提取到 Riverpod provider 中，例如 `filteredLibraryMangaProvider`。下载、追踪等状态先批量取成 `Set`，再在内存中 O(1) 判断，避免每个 item 单独查库。
- 分类使用 `TabBarView` 和稳定的 `TabController`，分类页天然更容易保持住页面状态。
- `CustomExtendedNetworkImageProvider` 把图片加载做成 ImageProvider：全局内存 LRU、磁盘缓存、过期时间、缓存淘汰、网络回退都在图片管线中处理，而不是散落在列表 item 的 build 里。

可迁移到 Y300 的核心不是照搬 UI，而是：

- 批量准备状态，减少 per-item 查询。
- 封面显示使用稳定 provider / resolver，避免每个 tile 自己做同步文件判断和 FutureBuilder。
- 分类页保持 alive，tab 切换不触发整页重建和封面重新解析。

### 2.2 Mihon 的可迁移经验

Mihon 的架构更接近“工程化书架”的答案：

- `libraryView.sq` 用一个 SQLite view 聚合漫画、章节总数、已读数、最近阅读、最新更新时间、书签数、分类列表。UI 不做每本漫画多次 count 查询。
- `LibraryScreenModel` 组合多个 flow，用 `distinctUntilChanged`、`debounce`、`collectLatest` 控制更新频率；分组和排序结果进入状态，而不是每次 build 重新推导。
- `CoverCache` 是独立封面缓存，不和普通网络临时缓存混在一起。
- `MangaCoverFetcher` 的读取顺序清晰：自定义封面、本地 library cover cache、通用磁盘 cache、网络；网络响应成功后会写入 library cover cache。
- `MangaCoverKeyer` 用 `coverLastModified` 等稳定字段控制缓存 key，既避免旧封面不刷新，也避免无意义地破坏缓存命中。

可迁移到 Y300 的核心是：

- shelf 列表要有“聚合快照”，不要在适配器里为每个作品临时查很多次。
- 封面缓存要成为独立、可观测、可限流的 pipeline。
- 书架状态要支持增量更新，封面 resolved 后只更新相关 item / tile。

## 3. 当前实现瓶颈诊断

### 3.1 首次进入等待的直接原因

`UnifiedShelfPage.initState` 中 post-frame 调用 `_controller.initialize()`，控制器进入 `_reload()` 后：

1. `loadDisplayPreference()`
2. `loadCategories()`
3. `_adapter.queryItems(...)`
4. 全部完成后才把 `isLoading` 设为 `false`

也就是说，页面是否能进入 shelf，取决于 `queryItems` 是否完成。

当前 `queryItems` 不只是“查列表”：

- 漫画和小说适配器会先按分类取数据，再 `Future.wait(items.map(_mapWork))`。
- `_mapWork` 会逐个作品查询未读数、已读数、下载数、标签状态。
- `_mapWork` 还会调用 `_ensureCoverCached`，进而可能进入 `ImageCacheService.ensureCached`，触发磁盘检查、cache manager 查询、header 构建、下载、写库。
- 收藏适配器 `FavoriteShelfAdapter.queryItems` 拿到 repository 结果后，还会 `_ensureCoversForQueryResult`，收藏封面同样可能触发缓存和写回。
- 收藏页 `loadCategories` 第一次还可能 `_ensureInitialSync()`，这会把首次同步纳入进入页面的关键路径。

因此第一次进入书架时，用户看到的转圈并不只是 DB 查询，而是在等待“列表元数据 + 每本作品状态 + 封面缓存 + 可能的网络同步”。

### 3.2 封面读取慢且随机的原因

`LibraryCachedImage` 当前逻辑：

- build 阶段读取 `localPath` 后执行 `io.File(local).existsSync()`。
- 本地文件不存在时，如果需要 headers，就创建 `FutureBuilder` 等待 `buildHeaders`。
- 最后使用 `NetworkImage` 显示远程图。

问题点：

- `existsSync()` 在 build 中同步访问文件系统，列表快速滚动或首屏大量 tile 构建时会制造主线程抖动。
- `FutureBuilder` 以 tile 为单位等待 headers，首屏多个远程图会各自进入异步状态，出现随机完成顺序。
- `NetworkImage` 依赖 Flutter 默认 image cache，但没有和项目已有 `cachedImagesTable`、protected cover、写回策略形成统一链路。
- 当前 `cacheExtent: 900` 只是让更多 widget 提前 build，不等于按视口优先级预取、下载、解码封面。

### 3.3 tab 切换有消隐感的原因

当前 shelf 使用 `PageView.builder`。每次 `selectCategory` 或搜索、筛选、排序后，外层 `setState` 会重建整页。虽然 Flutter 的 image cache 可能保留一部分 decoded image，但当前分类页没有明确的 per-category keep-alive、稳定滚动存储和封面解析缓存。

结果是：

- 页面切换时 item subtree 可能被重新 build。
- `LibraryCachedImage` 又重新做本地路径检查、header Future、NetworkImage 创建。
- 如果封面还没有进入 decoded image cache，就会出现“先空再出现”的感受。

### 3.4 查询层重复工作偏多

漫画、小说、收藏都有 per-category / per-item 重复查询：

- 漫画/小说：`countUnreadEpisodes`、`countReadEpisodes`、`countDownloadedEpisodes`、`hasAnyTag` 是逐作品查询。
- 收藏：`_mapWorkItem` 中每条收藏还会查 tag、查模块封面；`queryItems` 按分类循环，分类多时重复成本放大。
- Mihon 的做法是把这些聚合进 `libraryView`，一次 query 拿到 UI 所需字段。

这类问题在数据少时不明显，数据一多就会变成 shelf 首屏的核心成本。

## 4. 总体优化原则

后续实现建议遵守四条原则：

1. shelf 页面进入只等待本地元数据，不等待网络封面，不等待全量封面缓存。
2. 列表查询返回的是稳定快照，封面预热是后台任务，两个链路解耦。
3. 封面加载顺序必须由视口优先级控制：当前分类首屏 > 当前分类下一屏 > 相邻分类首屏 > 后台全量补齐。
4. UI 层不负责缓存策略；UI 只消费一个“当前最好可用封面候选”，并在后台结果回来后增量刷新。

不建议做的事情：

- 单纯把 `cacheExtent` 调大。这会提前 build 更多 tile，但也会提前制造更多同步文件检查和网络请求。
- 对所有作品 `Future.wait` 下载封面。并发太大时，DB、磁盘、网络、解码会互相抢资源。
- 在 build 中做文件系统同步检查。
- 每次封面更新都重建整个 shelf 页面。
- 首次进入收藏页时强制等待完整同步完成。应该显示本地快照或空态 + 同步进度，后台补齐。

## 5. 分阶段路线总览

| 阶段 | 目标 | 耗时 | 收益 |
| --- | --- | ---: | --- |
| Phase 0 | 建立性能基线和关键路径日志 | 0.5-1 天 | 确认真正耗时点，避免盲改 |
| Phase 1 | 元数据查询与封面缓存解耦 | 1-2 天 | 首次进入明显变快 |
| Phase 2 | 聚合查询 / shelf snapshot | 2-4 天 | 消灭 per-item count 查询 |
| Phase 3 | 独立封面 pipeline 与优先级队列 | 3-5 天 | 封面加载顺序稳定、可控 |
| Phase 4 | tab/page 保活与视口预热 | 2-3 天 | tab 切换不闪、不重载 |
| Phase 5 | 现代化图片组件 / ImageProvider | 2-3 天 | 减少 build 抖动，提升丝滑度 |
| Phase 6 | 增量状态更新与 stale-while-revalidate | 2-4 天 | 封面更新不重建整页 |
| Phase 7 | 缓存一致性、失效和清理策略 | 1-2 天 | 长期稳定，避免缓存膨胀和旧封面 |
| Phase 8 | 验收、测试、灰度开关 | 1-2 天 | 降低回归风险 |

推荐执行顺序：

1. 先做 Phase 0 和 Phase 1，这是最快能改善“进入转圈”的部分。
2. Phase 2 和 Phase 3 是核心工程化改造，建议连续做。
3. Phase 4 和 Phase 5 可以并行或穿插做，主要改善 tab 和图片丝滑度。
4. Phase 6 让架构真正稳定，避免后续功能越加越慢。

## 6. Phase 0：性能基线与观测

**耗时：0.5-1 天**

### 目标

在不改变业务行为的前提下，记录 shelf 首次进入、查询、封面缓存、图片显示的耗时。优化前必须知道每段耗时占比。

### 建议改动

在 debug/profile 下增加轻量 instrumentation：

- `UnifiedShelfController._reload`
  - `loadDisplayPreference` 耗时
  - `loadCategories` 耗时
  - `queryItems` 总耗时
  - 分类数、作品数
  - `isLoading=true -> false` 总耗时
- `ComicShelfAdapter` / `NovelShelfAdapter` / `FavoriteShelfAdapter`
  - 每个分类 `getShelfItems/loadCategoryItems` 耗时
  - `_mapWork` 总耗时
  - per-item 状态查询总耗时
  - `_ensureCoverCached` 命中本地、命中 cacheManager、下载、失败的数量
- `LibraryCachedImage`
  - 本地路径存在命中次数
  - 本地路径不存在次数
  - header Future 等待次数
  - remote fallback 次数
- `DefaultImageCacheService.ensureCached`
  - repository 命中
  - 文件存在命中
  - cacheManager 命中
  - network download
  - write-back 耗时

实现方式：

- 增加一个 debug-only 工具，例如 `ShelfPerfTrace`。
- 使用 `Stopwatch` 和 `dart:developer` 的 `TimelineTask`，release 下为空实现。
- 每次 shelf reload 生成一个 `traceId`，把 controller、adapter、cover cache 的日志串起来。

### 输出指标

至少记录这些指标：

- `shelf_first_metadata_ms`：进入页面到 metadata 可展示。
- `shelf_query_items_ms`：`queryItems` 总耗时。
- `shelf_item_count`：当前模块作品数。
- `cover_blocking_count`：首轮 query 中触发封面缓存的次数。
- `cover_network_count`：首轮 query 中触发网络下载的次数。
- `tab_switch_rebuild_count`：切换 tab 时当前页 item build 次数。
- `first_screen_local_cover_hit_rate`：首屏本地封面命中率。

### 验收标准

- 可以用日志判断：首屏慢到底是 DB、网络、文件系统、header、图片解码还是同步。
- 后续每个阶段改动后都能对比同一组指标。

### 风险

- 日志太多会污染性能。只在 debug/profile 打开，并按一次 reload 聚合输出。

## 7. Phase 1：元数据查询与封面缓存解耦

**耗时：1-2 天**

### 目标

让 `queryItems` 只负责返回书架元数据，不再负责下载、复制、写回封面。页面先显示数据，封面后台补齐。

### 当前要拆掉的耦合

漫画：

- `ComicShelfAdapter._mapWork` 调用 `_ensureCoverCached`。
- `_ensureCoverCached` 可能调用 `_coverCacheService.ensureProtectedCover`，导致进入 `DefaultImageCacheService.ensureCached`。

小说：

- `NovelShelfAdapter._mapWork` 调用 `_ensureCoverCached`。

收藏：

- `FavoriteShelfAdapter.queryItems` 调用 `_ensureCoversForQueryResult`。
- `_ensureFavoriteCoverCachedWithTarget` 可能进行封面下载和写回。

### 建议改动

1. 改造适配器映射：
   - `_mapWork` 只从 DB 原始记录读取 `coverImageUrl`、`customCoverImageUrl`、`coverLocalPath`、`customCoverLocalPath`。
   - 不在 `_mapWork` 中调用 `_ensureCoverCached`。
   - `loadCategoryItems`、`searchItemsByKeyword`、`queryItems` 都保持 metadata-only。

2. 新增后台封面预热入口：
   - 在 shared 层增加 `LibraryCoverWarmupService` 或 `ShelfCoverWarmupCoordinator`。
   - `UnifiedShelfController._reload` 设置 `isLoading=false` 后，再触发 warmup。
   - warmup 不影响 `_reload` 返回，不阻塞 UI。

3. 收藏首次同步改为非阻塞：
   - `FavoriteShelfAdapter.loadCategories` 不应因为没有 sync snapshot 就阻塞完整同步。
   - 如果没有 snapshot，先返回系统分类或空分类结构，让页面展示进度 banner。
   - 同步任务用 `taskProgress` 展示，完成后触发 refresh/reload。

4. 控制后台并发：
   - 第一版可以简单限制：同时下载 2-4 个封面。
   - 同一 `cacheKey` 去重，避免多个分类重复请求同一作品封面。

### 涉及文件

- `lib/features/comic/presentation/adapters/comic_shelf_adapter.dart`
- `lib/features/novel/presentation/adapters/novel_shelf_adapter.dart`
- `lib/features/favorites/presentation/adapters/favorite_shelf_adapter.dart`
- `lib/features/library_shared/presentation/controllers/unified_shelf_controller.dart`
- 新增 `lib/features/library_shared/domain/services/shelf_cover_warmup_service.dart` 或同类文件

### 第一版实现形态

可以先做最小实现：

```dart
class ShelfCoverWarmupRequest {
  const ShelfCoverWarmupRequest({
    required this.moduleKey,
    required this.workId,
    required this.cacheKey,
    required this.ownerType,
    required this.role,
    required this.sourceUrl,
    this.custom = false,
  });

  final LibraryModuleKey moduleKey;
  final String workId;
  final String cacheKey;
  final ImageCacheOwnerType ownerType;
  final ImageCacheRole role;
  final String sourceUrl;
  final bool custom;
}
```

适配器只负责提供 request：

- 漫画普通封面：`ImageCacheKeys.comicCover(workId)`
- 小说普通封面：`ImageCacheKeys.novelCover(workId)`
- 自定义封面：`ImageCacheKeys.customCover(...)`

### 验收标准

- `UnifiedShelfController._reload` 不再等待任何封面网络下载。
- `queryItems` 日志中 `cover_network_count = 0`。
- 有本地封面路径的作品仍立即显示。
- 没有本地封面的作品显示 placeholder，随后后台按顺序补图。

### 风险与回滚

- 风险：封面写回从同步链路变成后台链路后，UI 需要知道何时刷新 local path。
- 临时方案：后台预热完成后触发一次轻量 `refreshCoversOnly`，只读取封面路径并更新当前 state。
- 回滚简单：保留旧 `_ensureCoverCached` 方法，但不在 query 中调用。

## 8. Phase 2：聚合查询 / ShelfSnapshot

**耗时：2-4 天**

### 目标

把 shelf 页面需要的字段一次性查出来，避免每个作品多次查询状态表和标签表。这个阶段对应 Mihon `libraryView.sq` 的思想。

### 当前问题

漫画/小说每个 item 至少会产生：

- unread count 查询
- read count 查询
- downloaded count 查询
- has tag 查询
- 封面缓存查询，Phase 1 后移除

收藏每个 item 还会：

- 查 tag
- 查漫画/小说模块封面
- 按分类重复 load item

作品数一多，这会从 O(分类 * 作品 * 多次查询) 放大成明显卡顿。

### 建议新增模型

在 shared 层增加聚合快照：

```dart
class LibraryShelfSnapshot {
  const LibraryShelfSnapshot({
    required this.categories,
    required this.itemsByCategory,
    required this.visibleMatchCountByCategory,
  });

  final List<LibraryCategory> categories;
  final Map<String, List<LibraryWorkItem>> itemsByCategory;
  final Map<String, int> visibleMatchCountByCategory;
}
```

适配器增加可选能力：

```dart
abstract class ShelfSnapshotAdapter {
  Future<LibraryShelfSnapshot> querySnapshot({
    required LibraryFilterSet filters,
    required LibraryShelfSortOption sortOption,
    required String keyword,
  });
}
```

`UnifiedShelfController` 优先使用 `querySnapshot`，否则回退旧的 `loadCategories + queryItems`。

### 漫画聚合查询建议

新增 `ComicShelfSnapshotRepository` 或在 `ComicRepository` 扩展方法：

```sql
WITH episode_stats AS (
  SELECT
    content_type,
    work_id,
    COUNT(*) AS state_count,
    SUM(CASE WHEN is_read = 0 THEN 1 ELSE 0 END) AS unread_count,
    SUM(CASE WHEN is_read = 1 THEN 1 ELSE 0 END) AS read_count,
    SUM(CASE WHEN is_downloaded = 1 THEN 1 ELSE 0 END) AS downloaded_count
  FROM library_episode_state
  WHERE content_type = 'comic'
  GROUP BY content_type, work_id
),
tag_stats AS (
  SELECT content_type, work_id, 1 AS has_tags
  FROM library_work_tags
  WHERE content_type = 'comic'
  GROUP BY content_type, work_id
),
chapter_stats AS (
  SELECT comic_id AS work_id, COUNT(*) AS total_count
  FROM episodes
  GROUP BY comic_id
)
SELECT
  si.category_id,
  si.added_at,
  si.sort_order,
  c.comic_id AS work_id,
  c.title,
  c.author,
  COALESCE(c.custom_cover_image_url, c.cover_image_url) AS cover_image_url,
  c.custom_cover_image_url,
  c.cover_local_path,
  c.custom_cover_local_path,
  COALESCE(es.unread_count, 0) AS unread_count,
  COALESCE(cs.total_count, es.state_count, 0) AS total_count,
  COALESCE(es.read_count, 0) AS read_count,
  COALESCE(es.downloaded_count, 0) AS downloaded_count,
  COALESCE(ts.has_tags, 0) AS has_tags
FROM shelf_items si
JOIN comics c ON c.comic_id = si.comic_id
LEFT JOIN episode_stats es ON es.work_id = c.comic_id
LEFT JOIN chapter_stats cs ON cs.work_id = c.comic_id
LEFT JOIN tag_stats ts ON ts.work_id = c.comic_id
```

按当前表名替换为 `ComicLocalDb` 常量。排序和筛选可以先在 Dart 层做，稳定后再逐步下推到 SQL。

### 小说聚合查询建议

小说已有 `work_episodes` 和 `works`，可以类似：

```sql
WITH episode_stats AS (
  SELECT
    content_type,
    work_id,
    COUNT(*) AS total_count
  FROM work_episodes
  WHERE content_type = 'novel'
  GROUP BY content_type, work_id
),
state_stats AS (
  SELECT
    content_type,
    work_id,
    SUM(CASE WHEN is_read = 0 THEN 1 ELSE 0 END) AS unread_count,
    SUM(CASE WHEN is_read = 1 THEN 1 ELSE 0 END) AS read_count,
    SUM(CASE WHEN is_downloaded = 1 THEN 1 ELSE 0 END) AS downloaded_count
  FROM library_episode_state
  WHERE content_type = 'novel'
  GROUP BY content_type, work_id
),
tag_stats AS (...)
SELECT ...
FROM novel_shelf_items si
JOIN works w ON w.work_id = si.novel_id AND w.content_type = 'novel'
LEFT JOIN episode_stats es ON es.work_id = w.work_id
LEFT JOIN state_stats ss ON ss.work_id = w.work_id
LEFT JOIN tag_stats ts ON ts.work_id = w.work_id
```

### 收藏聚合查询建议

收藏建议避免 `_mapWorkItem` 中每条记录查模块封面。可以用两个 LEFT JOIN 分别关联漫画和小说：

```sql
SELECT
  ft.*,
  fc.category_id AS custom_category_id,
  c.cover_image_url AS comic_cover_image_url,
  c.custom_cover_image_url AS comic_custom_cover_image_url,
  c.cover_local_path AS comic_cover_local_path,
  c.custom_cover_local_path AS comic_custom_cover_local_path,
  w.cover_image_url AS novel_cover_image_url,
  w.cover_local_path AS novel_cover_local_path,
  w.custom_cover_local_path AS novel_custom_cover_local_path,
  CASE WHEN tags.work_id IS NULL THEN 0 ELSE 1 END AS has_tags
FROM favorite_threads ft
LEFT JOIN favorite_thread_category fc ON fc.tid = ft.tid
LEFT JOIN comics c ON ft.content_kind = 'comic' AND ft.work_id = c.comic_id
LEFT JOIN works w ON ft.content_kind = 'novel' AND ft.work_id = w.work_id AND w.content_type = 'novel'
LEFT JOIN (
  SELECT content_type, work_id
  FROM library_work_tags
  WHERE content_type = 'favorite'
  GROUP BY content_type, work_id
) tags ON tags.work_id = ...
WHERE ft.removed_at IS NULL
```

系统分类和自定义分类可以先用两条 query，仍然比每 item 查询强很多。

### 索引建议

当前已有部分索引，例如 episode state、work tags、favorite category。建议确认并补充：

- 漫画 shelf：`shelf_items(category_id, sort_order, added_at)`、`shelf_items(comic_id)`。
- 小说 shelf：`novel_shelf_items(category_id, sort_order, added_at)`、`novel_shelf_items(novel_id)`。
- 作品章节：`episodes(comic_id, order_index)`、`work_episodes(content_type, work_id, order_index)`。
- 状态聚合：`library_episode_state(content_type, work_id, is_read)`、`library_episode_state(content_type, work_id, is_downloaded)`。
- 标签：`library_work_tags(content_type, work_id)`。
- 收藏：`favorite_threads(content_kind, removed_at, remote_order)`、`favorite_thread_category(category_id, tid)`。

### 验收标准

- 每次 shelf reload 的 SQL 查询数量与作品数基本无关。
- 作品数增加时，`querySnapshot` 耗时增长接近线性，而不是作品数乘以 per-item query 数。
- Phase 1 后的“无封面网络阻塞”继续保持。

### 风险与回滚

- 风险：旧 per-item 逻辑和聚合 SQL 的统计口径可能不完全一致。
- 处理：保留旧方法作为 fallback；为聚合查询补单元测试，逐项对比 unread/read/download/tag。

## 9. Phase 3：独立封面 Pipeline 与优先级队列

**耗时：3-5 天**

### 目标

把封面从“列表查询时顺手下载”改为“可限流、可取消、可按视口优先级调度”的 pipeline。

### 核心组件

建议新增 shared 层服务：

1. `ShelfCoverResolver`
   - 只负责解析某个作品当前最好可用封面。
   - 读取顺序：自定义本地封面 > 普通本地封面 > image cache metadata > cache manager file > 远程 URL。
   - `resolveFast` 不触发网络，只返回当前可立即使用的 candidate。

2. `ShelfCoverWarmupQueue`
   - 负责后台下载和写回。
   - 支持优先级、去重、并发限制、取消。

3. `ShelfCoverWriteBack`
   - 把下载成功的 local path 写回漫画、小说或收藏对应模块。
   - 收藏本身不复制封面策略，仍写回漫画/小说模块，保持当前设计方向。

4. `ShelfCoverStateStore`
   - 保存 `workId/cacheKey -> resolved local path/status`。
   - 给 controller 或 tile 提供增量通知。

### 推荐读取顺序

与 Mihon 的 `MangaCoverFetcher` 思路对齐：

1. 自定义本地封面 `customCoverLocalPath`
2. 普通本地封面 `coverLocalPath`
3. `cachedImagesTable` 中的 protected cover path
4. `flutter_cache_manager` 的 cache file
5. 网络下载
6. placeholder

注意：1-4 可以作为 fast path；5 必须进队列，不能阻塞首屏。

### 优先级设计

定义四级优先级：

| 优先级 | 范围 | 用途 |
| --- | --- | --- |
| P0 | 当前分类首屏可见 item | 进入页面后立即补齐 |
| P1 | 当前分类下一屏 1-2 屏 | 滚动前预热 |
| P2 | 左右相邻分类首屏 | tab 切换前预热 |
| P3 | 当前模块剩余作品 | 空闲时慢慢补齐 |

队列策略：

- P0/P1 允许网络并发 2-4。
- P2/P3 网络并发 1-2。
- 磁盘 local path 验证可以并发高一些，但不要在 build 中同步做。
- 同一 `cacheKey` 去重。
- 用户快速切 tab 或离开页面时，降低旧任务优先级或取消未开始任务。
- 失败记录短期冷却，例如 5-10 分钟内不重复请求同一失败 URL。

### 关键流程

页面首次进入：

1. `querySnapshot` 返回元数据。
2. UI 立刻显示。
3. controller 根据当前分类和 grid/list 估算首屏 item 数。
4. post-frame 发起 P0 cover warmup。
5. 下一帧或空闲时发起 P1/P2。
6. warmup 成功后，只更新对应 item 的 cover path。

滚动时：

1. 收集可见 index 范围。
2. 对可见范围和后续 N 个 item enqueue P0/P1。
3. 已经完成或正在执行的 `cacheKey` 不重复入队。

tab 切换时：

1. 新分类首屏升级为 P0。
2. 前后相邻分类首屏保持 P2。
3. 旧分类未完成的 P3 降级或暂停。

### cache key 与失效

推荐 key：

- 普通漫画封面：`cover/comic/{workId}`
- 普通小说封面：`cover/novel/{workId}`
- 自定义封面：`cover/{module}/{workId}/custom`

失效条件：

- `lastSourceUrl` 改变。
- 自定义封面发生变化。
- 用户主动清理封面缓存。
- 文件不存在或长度为 0。

不要把时间戳直接拼进 cache key 导致每次刷新都失去命中。更好的做法是稳定 key + metadata 中记录 `lastSourceUrl/updatedAt/coverVersion`，需要更新时覆盖同一个 key。

### 验收标准

- 首次进入不出现全量封面网络风暴。
- 首屏封面按位置顺序补齐，不再随机散点式出现。
- 快速切 tab 时，新 tab 首屏优先级立即提升。
- 同一作品在多个分类或收藏页中只下载一次。

### 风险与回滚

- 风险：后台队列和 controller 生命周期耦合不当，页面销毁后仍回调。
- 处理：每个 controller 维护 generation token；结果回来时 token 不匹配则丢弃。

## 10. Phase 4：tab/page 保活与视口预热

**耗时：2-3 天**

### 目标

让分类切换像成熟漫画应用一样稳定：已经展示过的页面和封面不重新从零开始。

### 建议改动

1. 为每个分类页拆出独立 widget：

```dart
class ShelfCategoryPage extends StatefulWidget {
  const ShelfCategoryPage({
    super.key,
    required this.categoryId,
    required this.items,
  });
}
```

内部使用：

- `AutomaticKeepAliveClientMixin`
- `PageStorageKey('shelf-category-$categoryId')`
- `RepaintBoundary`
- 独立 `ScrollController` 或依赖 PageStorage 保存 offset

2. `PageView.builder` 保留也可以，但 itemBuilder 返回稳定 key 的 category page：

```dart
return ShelfCategoryPage(
  key: ValueKey('shelf-category-page-${category.categoryId}'),
  categoryId: category.categoryId,
  items: items,
);
```

3. tab 切换时不要清空 `itemsByCategory`：
   - refresh 时保留旧 state。
   - 在 app bar 或 banner 显示刷新中。
   - 新数据回来后 diff 更新。

4. 增加相邻 tab 预热：
   - 当前 tab 首屏 P0。
   - `selectedIndex - 1` 和 `selectedIndex + 1` 首屏 P2。
   - 切换动画开始前就 enqueue 新 tab 首屏。

5. 减少切换动画带来的“消隐”：
   - 当前 `animateToPage` 220ms 可以保留，但图片层要 `gaplessPlayback`。
   - 避免封面 widget 因 key 改变而重建。
   - title overlay、badge 等固定层不依赖图片状态。

### 验收标准

- 从 A tab 切到 B tab 再切回 A tab，A tab 的滚动位置和已显示封面保持。
- 切换到相邻 tab 时，首屏封面大多已经命中本地/内存或正在 P0 下载。
- 搜索、筛选、排序时不会出现整页长时间空白。

### 风险与回滚

- 风险：keep-alive 太多会占用内存。
- 处理：只保持最近访问的 3-5 个分类，或使用 `PageView` 默认邻页缓存 + 手动保存 scroll offset。

## 11. Phase 5：图片组件现代化

**耗时：2-3 天**

### 目标

替换当前 `LibraryCachedImage` 的同步文件检查和 per-tile header Future，让图片展示更接近 ImageProvider 管线。

### 当前问题复盘

`LibraryCachedImage` 做了三件不适合 build 阶段做的事：

- `File.existsSync()`
- 为每个 tile 创建 header Future
- 直接 fallback 到 `NetworkImage`

这些会造成首屏和 tab 切换时的抖动。

### 建议新组件

新增 `ShelfCoverImage`，逐步替代 `LibraryCachedImage` 在 shelf 场景的使用。保留 `LibraryCachedImage` 给详情页或帖子图片，避免一次性改太大。

`ShelfCoverImage` 输入：

```dart
class ShelfCoverImage extends StatelessWidget {
  const ShelfCoverImage({
    super.key,
    required this.coverKey,
    required this.localPath,
    required this.remoteUrl,
    required this.fit,
    required this.placeholder,
    this.width,
    this.height,
  });
}
```

推荐行为：

- 如果 resolver 已确认 local path 有效，直接使用 `FileImage` 或 `ResizeImage(FileImage(...))`。
- 如果只有 remoteUrl，不直接发起不可控网络下载，而是显示 placeholder 并触发队列。
- 对已经完成的网络缓存，由 resolver 提供 local path 后再切换到 `FileImage`。
- `Image` 使用 `gaplessPlayback: true`，避免 local path 更新时闪烁。
- 固定尺寸下传 `cacheWidth/cacheHeight`，减少解码成本。

### header 缓存

当前 header 构建每个 tile 自己等 Future。建议增加 `ImageHeaderCache`：

- key 使用 normalized URL 的 origin 或完整 URL，视站点 cookie/header 策略决定。
- 同一 URL 的 header Future 共享。
- headers 短期有效，例如 5-10 分钟。
- shelf 图片下载由 `DefaultImageCacheService` 使用共享 header cache，UI 不再 FutureBuilder 等 header。

### placeholder 策略

成熟书架应用通常不在每个封面上显示 spinner。建议：

- placeholder 是固定底色 + 图标或轻量骨架。
- 本地图片切换不做 fade。
- 网络首次完成可以短 fade，但不要超过 120ms。
- 错误态与 placeholder 一致，避免杂乱。

### Flutter image cache 调整

可以在 app 初始化或 shelf 模块初始化时设置：

```dart
PaintingBinding.instance.imageCache.maximumSizeBytes = 100 << 20;
PaintingBinding.instance.imageCache.maximumSize = 1000;
```

具体数值要结合设备内存。不要无限调大，封面图建议配合 `cacheWidth/cacheHeight` 限制解码尺寸。

### 验收标准

- shelf item build 阶段不再出现同步文件系统检查。
- 首屏 headers 不再以 tile 为单位重复等待。
- 本地封面 path 更新时不闪烁。
- 快速滚动时帧时间更稳定。

### 风险与回滚

- 风险：详情页、帖子图片和 shelf 封面需求不同。
- 处理：不要直接全局替换 `LibraryCachedImage`；先只在 `ShelfCoverCard` 和 shelf list leading 中使用新组件。

## 12. Phase 6：增量状态更新与 stale-while-revalidate

**耗时：2-4 天**

### 目标

让 shelf 状态能先展示旧快照，再后台刷新；封面变化只更新相关 tile，不重建整个页面。

### 当前状态问题

`UnifiedShelfController` 当前只是普通对象，页面通过 `setState` 手动刷新。任何状态变化都会让 `UnifiedShelfPage.build` 重新运行，进而 `PageView` 和内部列表也可能重新 build。

### 建议状态模型

把状态拆成三层：

1. `ShelfMetadataState`
   - categories
   - itemsByCategory
   - filter/sort/search
   - selectedCategoryId

2. `ShelfCoverState`
   - `workId/cacheKey -> CoverStatus`
   - localPath
   - loading/failed

3. `ShelfUiState`
   - selected tab
   - scroll offsets
   - display mode
   - grid count

实现选择：

- 继续用 controller，但让 `UnifiedShelfController extends ChangeNotifier`。
- 或迁移成 Riverpod `AsyncNotifier` / `Notifier`。
- 如果暂时不想大迁移，可以用 `ValueNotifier<UnifiedShelfState>` 作为过渡。

### 增量更新方式

封面预热完成后：

- 不重新跑 `queryItems`。
- 不替换整个 `itemsByCategory`。
- 根据 `workId` 找到对应 item，复制一个新 item 更新 `coverLocalPath/customCoverLocalPath`。
- 或更进一步：封面状态从 `LibraryWorkItem` 中拆出，tile 通过 `coverStateProvider(workId)` 订阅。

如果保留 `LibraryWorkItem`，建议加 `copyWith`：

```dart
LibraryWorkItem copyWith({
  String? coverLocalPath,
  String? customCoverLocalPath,
  ...
})
```

### stale-while-revalidate

进入页面时：

1. 立即显示上一次 state 或 DB snapshot。
2. 后台刷新 metadata。
3. 新 snapshot 和旧 snapshot diff。
4. 只对新增、删除、排序变化更新列表。
5. 封面 pipeline 根据 diff 添加/取消任务。

搜索和筛选：

- 保留 250ms debounce。
- 增加 generation token：旧搜索结果回来时，如果不是最新 keyword，丢弃。
- 搜索期间不清空旧结果，可以显示轻量 loading indicator。

### 验收标准

- 一个封面下载完成不会触发所有 tab 的 item 重新 build。
- 快速输入搜索关键字时，旧请求结果不会覆盖新请求。
- refresh 时旧列表保持可见，用户不会看到长时间空白。

### 风险与回滚

- 风险：状态拆分过快会引入复杂度。
- 处理：先用 `ChangeNotifier + generation token + item copyWith`，稳定后再考虑 Riverpod 化。

## 13. Phase 7：缓存一致性、失效和清理

**耗时：1-2 天**

### 目标

避免长期使用后出现旧封面不刷新、无效本地路径越来越多、缓存无限膨胀的问题。

### 现有基础

当前已有：

- `cachedImagesTable`
- `ImageCacheRepository`
- `DefaultImageCacheService`
- `protected` 标记
- owner type / owner id / role

这套基础可以继续使用，但要把“封面缓存”作为明确策略管理。

### 建议策略

1. protected cover 与普通页面图片分开：
   - shelf 封面默认 protected。
   - 阅读页临时图片可以 unprotected，按容量清理。

2. 失效规则：
   - sourceUrl 变化时强制刷新同一个 cacheKey。
   - 自定义封面更新时，普通封面不覆盖自定义封面。
   - custom cover 删除后，回退普通封面。
   - local path 文件不存在时，标记 metadata stale，并 enqueue 重新 warm。

3. 清理规则：
   - unprotected 按 `last_accessed_at` 清理。
   - protected 不参与普通容量清理，但可以提供“清理失效封面”功能。
   - orphan protected cover：owner 不存在时可清理。

4. 命中更新：
   - resolver 读取本地/磁盘命中时 touch `last_accessed_at`。
   - 不要在 build 中 touch；由 resolver 或 warmup 成功路径统一处理。

### 验收标准

- 更换封面 URL 后不会继续显示旧图。
- 删除自定义封面后能正确回到普通封面。
- 清理普通缓存不影响书架 protected 封面。
- 删除作品后可以清理孤儿封面。

## 14. Phase 8：验收、测试与灰度

## 16. 建议的最终架构图

```text
UnifiedShelfPage
  |
  | listens
  v
UnifiedShelfController / Notifier
  |
  | querySnapshot(metadata only)
  v
ShelfModuleAdapter
  |
  +-- ComicShelfSnapshotRepository
  +-- NovelShelfSnapshotRepository
  +-- FavoriteShelfSnapshotRepository

UnifiedShelfController
  |
  | visible range / adjacent tabs
  v
ShelfCoverWarmupQueue
  |
  +-- ShelfCoverResolver(resolve fast)
  +-- ImageCacheService(download/write metadata)
  +-- ModuleCoverWriteBack(update local path)
  |
  v
ShelfCoverStateStore
  |
  | incremental update
  v
ShelfCoverImage / ShelfCoverCard
```

核心边界：

- Adapter/repository：只产出元数据快照。
- Cover pipeline：只处理封面候选、下载、缓存、写回。
- Controller：编排状态、选择优先级、增量通知。
- Widget：只展示状态，不拥有缓存策略。

## 18. 实现时的注意事项

1. 不要让 Phase 1 变成“大重构”。第一步只需要保证 query 不下载封面。
2. Phase 2 的 SQL 先求正确，再求更极致的排序/筛选下推。
3. Phase 3 的队列要小而稳：限流、去重、生命周期 token 是必须的。
4. Phase 4 的 keep-alive 要控制数量，避免低端设备内存压力。
5. Phase 5 不要一次替换所有图片场景；书架封面和帖子正文图片是两个不同问题。
6. 每个阶段都用 Phase 0 指标验收，不靠主观感觉判断。

## 19. 预期收益

完成 Milestone A 后：

- 首次进入不再被封面下载拖住。
- 用户会更快看到分类、标题和占位封面。

完成 Milestone B 后：

- 作品数增长时，书架查询不会线性乘以多次 per-item 查询。
- 搜索、筛选、排序会更稳定。

完成 Milestone C 后：

- 封面加载顺序更像“从当前屏幕开始铺开”，而不是随机出现。
- tab 切换时，已访问页面的封面和滚动位置保持。

完成 Milestone D 后：

- shelf 成为可持续扩展的模块，后续加阅读进度、下载状态、标签、收藏同步都不会继续把首屏拖慢。
