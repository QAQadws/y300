# 收藏自动刷新与搜索等待队列方案

## 背景

当前收藏页第一次进入时会触发 `FavoriteSyncService.sync()`，流程是读取收藏列表、保存本地收藏记录、补全缺失的帖子详情，再按帖子类型写入漫画或小说模块。这个链路已经解决了“收藏页能自动识别漫画/小说”的问题，但还没有把漫画详情页的章节刷新策略纳入收藏同步，所以会出现：

1. 第一次使用收藏模块后，漫画虽然进了书架，但完整章节仍需要用户逐个进入详情页手动更新。
2. 新增收藏的漫画不会自动执行一次漫画详情更新。
3. 漫画刷新失败回退到搜索时，没有统一的等待队列，容易和论坛搜索、详情页手动更新互相抢搜索冷却。
4. 收藏页进度文字仍偏同步阶段，没有展示正在解析哪一个收藏标题，也没有在解析结束后展示搜索等待状态。
5. 漫画和小说书架页没有统一的后台刷新通知，收藏同步或搜索队列完成后，页面不一定能实时看到新章节、封面和数量变化。

本文目标是给出一套分阶段、可测试、可渐进落地的实现方案。重点不是把逻辑塞进某一个页面，而是把“收藏补全、漫画刷新策略、搜索节流、书架失效通知”整理成清晰的服务边界。

## 当前代码链路梳理

### 收藏同步

- `lib/features/favorites/data/favorite_sync_service.dart`
  - `NetworkFavoriteSyncService.sync()` 负责收藏列表同步。
  - `_fillMissingDetails()` 批量读取 `detail_loaded_at IS NULL` 的收藏记录。
  - `_fillOneDetail()` 拉取帖子详情、分类为漫画/小说/普通帖子，再调用 `_syncModule()`。
  - `_syncModule()` 对漫画调用 `ComicFavoriteIngestService.upsertFromThreadDetail()`，对小说调用 `NovelFavoriteIngestService.upsertFromThreadDetail()`。
- `lib/features/favorites/presentation/adapters/favorite_shelf_adapter.dart`
  - 把 `FavoriteSyncProgress` 映射为 shared 层的 `LibraryShelfTaskProgress`。
  - `UnifiedShelfPage` 已经能在原位置展示任务进度条。

### 漫画收藏入库

- `lib/features/comic/data/comic_favorite_ingest_service.dart`
  - 当前只把收藏帖子详情解析成 `ParsedComicPost`，再调用 `ComicRepository.addToShelf()`。
  - 不会调用 `ComicEpisodeRefreshService.fetchEpisodeLinks()`，所以不会自动走目录、搜索、current-only 三段刷新策略。
- `lib/features/comic/data/local_comic_repository.dart`
  - `addToShelf()` 会保存当前解析出的 `episodeLinks` 和首楼图片。
  - `mergeEpisodesFromLinks()` 能把刷新得到的章节链接合并进本地章节表。
  - `saveEpisodeImages()` 内部已有 `_promoteFirstEpisodeCoverIfNeeded()`，会在保存最小 `tid` 章节图片时，把第一张图提升为普通封面，且不会覆盖用户自定义封面。

### 小说收藏入库

- `lib/features/novel/data/novel_favorite_ingest_service.dart`
  - `upsertFromThreadDetail()` 已经调用 `repository.refreshEpisodes(novelId: novelId)`。
  - 因此小说解析逻辑按你的要求保持不变，只需要补上书架实时刷新通知。

### 漫画详情刷新

- `lib/features/comic/domain/services/comic_services_impl.dart`
  - `NetworkComicEpisodeRefreshService.fetchEpisodeLinks()` 当前已经实现完整策略：
    1. `ComicEpisodeDiscoveryService.discoverFromTidWithPreference(preferCatalogFirst: true)`。
    2. 若不是 `EpisodeDiscoveryStrategy.catalog`，调用 `ForumSearchService.searchForum()` 搜索 `fid=30`。
    3. 搜索候选走相似度评分、top 3 回探、合并链接。
    4. 搜索失败则返回当前帖子发现的链接。
  - 问题是这个方法返回值只有 `List<ComicEpisodeLink>`，调用方不知道这次是否命中目录、是否使用了搜索、是否应该进入等待队列。
- `lib/features/comic/presentation/adapters/comic_detail_adapter.dart`
  - `refreshWork()` 直接调用完整 `fetchEpisodeLinks()` 并等待结果。
  - 如果走搜索，它会占用搜索冷却，而且详情页关闭后缺少一个明确的后台任务状态。

### 论坛搜索

- `lib/features/search/data/discuz_search_service.dart`
  - `DiscuzSearchService` 通过 `SearchRateLimiter` 做 10 秒冷却。
  - 当前只有服务内部的 rate limit，不知道漫画后台搜索队列的存在。
- `lib/features/search/presentation/forum_search_page.dart`
  - 直接调用 `discuzSearchServiceProvider.searchForum()`。
  - 当漫画搜索队列存在时，搜索页无法展示 `{xxx} 正在等待搜索 预计耗时...`。

### 书架刷新

- `UnifiedShelfController` 已经会在 `taskProgress` 从 active 变为 inactive 时重新加载一次收藏页数据。
- 漫画、小说书架适配器当前没有 `taskProgress`，也没有通用的“后台数据已变更”事件。
- 这意味着收藏同步、搜索队列、封面提升完成后，漫画/小说书架需要一个 shared 层可复用的刷新通知。

## 目标状态

1. 收藏第一次同步时，每一个收藏详情进度展示为：
   - 左侧：`正在解析: {收藏列表中的 title}`
   - 右侧：`20/57` 这类进度数字，继续使用现有 `LibraryShelfTaskProgress.current/total`。
2. 收藏同步识别为漫画后，自动先执行漫画刷新策略 1，也就是 catalog-first 的目录发现。
3. 漫画策略 1 成功时，立即合并章节，并尝试把最小 `tid` 章节的第一张图片设为漫画普通封面，收藏页、漫画书架页、漫画详情页共用这份封面。
4. 漫画策略 1 未命中目录时，不立即搜索，而是进入“搜索等待队列”。
5. 搜索等待队列按 10.5 秒节奏执行策略 2 和策略 3。执行完成后同样合并章节、提升封面、刷新书架。
6. 收藏页 UI 位置不变。收藏详情解析结束后，如果搜索队列中仍有任务，原进度 banner 显示：
   - `{title} 正在等待搜索 预计耗时{10.5 * 队列数量}s`
7. 新增收藏：
   - 小说保持现有刷新逻辑，但需要通知小说书架刷新。
   - 漫画自动执行一次策略 1，失败则加入搜索等待队列，并通知漫画/收藏书架刷新。
8. 任何会用到论坛搜索的地方都能感知搜索等待队列：
   - 论坛搜索页提交搜索时，如果队列非空，提示 `{xxx} 正在等待搜索 预计耗时{10.5 * 队列数量}s`。
   - 漫画详情页手动更新时，如果需要搜索且队列非空，提示 `更新预计耗时{10.5 * 队列数量}s`。
   - 用户离开详情页后，已入队的漫画仍继续等待并执行更新。

## 设计原则

1. 策略拆分，不让 `fetchEpisodeLinks()` 同时承担“立即刷新”和“后台排队”的职责。
2. 搜索节流集中治理，所有真实 `searchForum()` 网络请求都经过同一个调度入口。
3. 队列状态可观察，UI 只订阅快照，不直接操纵后台任务。
4. 队列任务可持久化，页面关闭或 provider 重建不应丢任务。
5. 封面提升复用已有逻辑，尊重用户自定义封面，不覆盖 `custom_cover_*`。
6. 书架刷新使用 shared 层事件，避免收藏模块直接引用漫画/小说页面控制器。

## 推荐架构

### 1. 拆分漫画刷新策略

保留现有 `ComicEpisodeRefreshService.fetchEpisodeLinks()` 作为兼容入口，但新增更明确的策略级接口。

建议模型：

```dart
enum ComicEpisodeRefreshPhase {
  catalogOnly,
  searchAndCurrentOnly,
  fullImmediate,
}

enum ComicEpisodeRefreshSource {
  catalog,
  search,
  currentOnly,
  empty,
}

class ComicEpisodeRefreshOutcome {
  const ComicEpisodeRefreshOutcome({
    required this.source,
    required this.links,
    this.usedSearch = false,
    this.catalogMatched = false,
  });

  final ComicEpisodeRefreshSource source;
  final List<ComicEpisodeLink> links;
  final bool usedSearch;
  final bool catalogMatched;
}
```

推荐接口：

```dart
abstract class ComicEpisodeRefreshService {
  Future<List<ComicEpisodeLink>> fetchEpisodeLinks(
    ComicEpisodeRefreshRequest request,
  );

  Future<ComicEpisodeRefreshOutcome> fetchCatalogOnly(
    ComicEpisodeRefreshRequest request,
  );

  Future<ComicEpisodeRefreshOutcome> fetchSearchAndCurrentOnly(
    ComicEpisodeRefreshRequest request,
  );
}
```

落点：

- `fetchCatalogOnly()` 只调用 `ComicEpisodeDiscoveryService.discoverFromTidWithPreference(preferCatalogFirst: true)`。
- 只有 `strategy == EpisodeDiscoveryStrategy.catalog && episodeLinks.isNotEmpty` 时返回 `catalogMatched=true`。
- `fetchSearchAndCurrentOnly()` 复用现有 `_searchFallbackFromCurrentTid()` 和 current-only 回退逻辑。
- `fetchEpisodeLinks()` 继续维持旧行为，避免一次性修改所有测试和调用点。

这样收藏自动刷新可以先调用 `fetchCatalogOnly()`，失败后只入队，不会误触发搜索。

### 2. 新增漫画封面提升服务

把“最小 `tid` 的第一张图片设为封面”从详情适配器和仓储私有方法中抽成一个可复用服务。

建议名称：

```text
lib/features/comic/domain/services/comic_first_episode_cover_service.dart
```

职责：

1. 读取漫画本地章节，按 `source_tid` 数值升序找最小 `tid`。
2. 如果该章节已有 `episode_images`，直接用第一张图。
3. 如果没有图片，调用 `ComicReaderService.fetchEpisodeImagesByTid(minTid)` 拉取图片。
4. 调用 `ComicRepository.saveEpisodeImages()` 写入图片，复用仓储内现有 `_promoteFirstEpisodeCoverIfNeeded()`。
5. 如果作品存在自定义封面，直接跳过。

建议接口：

```dart
class ComicFirstEpisodeCoverService {
  Future<bool> promoteIfPossible({
    required String comicId,
  });
}
```

这能同时服务：

- 收藏首次同步后的 catalog 成功。
- 搜索等待队列完成后。
- 详情页手动更新成功后。

### 3. 新增搜索等待队列

搜索等待队列建议拆成两个层次。

#### 3.1 通用搜索调度器

放在 search feature，负责 10.5 秒节流和队列快照，不依赖漫画。

建议路径：

```text
lib/features/search/domain/forum_search_scheduler.dart
```

核心能力：

- 暴露 `ValueListenable<ForumSearchQueueSnapshot>`。
- 统一计算 `estimatedSeconds = queueLength * 10.5`。
- 保证同一时刻只有一个搜索任务使用底层 `ForumSearchService`。
- 底层真实搜索服务建议重命名为 `rawDiscuzSearchServiceProvider`。
- 对 UI 暴露 `currentTitle`、`pendingCount`、`estimatedDuration`。

#### 3.2 漫画搜索刷新队列

放在 comic feature，负责持久化漫画任务和执行策略 2/3。

建议路径：

```text
lib/features/comic/domain/services/comic_search_refresh_queue.dart
lib/features/comic/data/comic_search_refresh_queue_repository.dart
```

建议持久化表：

```sql
CREATE TABLE comic_search_refresh_queue (
  task_id TEXT PRIMARY KEY,
  comic_id TEXT NOT NULL,
  source_tid TEXT NOT NULL,
  title TEXT NOT NULL,
  display_title TEXT,
  source_title TEXT,
  custom_title TEXT,
  custom_search_title TEXT,
  origin TEXT NOT NULL,
  status TEXT NOT NULL,
  priority INTEGER NOT NULL DEFAULT 0,
  attempt_count INTEGER NOT NULL DEFAULT 0,
  last_error TEXT,
  enqueued_at INTEGER NOT NULL,
  started_at INTEGER,
  completed_at INTEGER,
  next_run_at INTEGER
);
```

索引：

```sql
CREATE UNIQUE INDEX idx_comic_search_refresh_queue_active_comic
ON comic_search_refresh_queue(comic_id)
WHERE status IN ('pending', 'running');

CREATE INDEX idx_comic_search_refresh_queue_status_next
ON comic_search_refresh_queue(status, next_run_at, priority, enqueued_at);
```

任务状态：

- `pending`：等待搜索。
- `running`：正在执行策略 2/3。
- `succeeded`：已合并章节并完成封面尝试。
- `failed`：达到重试上限或发生不可恢复错误。
- `cancelled`：作品被移出书架或收藏被取消。

执行规则：

1. worker 只取一个 pending 任务。
2. 每次真实搜索前确保距离上次搜索至少 10.5 秒。
3. 调用 `fetchSearchAndCurrentOnly()`。
4. 若得到链接，调用 `mergeEpisodesFromLinks()`。
5. 调用 `ComicFirstEpisodeCoverService.promoteIfPossible()`。
6. 通知漫画书架和收藏书架刷新。
7. 标记任务完成。

去重规则：

- 同一个 `comic_id` 已有 pending/running 任务时不重复入队。
- 新请求可以更新 `title`、搜索关键词和 `origin`，但保留原始 `enqueued_at`，避免队列位置跳动。
- 详情页手动更新可以提高 `priority`，但不要插队到正在执行任务之前。

队列快照约定：

- `queueLength = runningCount + pendingCount`。
- `headTitle = running.title ?? firstPending.title`。
- `estimatedSeconds = queueLength * 10.5`，展示时最多保留 1 位小数，整数可省略 `.0`。
- 收藏页、论坛搜索页、详情页都只读取这个快照，不自行计算队列内部状态。

### 4. 书架刷新通知总线

新增 shared 层的轻量事件总线，让后台服务通知对应书架刷新。

建议路径：

```text
lib/features/library_shared/domain/services/library_shelf_invalidation_bus.dart
```

建议能力：

```dart
class LibraryShelfInvalidationBus {
  ValueListenable<int> listenableFor(LibraryModuleKey moduleKey);

  void notify(LibraryModuleKey moduleKey);

  void notifyMany(Iterable<LibraryModuleKey> moduleKeys);
}
```

接入方式：

- `ShelfModuleAdapter` 增加可选能力：

```dart
ValueListenable<int>? get shelfInvalidations => null;
```

- `UnifiedShelfController` 同时监听 `taskProgress` 和 `shelfInvalidations`。
- 收到 invalidation 时，执行非阻塞 `_reload()`，并保持现有 stale-while-revalidate 体验。

通知规则：

- 漫画章节合并或封面提升后：通知 `comic` 和 `favorite`。
- 小说收藏入库刷新后：通知 `novel` 和 `favorite`。
- 收藏同步列表变化后：通知 `favorite`。

这样“实时自动刷新漫画和小说的 shelf 页”不需要页面轮询，也不需要业务服务持有页面 controller。

## 分阶段实施方案

### 阶段 1：刷新策略拆分与结果建模

预计耗时：0.75 天

改动范围：

- `lib/features/comic/domain/services/comic_services_impl.dart`
- `test/features/comic/domain/services/network_comic_episode_refresh_service_test.dart`

实施内容：

1. 增加 `ComicEpisodeRefreshOutcome`、`ComicEpisodeRefreshSource`。
2. 为 `NetworkComicEpisodeRefreshService` 增加 `fetchCatalogOnly()`。
3. 为 `NetworkComicEpisodeRefreshService` 增加 `fetchSearchAndCurrentOnly()`。
4. 保留现有 `fetchEpisodeLinks()`，内部改为先 `fetchCatalogOnly()`，失败后调用 `fetchSearchAndCurrentOnly()`，从而兼容旧调用方。
5. 给搜索回退方法返回更明确的 `usedSearch` 信息，方便详情页判断是否需要入队或提示。

验收标准：

- 现有漫画刷新单测继续通过。
- 新增单测覆盖：
  - catalog 成功时 `catalogMatched == true`。
  - catalog 失败时不会触发 `ForumSearchService.searchForum()`。
  - `fetchSearchAndCurrentOnly()` 能复用现有搜索候选评分和 current-only 回退。

### 阶段 2：封面提升服务解耦

预计耗时：0.5 天

改动范围：

- 新增 `lib/features/comic/domain/services/comic_first_episode_cover_service.dart`
- `lib/features/comic/data/comic_repository.dart`
- `lib/features/comic/data/local_comic_repository.dart`
- `lib/features/comic/domain/services/comic_services_impl.dart`
- `lib/features/comic/presentation/adapters/comic_detail_adapter.dart`

实施内容：

1. 新增 `ComicFirstEpisodeCoverService`。
2. 服务内部复用 `ComicRepository.getComicEpisodes()`、`getEpisodeImages()`、`saveEpisodeImages()`。
3. 图片缺失时，复用 `ComicReaderService.fetchEpisodeImagesByTid()`。
4. 如有必要，在 `ComicRepository` 增加只读方法读取封面元数据，避免覆盖自定义封面。
5. `ComicDetailAdapter.loadHeader()` 可以继续保留兜底逻辑，但优先交给新服务处理，逐步减少详情页里的封面副作用。

验收标准：

- 最小 `source_tid` 章节第一张图能写回 `comics.cover_image_url`。
- 已设置自定义封面时不覆盖。
- 收藏页、漫画书架、详情页读取到同一个普通封面源。

### 阶段 3：搜索等待队列与搜索调度器

预计耗时：1.25 天

改动范围：

- 新增 search 调度器。
- 新增 comic 搜索队列仓储和服务。
- `lib/features/comic/data/local/comic_local_db.dart`
- `lib/features/search/data/discuz_search_service.dart`
- `lib/features/search/data/search_rate_limiter.dart`

实施内容：

1. `ComicLocalDb` 增加 `comic_search_refresh_queue` 表，并把 `dbVersion` 从 15 提升到 16。
2. 新增 `ForumSearchScheduler`，统一持有 10.5 秒节奏。
3. 将 `discuzSearchServiceProvider` 拆为：
   - `rawDiscuzSearchServiceProvider`：只负责真实网络搜索。
   - `forumSearchSchedulerProvider`：负责排队、快照、节流。
4. 新增 `ComicSearchRefreshQueueService`：
   - `enqueue(request, title, origin)` 返回队列位置和预计耗时。
   - `start()` 恢复 pending/running 任务。
   - `snapshot` 暴露当前队列标题、数量、预计耗时。
5. worker 执行策略 2/3、合并章节、提升封面、通知书架。
6. app 启动或主壳页面加载时启动 queue runner，保证离开详情页后任务仍继续。

验收标准：

- 同一漫画重复入队只保留一个 active 任务。
- fake clock 下能验证两个任务之间至少间隔 10.5 秒。
- worker 中途异常会写入 `last_error` 并按重试策略延后。
- app 重启后 pending/running 任务能恢复为 pending 并继续执行。

### 阶段 4：收藏首次同步与新增收藏自动刷新

预计耗时：1 天

改动范围：

- `lib/features/favorites/data/favorite_sync_service.dart`
- `lib/features/favorites/data/local_favorite_repository.dart`
- `lib/features/favorites/presentation/adapters/favorite_shelf_adapter.dart`
- `lib/features/favorites/data/favorite_providers.dart`
- `lib/features/comic/data/comic_favorite_ingest_service.dart`
- `lib/features/novel/data/novel_favorite_ingest_service.dart`

实施内容：

1. `LocalFavoriteRepository` 增加 `countMissingDetailRecords()`，用于计算收藏详情解析总数。
2. `_fillMissingDetails()` 进入每条记录前发出：

```dart
FavoriteSyncProgress(
  phase: FavoriteSyncProgressPhase.loadingDetails,
  message: '正在解析: ${record.title}',
  current: processed + 1,
  total: totalMissingDetails,
)
```

3. 在漫画 `_syncModule()` 成功写入漫画后，调用新的 `ComicFavoriteAutoRefreshCoordinator`：
   - 先 `fetchCatalogOnly()`。
   - catalog 成功则 `mergeEpisodesFromLinks()`。
   - 调用封面提升服务。
   - 通知 `comic` 和 `favorite` 书架刷新。
   - catalog 失败则加入搜索等待队列。
4. 小说 `_syncModule()` 保持现有 `refreshEpisodes()`，成功后通知 `novel` 和 `favorite` 书架刷新。
5. 首次无 `FavoriteSyncSnapshot` 时，收藏同步本来会全量补全详情。此时所有识别为漫画的收藏都会经过上述 catalog-only 引导，等价于“对收藏中的全部漫画调用一次策略 1”。
6. 为兼容已有旧本地数据，可增加一个低优先级一次性回填：
   - 查询 active favorite comic 记录。
   - 如果作品章节数为 0 或只有当前 `sourceTid`，执行一次 catalog-only。
   - 失败则入队搜索。
   - 回填完成后用队列表或 work state 记录，避免每次启动重复扫描。
7. `FavoriteShelfAdapter.taskProgress` 改成组合进度：
   - 收藏同步 active 时，显示收藏同步进度。
   - 收藏同步不 active 但搜索队列非空时，显示搜索等待队列消息。

搜索等待消息格式：

```text
{headTitle} 正在等待搜索 预计耗时{estimatedSeconds}s
```

其中 `headTitle` 优先使用收藏列表中的 `FavoriteThread.title`，不要使用详情页重新解析后的 subject。

验收标准：

- 收藏页解析阶段左侧显示 `正在解析: title`，右侧显示 `n/total`。
- 漫画收藏 catalog 成功后，不需要进入详情页即可生成章节。

## 关键重构建议

### 1. 不建议让 `fetchEpisodeLinks()` 自己决定入队

`fetchEpisodeLinks()` 应该是纯刷新策略服务。是否立即搜索、是否后台排队，属于上层编排。这样收藏同步、详情页、测试都能明确控制行为。

### 2. 不建议在 UI 层直接创建搜索 `Timer`

队列必须在服务层持久化和运行。UI 只显示 `snapshot`，否则详情页关闭后任务会丢失，也难以让论坛搜索知道队列状态。

### 3. 推荐把搜索服务分为 raw 与 scheduler

底层 `DiscuzSearchService` 只负责 HTTP、cookie、formhash、解析。调度器负责等待、队列、提示和全局搜索互斥。这样不会让搜索数据层反向依赖漫画。

### 4. 推荐封面提升只写普通封面

自动封面来自最小 `tid` 第一张图片，应写入 `cover_image_url/cover_local_path`，不要写入 `custom_cover_*`。用户自定义封面永远优先。

### 5. 推荐用 invalidation bus 刷新书架

直接在后台服务里拿页面 controller 或强制 rebuild 页面会造成耦合。shared 层事件总线更适合当前 `UnifiedShelfPage + Adapter` 架构。
